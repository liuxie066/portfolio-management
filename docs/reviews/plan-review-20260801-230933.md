## Assumptions Tested

1. Every official NAV writer can construct and pass the one fresh `CashFlowDatasetSnapshot` required by S6.
2. S9's allowed file boundary can make one normalized valuation snapshot feed both NAV totals and persisted snapshot rows.
3. S10's `overwrite_existing + confirm` authority can reach the exact-set engine and be durably reused by compensation.
4. S5's duplicate rule distinguishes a unique cash-flow row from an actual duplicate group.
5. The proposed registry remains metadata-only and does not absorb financial formulas or runtime state.
6. Optional/unconfigured live tables and legacy transaction Text fields can be represented without a live migration.

Assumptions 1-4 were disproved by direct plan/source evidence. Assumptions 5-6 remain credible.

## Findings

### PR-01-未修复-高-S6 未覆盖全部官方 NAV 写入口，初始化路径会在新 fail-closed 契约下失效
- **位置**: S6 Allowed files、Exact changes 4-6、Tests
- **问题类型**: 架构边界 / 契约缺失 / 不可直接实施 / 测试缺口
- **当前写法**: 顶层 precheck 创建唯一现金流数据集，`AccountNavRecorderService` 将其传给下游；任何没有完整兼容数据集的官方 NAV 持久化必须失败。
- **反例/失败场景**: `NavInitializationService` 直接调用 `PortfolioManager.record_nav(..., persist=True)`，既不经过 `AccountNavRecorderService`，也没有 `run_id` 或现金流数据集。若按 S6 对 `NavRecordService` 加 fail-closed 门禁，空账户初始化会直接失败；若让下游自行扫描，则又违反“一次官方运行只使用一个顶层事实集”的目标。
- **为什么有问题**: 实施者只能在破坏初始化入口和让下游重新读存储之间二选一。S6 的允许文件不包含 `src/app/nav_initialization_service.py`，测试命令也没有明确覆盖初始化的相同对象/指纹契约。
- **直接证据**: 计划第 476-500 行只列出 `AccountNavRecorderService` 等文件并声明下游不访问 storage；`src/app/nav_initialization_service.py:69-96` 构建估值后直接调用 `portfolio.record_nav(... persist=True)`；`src/portfolio.py:204-227` 的公共委托签名没有现金流数据集参数。
- **影响**: 初始化功能回归，或官方 NAV 再次出现双扫描/不同事实集，S6 的核心成功信号不可证明。
- **建议改法和验证点**: 在计划中指定唯一 `CashFlowDatasetFactory`/builder 的所有权；将 `NavInitializationService`、相应测试和所需公共签名纳入 S6。明确所有 `persist=True` 入口必须由顶层构造并传入数据集，`persist=False` 的 repair/preview 使用显式非官方 fresh dataset 或明确豁免。新增初始化、手工记录、daily job 三条入口均传递同一对象和指纹的测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-S9 的文件边界无法兑现“估值快照是 NAV 与明细唯一输入”
- **位置**: S9 Objective、Allowed files、Exact changes 1-4、Completion signal
- **问题类型**: 架构边界 / 切片边界 / 不可直接实施 / 过度耦合
- **当前写法**: S9 新建 `NormalizedValuationSnapshot`，并要求 NAV totals 与 holdings_snapshot rows 消费同一个对象。
- **反例/失败场景**: 当前 `ValuationService` 直接把逐行计算累加为 `PortfolioValuation` 浮点汇总；`NavRecordService` 只接收该 `PortfolioValuation`，随后让 `SnapshotService` 再次从其中的 mutable holdings 构造行。S9 不允许修改 `NavRecordService`、`PortfolioManager` 或 `PortfolioValuation` 契约，因此即使生成了 normalized 对象，也无法证明 NAV 与持久化行消费的是同一实例。
- **为什么有问题**: 计划的最重要计算唯一真源承诺跨越了估值、NAV 编排和快照持久化三个边界，但切片只开放估值/读取/快照侧。实施者会被迫把对象隐藏在动态属性、重复投影，或越过允许文件范围。
- **直接证据**: 计划第 643-669 行要求同一对象，第 650-662 行未包含 NAV 编排或公共模型文件；`src/app/valuation_service.py:96-246` 独立累计并构造 `PortfolioValuation`；`src/app/nav_record_service.py:301-327` 再调用 snapshot builder/persist；`src/app/snapshot_service.py:40-60` 从 `valuation.holdings` 二次构造行。
- **影响**: F10/F12 看似关闭但 NAV 和审计快照仍可能因精度、过滤或字段投影不同而漂移；review 无法验收“同一个对象”这一成功信号。
- **建议改法和验证点**: 在 S9 明确 normalized 对象的公共传递契约及所有权：优先由 `ValuationService` 一次构造，`PortfolioValuation` 只作为它的兼容投影，顶层 snapshot payload 显式携带 normalized 对象，`NavRecordService` 与 `SnapshotService` 均只消费它。把实现该传递链所需的模型、`portfolio.py`、`account_nav_recorder_service.py`、`nav_record_service.py` 及测试加入允许范围；或重排切片使该契约先于依赖它的 NAV 公式完成。测试必须故意篡改兼容投影并证明官方写入拒绝，而不能静默采用第二套数值。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-03-未修复-高-S10 要求双重覆盖授权，但 confirm 没有传到 exact-set 引擎
- **位置**: S10 Allowed files、Exact changes 3-9、Expected assertions
- **问题类型**: 权限边界 / 契约缺失 / 状态机漏洞 / 并发恢复风险
- **当前写法**: 首次写入不允许已有 slice；重写必须同时具备 `overwrite_existing/confirm`；compensation 复用已记录的授权。
- **反例/失败场景**: 当前 `confirm` 只存在于 `AccountNavRecorderService`/服务入口的防误写检查，`PortfolioManager.record_nav` 与 `NavRecordService.record_nav` 只接收 `overwrite_existing`。S10 又未把 `AccountNavRecorderService` 或初始化入口列为允许文件，因此 exact-set plan 无法知道 confirm 是否真实存在，也无法把授权范围和目标摘要写进 prepared event。简单地把 `overwrite_existing=True` 当作授权会弱化用户确认边界；每次 recovery 重新要求交互确认则无法自动重放已授权目标。
- **为什么有问题**: 这是写入权限而非普通参数遗漏。授权必须在第一个可能破坏既有 slice 的动作前被验证、绑定到 account/as_of/plan digest，并随 durable prepared event 传递。
- **直接证据**: 计划第 706-728 行没有顶层入口文件但要求复用授权；`src/portfolio.py:204-227` 没有 `confirm` 参数；`src/app/account_nav_recorder_service.py:212-222` 只向 portfolio 传 `overwrite_existing`；`src/app/snapshot_service.py:63-76` 也没有覆盖授权参数。
- **影响**: 可能未经完整确认删除/清空既有快照，或导致所有合法 overwrite/recovery 被阻断；compensation 的权限语义不可审计。
- **建议改法和验证点**: 定义最小的不可变 `SnapshotWriteAuthority`（account、as_of、overwrite_existing、confirmed、plan_digest/target_digest、issued_by/run_id），只由顶层入口创建。S10 纳入所有传播文件；prepared event 持久化该 authority，recovery 仅对完全匹配的目标复用，目标变更必须重新确认。测试覆盖缺 confirm 零写、scope/digest 不匹配零写、匹配 recovery 可重放、daily first-write 不需要 overwrite。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-04-未修复-高-S5 的重复判定文字会把每个正常单条分组都阻断
- **位置**: S5 Exact changes 2、Expected assertions
- **问题类型**: 契约缺失 / 不可直接实施 / 测试缺口
- **当前写法**: “Group by expected canonical dedup ... Any group with an in-scope row blocks all members.”
- **反例/失败场景**: 每个有效的单条 cash-flow 都会形成一个包含一条 in-scope row 的分组。照当前精确文字实现，所有正常单条记录都被标为 duplicate blocker，任何官方 NAV 都无法取得完整数据集。
- **为什么有问题**: 完成信号要求只有“unique”记录可完成，但当前规则没有 `group size > 1`、重复 record_id 或冲突范围条件，直接与目标相反。
- **直接证据**: 计划第 439-444 行给出精确实施顺序和当前条件；第 452 行只测试“duplicate groups block all members”，没有证明 singleton passes。
- **影响**: 所有账户现金流 reconcile/NAV 写入被错误阻断，是确定性的用户可见回归。
- **建议改法和验证点**: 改为“同一 expected canonical dedup 下有两个或以上不同 record_id 时，该组全部阻断”；明确重复检测基于 fresh full account scan，不能被 date filter 隐藏。新增 singleton 完成、两条相同 dedup 全阻断、observed dedup 被篡改仍按 expected dedup 成组、同一 record 不因投影重复计数的测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

## Open Questions

- `PortfolioValuation` 是继续作为 normalized snapshot 的只读兼容投影，还是由顶层 payload 并行携带 normalized 对象？计划修复时必须选定一种，不能留给实现阶段临时决定。
- 初始化首条 NAV 的现金流窗口起点应使用哪个明确规则？它需要与 S6 dataset window 和 S8 cash-flow basis 使用同一个定义。

## Residual Risks and Tracking Destination

- 现有 holdings 业务记录是否存在空 broker 或其它不符合新 fail-closed 契约的值尚未读取。该风险不应放宽源代码校验；应在部署前的、另行授权的只读数据一致性审计中跟踪。
- Feishu Number 的实际往返精度仍需独立 canary，继续留在 production-use gate。
- 外部编辑者在 fresh read 与 write 之间修改记录的竞态属于后续跨主机并发控制 work unit；本计划必须保留 as-of/fingerprint 和 unknown/partial 状态。
- 本 work unit 很大，逐 slice accepted commit 和 aggregate deepreview 是必要审计边界；不得为了缩短流程合并跳过。

## Conclusion

`fail`

方向和分层唯一真源设计成立，但以上四个 finding 使当前计划尚未达到 code-generation-ready。进入 implementation 前必须修订并重新执行 planreview，且 re-review 要逐项证明四个断口已闭合。
