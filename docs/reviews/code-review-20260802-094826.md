### DR-AGG-01-未修复-高-`asset_name` 在持仓注册表中必填，但校验层仍将缺失值变成可用的空名称

- **入口/函数**: `HoldingsValidator.validate()` -> `_asset_name()` -> `RecordValidation.valid_for_typed_holding` / `to_holding()` -> `ValidatedHoldingsSnapshot.from_evaluation()`
- **文件(行号)**: `src/feishu/contracts/registry.py:67-105,227-240`; `src/app/holdings_validation.py:24-51,291-374,462-517,685-746`; `src/app/holdings_nav_preflight_service.py:194-243`
- **输入场景**: 飞书 holdings 行具备 asset_id/asset_type/account/broker/quantity/currency，但 `asset_name` 缺失或空白，并进入正式 NAV 前的 raw-row validation。
- **实际分支**: 注册表 create row-required 包含 `asset_name`，严格 repository reader 也拒绝空名；但 app 层手写 `REQUIRED_FIELDS` 遗漏该字段，`_asset_name()` 返回 `optional_missing`/nonblocking，`to_holding()` 再用 `or ""` 构造 typed `Holding`。
- **预期行为**: row-required 集和 validation projection 从注册表投影；缺失名称必须保留为 blocking missing/completable state，在修补并重读前不得构造正式 typed holding。已存在的 manual name 即使与 provider 建议冲突，仍按 manual ownership 保留且不阻断。
- **实际行为**: 直接复现返回 `asset_name_status=optional_missing`, `blocks=False`, `valid_for_typed=True`, `typed_name=''`。正式 preflight 可因此发布一个与 strict repository/read contract 相矛盾的持仓快照。
- **直接证据**: 注册表 create required 为 `asset_id, asset_name, asset_type, account, broker, quantity, currency`；app `REQUIRED_FIELDS` 只有其中六个；`_asset_name()` 把无 provider 的缺失值标成 `ASSET_NAME_OPTIONAL_MISSING`；`to_holding()` 显式使用空字符串 fallback。
- **影响**: 核心 holdings 读、写、校验对同一字段作出不同决定；原始缺失会被 model default 遮蔽，破坏本 work unit 的 parser-default shield 和正式 NAV 完整性门禁。
- **建议改法和验证点**: 从 holdings create contract 导出 required/relevant fields；让 missing `asset_name` 阻断 typed conversion；让已存在的 nonblocking manual conflict 仍可使用 current raw value。增加 missing/no-evidence、missing/provider-completable 和 manual/provider-conflict 回归。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-AGG-02-未修复-高-`cash_flow` create contract 放行无业务键和无完成事实的核心行

- **入口/函数**: `FeishuClient.create_record()` / `batch_create_records()` -> `validate_write_fields("cash_flow", "create", ...)`
- **文件(行号)**: `src/feishu/contracts/registry.py:107-129,241-250,358-426`; `src/domain/cash_flow_contracts.py:20,133-220,229-460`; `docs/schema.md:48-74`
- **输入场景**: 直接调用公开 client create，只提供 flow_date/account/amount/currency，不提供 broker、dedup_key、flow_type、cny_amount、exchange_rate 和 source。
- **实际分支**: registry create required 只包含四个字段，因此 single/batch client 都会进入远端请求；但领域 `ManualCashFlowFacts` 要求 nonblank broker，`CompletedCashFlowFacts` 还要求其他 generated facts，且 registry 自身宣告业务键为 `dedup_key`。
- **预期行为**: 任何应用写入的 cash-flow create row 必须是 CompletedCashFlowFacts 的完整持久投影，create required 至少覆盖业务键、manual required 和 generated required fields；缺失时在网络请求前拒绝。
- **实际行为**: 直接复现显示 `{flow_date, account, amount, currency}` 被 `validate_write_fields` 接受。这类行之后会被 completed validation 和 aggregate/NAV gate 拒绝，却已成为远端核心表污染。
- **直接证据**: `cash_flow.business_key == ("dedup_key",)` 但 `dedup_key` 不在 create required；人写 schema policy 明确说 broker mandatory，generated contract 却不要求 broker；注册表和领域还分别硬编码了 DEPOSIT/WITHDRAW 集合，没有唯一投影。
- **影响**: 绕过 repository 的直接 client 调用可创建无法参与聚合、effect gate 或幂等 replay 的核心数据；业务键不是 create invariant，也无法保证防重。
- **建议改法和验证点**: 将 cash-flow create required 收紧为 completed persisted fields；建立通用断言，所有可写表的 business key 必须是 create-required 子集；由领域 cash-flow type contract 唯一定义状态值，registry 只投影 select options。验证 single/batch 零请求拒绝和 CompletedCashFlowFacts 完整通过。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-AGG-03-未修复-中-snapshot exact-set 使用的业务键顺序与注册表相反，全行 digest 也没有字段覆盖断言

- **入口/函数**: `snapshot_business_key()` / `snapshot_digest()` / `SnapshotExactSetPlan` / `SnapshotsRepository._changed_fields()`
- **文件(行号)**: `src/feishu/contracts/registry.py:150-174,258-269`; `src/domain/snapshot_contracts.py:88-165,194-395,775-801`; `src/feishu/repositories/snapshots_repository.py:15-96`; `src/snapshot_models.py:19-47`
- **输入场景**: 一个 snapshot 行 `as_of=2026-08-01, account=lx, asset_id=AAPL, broker=IBKR` 同时被 registry/schema tooling 和 exact-set planner/digest 消费；或后续向 snapshot registry/model 增加一个持久字段。
- **实际分支**: registry/已验收方案定义键顺序为 `(as_of, account, asset_id, broker)`；`snapshot_business_key()` 却返回 `(account, as_of, broker, asset_id)`，digest 也使用后者排序。`dedup_key` 字符串公式在 scope assertion 和 row builder 中重复。此外 `snapshot_row_payload()` 手写全部字段，但 model/registry/payload 之间没有可执行 coverage assertion。
- **预期行为**: 一个 domain-owned canonical snapshot business-key field tuple 驱动领域 key/sort 与 registry projection；dedup 只有一个函数；model fields、registry fields 和 full-row payload 存在 fail-fast 零漂移断言。
- **实际行为**: 直接复现得到 registry names `(as_of, account, asset_id, broker)`，domain values `('lx', '2026-08-01', 'IBKR', 'AAPL')`，按 registry 应为 `('2026-08-01', 'lx', 'AAPL', 'IBKR')`。当前字段集虽恰好相等，但新字段可被远端读取后由 Pydantic 默认忽略，并继续产生“完整”digest。
- **直接证据**: 方案与 generated `docs/schema.md` 都使用 registry 顺序；领域函数 docstring 和 tuple 使用另一顺序；`HoldingSnapshot.model_config` 未设 `extra='forbid'`；repository 只从 registry 生成读 projection，未比对 model field set。
- **影响**: 业务键对外定义和实际 plan/digest 语义分叉；未来 schema 扩展可被 exact-set readback/digest 静默丢弃，从而对非全行状态误报完成。
- **建议改法和验证点**: 在 snapshot domain 定义 canonical key fields 和 dedup helper，registry 从前者投影 business key，exact-set/digest 共用；full-row payload 从 strict model dump 完整投影并仅对 Number 做 canonicalization；repository import 时断言 model/registry 字段集和顺序一致。增加 key-order、dedup 和 field-coverage 回归。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中
