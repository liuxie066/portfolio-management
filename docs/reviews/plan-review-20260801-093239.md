# Plan Review — Holdings Case Precondition Identity

## Reviewed Target and Scope

- Target: `docs/gateflow/holdings-case-precondition-identity/implementation-plan.md`
- Review mode: adversarial implementation-plan review
- Included: case/precondition identity, v1-to-v2 lifecycle, durable confirmations,
  discovery/closure receipts, NAV preflight interaction, rollback, and the tests
  needed to prove those contracts.
- Excluded: fixing the implementation plan, source-code changes, production
  state mutation, commit/push, release, and remote upgrade.
- User boundary retained: the review is limited to the SPY workflow collision and
  the plan's proposed mechanism; it does not reopen timestamp, tag, listener, or
  asset-class-policy work.

## Assumptions Tested

1. A record-scoped SPY notify can migrate only the repaired `asset_name` case.
   This is false: materialization processes every currently active case on the
   record, including the unchanged timestamp cases in the plan's own regression
   fixture.
2. A v2 case-key transition is lazy and operationally bounded by avoiding an
   all-account notify. This is false: the canonical NAV preflight evaluates and
   materializes an account-wide plan.
3. Existing v1 `resolved_keep` decisions can safely remain audit history without
   a compatibility transition. This is false for blocking cases because plan
   evaluation recognizes a durable confirmation only by the exact current case
   key and confirmation scope.
4. Rolling the application back without deleting v1/v2 rows is a safe rollback.
   This is incomplete: changing the key contract in both directions drives real
   supersede/reopen transitions and interacts with deduplicated receipt keys.
5. The store collision guard should remain fail-closed. This assumption is
   supported and should be preserved; the findings below do not recommend
   weakening generic collision detection.

## Findings

### PR-01-未修复-高-v2 全局换 key 会使既有 resolved_keep 失效并重新阻断官方 NAV
- **位置**: `Case identity v2`、`Confirmation and outage safety`、`Migration and Rollout`、`State transitions`
- **问题类型**: 状态机漏洞
- **当前写法**: 方案把 `CASE_CONTRACT_VERSION` 从 v1 升到 v2，并把 precondition digest 放入 case key；同时声明 v1 `resolved_keep` 对 v2 无效、v1 行仅保留为审计历史，并通过惰性 materialization 完成迁移。
- **反例/失败场景**: 某账户已有一个会阻断 NAV、且已经人工 `resolved_keep` 的 v1 case。升级后下一次官方 NAV preflight 为该事实生成 v2 key。`plan_evaluation()` 只按 v2 key 查询 durable case，找不到 v1 确认，于是把新 case 放入 `blocking_case_keys`；随后 preflight 先 materialize v2 case、supersede v1 case，再返回 `holdings_confirmation_required`。原本已被人工确认的账户因此重新阻断 NAV。
- **为什么有问题**: 用户目标是解除一个不相关字段导致的 SPY 碰撞，不是让所有既有人工确认失效。方案将局部 identity bug 扩大为全局确认合同迁移，却没有确认迁移矩阵、现状盘点、NAV 连续性门禁或重新确认流程。
- **直接证据**: 方案第 75-93 行要求全局 v2 key 并明确 v1 `resolved_keep` 无效，第 150-160 行仅说明惰性替换。`src/app/holdings_workflow_service.py:172-199` 仅在“当前 exact case key 存在 `resolved_keep` 且 scope 相同”时移除 blocking key；`src/app/holdings_nav_preflight_service.py:337-355,377-400` 对账户全部 records 生成并 materialize plan，之后才根据 `blocking_case_keys` 返回结果；`src/app/operation_state_store.py:29-32,838-893` 将旧 `resolved_keep` 纳入 supersede 范围。
- **影响**: 官方 NAV 可在升级后意外中断；已完成的人工作业失效；用户需要重复确认；回滚和恢复复杂化。
- **建议改法和验证点**: 先把方案改为显式的迁移状态机。优先评估保持 semantic case key 稳定、把 field-specific precondition 作为独立确认/apply token，并按 pending、resolved_keep、applying、apply_outcome_unknown 分别定义 precondition 变化的处理。若仍采用 v2 key，必须增加升级前 v1 blocking/resolved_keep 盘点、仅在新旧字段级 authority scope 等价时迁移确认的规则、不可迁移时的人工门禁，以及“已有 resolved_keep 的账户升级前后 NAV 结果不变”的端到端测试。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-SPY 精确 notify 也会制造迁移型关闭和发现回执，违反单一关闭回执验收
- **位置**: `Success Signals`、`Case identity v2`、`State transitions`、`Migration and Rollout`、`Tests and Expected Assertions`
- **问题类型**: 契约缺失
- **当前写法**: 成功信号要求 SPY 旧 `asset_name` case 关闭并只排入一条 closure receipt，未变化的 timestamp cases 保持 open；与此同时，方案规定不同 v2 key 会 supersede 旧 case、创建 replacement，并让 closure/discovery receipts 一起提交。
- **反例/失败场景**: 方案自己的 SPY 回归样例同时存在 `created_at`、`updated_at` open cases。即使 field-specific precondition 已不再受 `asset_type` 影响，contract version 从 v1 变为 v2 仍会改变这两个 case key。一次 record-scoped notify 会对每个 timestamp case 生成旧 key 的 superseded closure receipt和新 key 的 discovered receipt；此外才是 repaired `asset_name` 的 `resolved_external` closure。用户会看到与本次修复无关的“关闭后重新发现”消息，且总回执数不再是成功信号描述的一条。
- **为什么有问题**: “不运行 all-account notify”不能限制一次 exact-record materialization 内的迁移范围。方案既要求 timestamp cases 继续 open，又把它们当作 semantic case changed 关闭并重建，缺少 migration-only receipt 的产品语义和精确数量约束。
- **直接证据**: 方案第 10-13、31-39 行明确 exact SPY 场景和单一 closure 信号，第 75-84、130-145、164-182 行要求所有不同 key 走 supersede + replacement。`src/app/operation_state_store.py:838-893` 为每个旧 key 生成 superseded closure；同文件 `1007-1060` 为每个新 key 创建 discovered event 和 discovery receipt；`src/app/holdings_workflow_service.py:1118-1122` 的 discovery receipt key直接包含新 case key。
- **影响**: 飞书回执噪声、人工误解、验收条件自相矛盾，并可能在账户级 NAV preflight 时放大为全账户消息风暴。
- **建议改法和验证点**: 在方案中选择并固定一种迁移回执策略：相同事实的 contract migration 应静默迁移并保留一条连续 lifecycle，或明确把它视为需要重新确认的新事实并取得用户授权；不能复用普通 semantic supersession 语义而不计回执。为 exact SPY 测试断言完整 case/event/outbox 集合和精确数量：仅 name 的外部关闭是否发一条消息、两个 timestamp 是否保持同一生命周期、重复 notify 是否为零增量；再增加账户级 preflight 的回执上限测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-03-未修复-中-当前 rollback 会反向 supersede v2 并静默 reopen v1，不是安全回退
- **位置**: `Migration and Rollout`、`Tests and Expected Assertions`
- **问题类型**: 并发恢复风险
- **当前写法**: 方案只规定回滚到前一应用版本，并保留所有 v1/v2 case rows；没有定义回滚后的 case authority、receipt 行为和 NAV 验收。
- **反例/失败场景**: v2 已 materialize 后回滚到生成 v1 key 的旧版本。下一次 materialization 会把 active v2 case supersede；已有的 v1 row 处于 `superseded`，因此会被 reopen。v1 discovery receipt key 早已存在，reopen 路径又不会新建 discovery receipt，导致 case 再次 open 但用户未收到新的发现通知。若该 case blocking，NAV 还会再次改变状态。
- **为什么有问题**: 不删除数据只保证审计行存在，不能保证回滚的业务状态和通知可恢复。key contract 的双向切换是状态迁移，不是普通二进制回退。
- **直接证据**: 方案第 150-160 行把“保留 v1/v2 行”当作完整 rollback。`src/app/operation_state_store.py:33-37,935-970` 会将已有 `superseded` case reopen；同文件 `838-893` 会 supersede 另一 contract 的 active case；`1007-1060` 只在全新 insert 时创建 discovery receipt，而 reopen 分支在第 970 行直接结束；`src/app/holdings_workflow_service.py:1118-1122` 还把 discovery receipt 唯一性绑定到 case key。
- **影响**: 回滚后出现状态振荡、未通知的 open case、NAV 行为变化，且运维人员无法仅靠版本回退恢复到升级前语义。
- **建议改法和验证点**: 在修改 key contract 前定义可逆迁移或明确 forward-fix-only 边界。增加“v1 -> v2 materialize -> 旧版本语义 materialize”的 deterministic rollback test，断言唯一 active lifecycle、confirmation authority、blocking 结果和消息可见性；发布门禁必须记录升级前 case/outbox 快照，并给出触发 rollback 后的恢复步骤。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 中

## Open Questions

1. v1 pending case 切换到 field-specific precondition 后，应当保持同一用户可见生命周期，还是明确关闭并重新发现？这是实施前必须固定的产品合同。
2. 对 v1 `resolved_keep`，哪些字段级 authority inputs 等价时允许迁移既有确认，哪些必须重新人工确认？
3. migration-only state event 是否允许生成飞书消息；若允许，单条 record notify 和账户 NAV preflight 的最大回执预算分别是多少？

## Residual Risks and Tracking Destination

- `materialize_holding_cases()` 与 `materialize_and_prepare_holding_apply()` 各自实现了一套 supersede/collision 状态机。修订计划应要求共享迁移规则，或分别覆盖 read/notify path 和 apply path 的原子性、stale-scope、rollback 测试；跟踪到本 work unit 的 revised implementation plan，而不是另开范围。
- 发布前仍需只读盘点 v1 active、blocking、resolved_keep cases 和 outbox 状态，用于验证迁移上限；跟踪到本 work unit 的 rollout gate，不包含本次 review 的生产写入。
- field-specific dependency map 本身方向合理，但 `asset_type` 对每个字段是否构成 authority input 应由已有 validation policy 的实际读取路径逐项验证；跟踪到 S1 focused tests。

## Conclusion

`fail`

Field-specific precondition 是正确方向，但当前计划把局部碰撞修复绑定到全局 v2 key 迁移，且没有闭合 durable confirmation、NAV preflight、receipt fanout 和 rollback 合同。修订后应再次运行 PlanReview，再进入实现。
