## Assumptions tested

- Existing Daily NAV results always retain Holdings preflight workflow facts
  after the workflow has been materialized.
- Counts alone preserve the operational usefulness of the individual discovery
  receipts that the plan suppresses.
- The explicit `enqueue_receipts` switch can change delivery without changing
  case/event persistence.
- Existing `nav:<run_id>` durability is sufficient for the aggregate envelope.
- Global and account summaries can be rendered without duplicate rows.
- The design does not require a new schema, queue, or general notification
  abstraction.

## Findings

### PR-01-未修复-高-后置失败路径会丢失已抑制回执的聚合事实
- **位置**: `Failure, retry, and idempotency`、S1 steps 2-4、validation assertions
- **问题类型**: 状态机漏洞 / 测试缺口 / 不可直接实施
- **当前写法**: 计划要求 Daily NAV preflight 不再入队单 Case 回执，并假设正常 blocking preflight 会进入最终 NAV 回执；实现范围只笼统要求传播 aggregate result。
- **反例/失败场景**: 账户预检已正式 materialize/close cases，随后 valuation、NAV persistence 或 `DailyReportPayloadService.build()` 抛错。单 Case 回执已被抑制，但失败返回没有携带 `holdings_preflight`，最终 NAV 失败/partial 回执也无法呈现这些已提交的生命周期变化。
- **为什么有问题**: 通知抑制和聚合传播跨越多个返回路径；只覆盖成功/直接 preflight blocker 会把真实已提交的 Case/Event 变成用户不可见状态，违背“一个完整任务信封”而不是“静默丢通知”的目标。
- **直接证据**: `AccountNavRecorderService.record()` 在 `holdings_preflight_result` 赋值后可能于 snapshot/record 阶段进入 `except`，该返回仅含 success/error/account/date/run_id/dry_run/confirm；`DailyAccountNavService.run()` 的 payload exception 返回包含 `nav_result`，但不包含 `record_result['holdings_preflight']`。两条路径都会被 `DailyNavJobService.items` 和最终 NAV renderer 消费。
- **影响**: 自动发现/关闭已写入审计状态但不出现在任何用户回执；出现 partial/failure 时最需要上下文，却只看到后置错误。
- **建议改法和验证点**: 计划必须要求一旦 preflight result 存在，所有后续 success/partial/failure return paths 都传播 sanitized `holdings_preflight`；新增 snapshot/record exception 与 report-payload exception 回归，断言最终 item 和 NAV message 仍包含正确 workflow counts。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-中-聚合仅保留计数会让自动发现的阻断 Case 失去处理入口
- **位置**: `Non-goals and scope boundary`、`Aggregate result contract`、`Rendering and ordering`
- **问题类型**: 契约缺失 / 最佳实践偏离 / 用户可见回归
- **当前写法**: 计划明确不在聚合消息中包含 Case identifier 或 raw evidence，只渲染新增、重开、关闭、替代、待处理和阻断计数。
- **反例/失败场景**: Daily NAV preflight 首次发现 `pending_confirmation` 或 `pending_manual_edit` 阻断 Case。旧的逐 Case discovery receipt 包含 exact Case key、record id、field 和 state-specific command；新方案抑制该回执后，用户只看到“阻断 1”，无法直接定位或执行确认/修复命令。
- **为什么有问题**: 用户确认的方案要求自动扫描聚合但保留 Case ID 和操作入口。消息数量优化不应删除 actionable contract；Case audit 可查询并不等价于通知中可操作。
- **直接证据**: `HoldingsWorkflowService._discovery_receipt()` 按 state 冻结 exact command；`HoldingsReceiptService.build_message()` 展示 Case/record/field/command。计划却把所有这些信息从唯一剩余的 NAV envelope 排除。
- **影响**: 阻断 NAV 的通知无法自助处理，用户需要另行诊断；优化消息洪峰导致功能性退化。
- **建议改法和验证点**: 从 preflight plan 的 frozen discovery payload 派生 bounded `action_items`（Case、记录、字段、状态、命令），每个 scope 最多展示 5 条并显示 omitted count；关闭/替代仍只计数。测试必须覆盖 exact command、cap/overflow、无行动项不渲染。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中
