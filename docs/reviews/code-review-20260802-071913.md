## Findings

### 1-未修复-高-旧的汇总 PortfolioValuation 会被自动提升为官方真源，绕过 ValuationService 和 CLOSED 唯一工厂

- **入口/函数**: `PortfolioManager.record_nav()` /
  `NavRecordService.record_nav()` →
  `NormalizedValuationSnapshot.from_compatibility_projection()` → NAV 与空
  holdings_snapshot 写入
- **文件(行号)**:
  `src/app/nav_record_service.py:164-203`;
  `src/domain/snapshot_contracts.py:574-681`;
  `tests/test_nav_record_service.py:38-56`
- **输入场景**: 任意直接调用方传入一个没有 holding rows、但带自报
  cash/stock/fund/total/shares/nav 的 `PortfolioValuation`，并提供合法的
  cash-flow dataset 后执行 `persist=True`。
- **实际分支**: 当 compatibility payload 没有 attached normalized object
  时，`record_nav()` 不会 fail closed；它把调用方自报的三个汇总差额
  转成 components，并显式设置 `official_eligible=True`、
  `source=legacy_aggregate_nav`。随后这些汇总数参与正式 NAV 计算，
  snapshot target 则是零行。测试公共 fixture 也通过同一个
  `official_eligible=True` 参数制造“官方”对象。
- **直接证据**: 对 `PortfolioValuation(account="a",
  total_value_cny=100, cash_value_cny=100, shares=100, nav=1)` 调用当前
  adapter，可得到 `official_eligible=True`、`rows=()` 的 normalized
  object；该对象通过 `assert_official_eligible()`。这条路径没有读取
  canonical holdings、没有 ValuationService price evidence，也不是
  `from_closed_input(ClosedNavTarget)`。
- **影响**: S9 宣称的唯一真源并未成立。旧调用方可以持久化一个没有
  可重放持仓集的普通官方 NAV，并产生看似完整的 v2 planned evidence；
  S10 若把该 target 当作精确集合，还可能把当日持仓快照收敛为空集。
- **建议改法和验证点**: 删除正式写入的 aggregate compatibility
  promotion。`persist=True` 只接受 ValuationService projection 上附着的
  exact normalized object，或显式 CLOSED factory 的对象；report/
  `persist=False` compatibility 可保留但永远不可升级为官方。把现有
  NAV 单测 fixture 改为真实 normalized rows/components 的明确 fixture，
  并新增回归：无 attached normalized 的 aggregate-only
  `PortfolioValuation` 在任何正式或 dry-run persistence 尝试中都零写
  fail closed。
- **修复风险**: 中
- **严重程度**: 高

### 2-未修复-高-显式 normalized 参数只比兼容投影而不比附着 digest，可替换未投影的来源和目标证据

- **入口/函数**: `NormalizedValuationSnapshot.to_portfolio_valuation()` →
  `NavRecordService.record_nav(normalized_valuation=...)` →
  `assert_compatible()` → `evidence()` / snapshot persistence
- **文件(行号)**:
  `src/domain/snapshot_contracts.py:752-809,918-980`;
  `src/app/nav_record_service.py:170-203,349-363`
- **输入场景**: compatibility valuation 是 normalized object A 的投影，
  但调用方显式传入 normalized object B；B 的 totals/holdings/price
  projection 与 A 相同，而 `source`、`source_provenance`、row source、
  excluded-zero evidence 或 component provenance 不同。
- **实际分支**: compatibility projection 已保存 A 的
  `_normalized_valuation_digest`，但 `record_nav()` 从不读取或比较它。
  `assert_compatible()` 只 hash `PortfolioValuation` 可见字段；上述 target
  与 authority evidence 不在 compatibility payload 中，因此 B 会通过，
  后续 NAV details 和 snapshot target 使用 B 的 digest/evidence。
- **直接证据**: 从同一个 aggregate compatibility valuation 分别以
  `source=source_a` 和 `source=source_b` 构造两个 normalized objects，
  二者 `digest` 不同，但 B 当前可对 A 的 compatibility projection
  成功执行 `assert_compatible()`。这证明“shared digest validation”实际
  只验证了一个有损投影。
- **影响**: 官方写入可以把 valuation projection 与另一份 normalized
  authority/target evidence 拼接。金额可能暂时相同，但 durable NAV
  details、S10 target digest、补偿和审计归因不再描述生成该 projection
  的 exact immutable object，破坏恢复与写权限绑定。
- **建议改法和验证点**: compatibility projection 已附着 normalized
  object 时，显式参数必须与 attached object 的完整 digest 精确相等；
  最好直接要求同一 immutable transmission。随后再做 compatibility
  projection 校验，以检测投影被改写。新增回归：只改 source
  provenance、excluded-zero digest、row source 或 component provenance
  均在 NAV/snapshot 写前失败；同一个 exact object 继续通过。
- **修复风险**: 低
- **严重程度**: 高

### 3-未修复-中-HoldingSnapshot 接受零数量，直接仓储和补偿写入可绕过 normalized zero-row exclusion

- **入口/函数**: `HoldingSnapshot()` →
  `SnapshotsRepository.batch_upsert_holding_snapshots()`；以及
  `CompensationService._apply_snapshot_target()` → 同一 repository writer
- **文件(行号)**:
  `src/snapshot_models.py:61-68,101-113`;
  `src/feishu/repositories/snapshots_repository.py:16-64`;
  `src/app/compensation_service.py:447-479`
- **输入场景**: 直接 writer、历史 compensation payload 或错误恢复
  target 包含 `quantity=0`、正价格、`market_value_cny=0` 的完整
  holdings_snapshot row。
- **实际分支**: quantity validator 只校验 finite 并量化，不拒绝零；
  replay invariant 认为 `0 × cny_price = 0` 合法。repository 随后直接
  create/update，该路径不经过 `ValuationService` 的 zero-row exclusion。
- **直接证据**: 当前 `HoldingSnapshot(as_of=..., quantity=0, price=1,
  cny_price=1, market_value_cny=0, ...)` 构造成功且 quantity 为 `0.0`；
  compensation 会用同一构造器反序列化并直接调用 batch upsert。
- **影响**: “零数量只进入 excluded count/key digest、永不成为持久化
  row”的 S9 invariant 只在一条 builder 路径成立。恢复或直接仓储调用
  仍可写入零行，使 v2 exact target、row count 和审计快照与 normalized
  provenance 不一致。
- **建议改法和验证点**: 把 nonzero quantity 设为 `HoldingSnapshot`
  写模型本身的 invariant（负数继续支持 short position）；所有
  repository/compensation 路径自然复用。新增单行、batch、compensation
  回归，确认 `0` 和 `-0` 都在任何 transport call 前失败，最小非零
  八位数量仍可重放。
- **修复风险**: 低
- **严重程度**: 中

## Open Questions

- None. The accepted S9 plan already assigns official construction to

## Residual Risk

- S9 still intentionally provides only planned snapshot evidence. Exact-set
  create/update/clear/delete authority, durable prepare, compensation reuse,
  fresh full-slice readback, and completed evidence belong to S10.
- Feishu Number ultimately uses JSON numeric transport, so extreme Decimal
  precision may not survive the external boundary. No live Number canary is
  authorized in this review.
- Same-host code cannot prevent external Feishu editors from changing a row
  after later S10 readback; this review covers deterministic source contracts,
  not remote atomicity.
