## Findings

### S2-CR-01 — 未修复 — 中 — holdings event status conflates App ID and target-table validity

- **入口/函数**: `cmd_holdings_events_status()`
- **文件(行号)**: `scripts/pm.py:446-470`
- **输入场景**: The Bitable App ID resolves successfully, but the holdings Base
  token or table ID is missing or invalid.
- **实际分支**: `HoldingsEventTarget.from_config()` fails for the table reference,
  `target` stays `None`, and `credentials.app_id_configured` is derived from
  `bool(target)`.
- **预期行为**: Credential status should resolve and report the canonical
  `feishu.bitable.app_id` independently from target-registry validity, matching
  the combined `events status` command.
- **实际行为**: The command reports `app_id_configured=false` even though the App
  ID is present and puts the target error inside the credential issue list.
- **影响**: A read-only migration/preflight diagnosis points the operator at the
  wrong configuration boundary and can obscure a table-reference problem as an
  identity problem.
- **建议改法和验证点**: Resolve both canonical Bitable identity fields through a
  small redacted status helper, keep target errors in a separate target-status
  field, and add a regression where App ID/secret are present but table routing
  fails.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
