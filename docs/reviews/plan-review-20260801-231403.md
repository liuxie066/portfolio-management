## Findings

### PRR-01-未修复-高-close_nav 是未纳入计划的直接 NAV 写入口，会同时绕过 S6/S9/S10
- **位置**: Public Contract、S6、S8、S9、S10 的入口 inventory / allowed files / tests
- **问题类型**: 架构边界 / 权限边界 / 契约缺失 / 不可直接实施 / 测试缺口
- **当前写法**: 修订计划声明 `AccountNavRecorderService` 与 `NavInitializationService` 是两个官方顶层 builder，所有 NAV 写入都必须携带 cash-flow dataset；新/rewrite NAV 使用 normalized valuation 和 scoped snapshot authority。
- **反例/失败场景**: `SkillAPI.close_nav` 是第三条明确确认的 NAV 写路径。它自行根据用户 float 输入构造 `NAVHistory`，直接执行 repository dry-run/real `write_nav_record`，不读取 cash-flow dataset、不构造 normalized valuation、不准备 exact empty snapshot target，也不把 overwrite 确认绑定到 durable authority。
- **为什么有问题**: 该路径不是测试辅助代码，而是公开的显式 CLOSED 业务操作。它产生的行会进入后续 NAV history/read/report 语义，因此不能作为未建模例外保留。当前修订使三个核心成功信号都只对普通 record/init 成立。
- **直接证据**: `skill_api.py:498-518` 定义公开 CLOSED 写语义；`skill_api.py:531-573` 独立计算/构造 NAV；`skill_api.py:575-589` 直接 dry-run 后真实写 repository。全仓 `write_nav_record` inventory 证明这是除 maintenance/repository/internal tests 外唯一公开的直接业务写入口。
- **影响**: CLOSED 行的 cash-flow basis、分解/精度、snapshot finality 和 overwrite authority 可与 canonical NAV 不一致；“所有方法一致”及 layered SSOT 目标无法验收。
- **建议改法和验证点**: 将 `close_nav` 纳入 plan，不允许直接 repository write。优先让它委托 `AccountNavRecorderService.record_closed(...)`：构造相同 S6 dataset；用唯一 `ClosedValuationInput` factory 生成零持仓 rows + 显式 manual cash/noncash components 的 normalized snapshot/compatibility projection；复用 S8 final invariants 与 S10 exact-set/authority engine（目标日 holdings_snapshot exact set 为空）。真实写仍需 confirm，已有同日 NAV 或 snapshot slice 需 overwrite authority。测试覆盖 direct repository zero-call、非有限/分解不一致拒绝、daily/gap basis、empty exact set、覆盖确认和后续 read/report 语义。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高
