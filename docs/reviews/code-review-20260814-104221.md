### DR-S1-01-未修复-高-compensation_pending 外部变化可被普通 observation 分支越权终结
- **入口/函数**: `CashFlowEffectService.scan()` ->
  `_scan_holding_fingerprints()`
- **文件(行号)**: `src/app/cash_flow_effect_service.py:635-680`；合法补偿终结入口见
  `src/app/cash_flow_effect_service.py:1970-2017`
- **输入场景**: 某 `cash_holding_external_change` 写入失败后处于
  `compensation_pending`，其 target identity 同时在 compensation target 集合中；
  当前 holding 观测值恰好等于该 identity 的 `last_confirmed_hash`。
- **实际分支**: scanner 先命中 `last_confirmed_hash == observed_hash`，随后把任何
  `UNRESOLVED_STATES`（其中包含 `compensation_pending`）更新为 `applied` 并
  `continue`；位于后面的 `compensation_identities` guard 永远不会执行。
- **预期行为**: `compensation_pending` 只能由 compensation task 成功、fresh
  readback 与 target 一致后，通过 `_finalize_compensation_if_resolved()` 从
  `compensation_pending` CAS 到 `applied`。
- **实际行为**: 普通 scanner 可绕过 task 状态和 target readback，把补偿 effect
  标成 `applied`；后续 `retry()` 会因 state 已不是 `compensation_pending` 而拒绝。
- **直接证据**: `UNRESOLVED_STATES` 包含 `compensation_pending`；scanner 在
  `src/app/cash_flow_effect_service.py:661-675` 使用整个集合更新，而 identity
  guard 直到 `:680` 才判断。正式补偿终结在 `:1976-2016` 明确要求 task
  `RESOLVED`、逐 target fresh readback 和 expected state
  `compensation_pending`。
- **影响**: recovery authority 被绕过，durable effect 状态可能与 compensation
  task 和真实目标不一致；正式 NAV 可能在未完成合法恢复时失去 blocker。
- **建议改法和验证点**: 将 compensation identity guard 提到任何 resolution
  分支之前，并在 observation resolution 的 expected states 中显式排除
  `compensation_pending`。新增回归测试：构造同 identity、同 confirmed
  observation 的 compensation-pending external effect，扫描后 state、task 和
  blocker 均保持不变。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### DR-S1-02-未修复-中-再次回到旧 drift 值会静默复用已 restore 的 applied effect
- **入口/函数**: `CashFlowEffectService.scan()` ->
  `_scan_holding_fingerprints()` non-Futu branch
- **文件(行号)**: `src/app/cash_flow_effect_service.py:690-769`
- **输入场景**: 一个非 Futu direct-drift effect 曾通过 `restore` 写回旧 baseline
  并终结为 `applied`；之后人工又把同一 holding 改回该 effect 记录过的相同
  observed amount/hash。
- **实际分支**: source 构造会复用旧 effect 的 `flow_date`，因此 source hash
  与旧版本相同；代码令 `accepted = existing_external`，但只在其 state 属于
  `UNRESOLVED_STATES` 时写 audit transition。对 terminal `applied` 不更新 effect
  或事件，却仍用该旧 effect id 确认新 fingerprint。
- **预期行为**: 新一次人工维护应留下 terminal `record_only` 的自动-policy
  audit 事实，effect state/confirmation/event 与新 baseline 的语义一致。
- **实际行为**: fingerprint 被静默改写为人工值，而 effect 仍表示此前的 restore
  已 `applied`；没有本次自动接受事件，审计链和 `confirmed_by_effect_id` 语义错误。
- **直接证据**: `:694-699` 在 observed hash 相同时复用 flow date；`:724-744`
  对同 source 仅处理 unresolved state；`:763-769` 无条件确认 fingerprint。
- **影响**: NAV 虽不被阻断，但人工 authority 的关键审计证据丢失，后续排查无法
  区分“恢复成功”与“后来再次人工改回同值”。
- **建议改法和验证点**: 同 source 的 terminal `applied` 也应以 CAS 更新为
  `record_only`、写 automatic-policy confirmation/event 后再确认 fingerprint；
  增加 restore -> 人工改回旧 drift -> scan 的回归测试，并验证第二次 scan 幂等。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### DR-S1-03-未修复-低-mixed already_reflected 预览把审计来源误标为 estimated
- **入口/函数**: `CashFlowEffectService._build_preview()`
- **文件(行号)**: `src/app/cash_flow_effect_service.py:1426-1435,1476-1481`
- **输入场景**: 一个 correction 同时包含 Futu operation 与非 Futu operation，
  operator 选择 `already_reflected`。
- **实际分支**: Futu row 标为 `futu_opend_currency_cash`，非 Futu row 标为
  `manual_current_includes_event`；aggregate `target_source` 只要来源不唯一就固定
  返回 `mixed_futu_exact_and_estimated`。
- **预期行为**: aggregate audit 字段不应把 explicit no-op declaration 描述为
  estimated target；逐 row facts 已足够，aggregate 可使用中性 `mixed`。
- **实际行为**: receipt/audit payload 对外声称 mixed target 含 estimated，和实际
  target rows 冲突。
- **直接证据**: non-Futu branch 在 `:1430-1435` 明确保持 fresh current；
  `:1477-1481` 对任何混合来源硬编码 `mixed_futu_exact_and_estimated`。
- **影响**: 不改变 holding 数值，但会产生误导性的 operator/audit 描述，尤其与本
  work unit 要求的显式 declaration 相冲突。
- **建议改法和验证点**: 多来源时改用中性 `mixed`（或由实际 source names
  稳定派生），增加 Futu + non-Futu `already_reflected` 预览断言。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
