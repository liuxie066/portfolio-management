## Review evidence

### Writer completeness

- All `holdings` table create, update, batch-create, and batch-update calls are
  owned by `HoldingsRepository`.
- Patch, additive upsert, replacement, bulk upsert, quantity update, object
  serialization, in-memory cache publication, and persistent cache snapshots
  all call `format_holding_date()` before the generic Feishu serializer.
- The generic serializer passes strings through unchanged, so the Feishu
  payload remains exactly `YYYY/MM/DD` rather than being converted to epoch
  milliseconds.
- The global `DATETIME_FORMAT` and all non-holdings repositories remain
  unchanged.

### Reader and validator agreement

- Repository materialization and standalone validation call the same strict
  `parse_holding_date()` helper.
- The parser accepts exact `YYYY/MM/DD` and the immediately preceding exact
  `YYYY-MM-DD HH:MM:SS` representation only. Round-trip comparison rejects
  non-zero-padded, date-only hyphen, ISO `T`, epoch, and arbitrary inputs.
- `RecordValidation.to_holding()` parses already-valid text into `datetime`
  values rather than relying on Pydantic's independent string parsing.
- Missing and malformed optional validation metadata preserve the existing
  nonblocking classification; repository preload remains aggregate and
  fail-closed before cache publication.

### Regression adequacy

- Exact payload assertions cover patch, single update/create, replacement,
  MMF sync, quantity update, bulk update/create, and cache representations.
- A 17-row production-shaped preload covers the incident slash representation
  plus one predecessor full timestamp and proves successful typed/cache
  materialization.
- A malformed-date regression proves the repository publishes neither holding
  ID nor field cache state on failure.
- Validator regressions cover both accepted forms, typed construction, and
  exact rejection cases.
