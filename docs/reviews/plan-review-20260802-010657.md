# Plan Review — Feishu Dual-App Credentials

- Reviewed target: `docs/gateflow/feishu-dual-app-credentials/implementation-plan.md`
- Mode: adversarial implementation-plan review
- Base: `origin/main@59625b0d6c666da338c0a520e85a221932846949`
- Scope: two Feishu application roles, credential resolution, systemd credential
  delivery, installer migration, tests, and documentation
- Excluded scope: live secrets, Feishu mutation, release, deployment, hosted
  multi-tenant secret storage, and business workflow changes

## Assumptions tested

- Exactly two Feishu application identities are sufficient.
- The Bitable identity can safely own both table API and event ingress.
- A systemd credential can coexist with legacy plaintext during controlled
  migration without selecting the wrong value.
- The proposed per-unit grant matrix covers every real call path without granting
  unnecessary credentials.
- Operator preflight remains executable when direct shells have no
  `CREDENTIALS_DIRECTORY`.
- Every listed validation command exists and can be run verbatim.
- The plan is specific enough that implementation does not need to invent limits
  or error behavior.

## Findings

### PR-01-未修复-高-安全模式与迁移状态机互相矛盾，轮换后的新密钥会被旧明文阻断
- **位置**: `Source order and secure mode`; `Compatibility aliases`;
  `Migration and rollback state machine`
- **问题类型**: 状态机漏洞 / 契约缺失
- **当前写法**: plan 要求 canonical/legacy 输入同时存在且不同时失败，并要求
  secure mode 发现任何明文来源都拒绝；迁移顺序却要求先加载新的 encrypted
  credentials、切换并通过 canary，最后才删除旧明文。
- **反例/失败场景**: 新监听应用的 rotated Secret 已作为 systemd credential
  注入，但旧 `feishu.app_secret` 仍在 YAML，或旧 conversation Secret 仍在
  `EnvironmentFile`。新旧值理应不同。secure service 启动时要么因冲突失败，
  要么因明文仍存在失败，因此永远无法进入 `secure_preflight_passed` 和 canary；
  若先删除旧值，又失去 plan 声称的切换前回滚能力。
- **为什么有问题**: 这是同一 plan 内的直接 sequencing 矛盾，不是部署环境不确定性。
  安全 resolver 必须区分“被选中的不安全 fallback”和“未读取、未选中的 legacy
  shadow”。Secret 也不应为了冲突比较而读取所有 shadow values。
- **直接证据**: 当前 resolver 是环境/YAML优先；plan 同时写明“different values
  produce a ... conflict”、“plaintext source present ... is rejected”以及
  `services_switched_secure -> ... -> plaintext_removed`。
- **影响**: 新 release 在真实迁移中无法启动，或操作员被迫在 canary 前删除唯一
  可回滚的旧凭据。
- **建议改法和验证点**: 对 secret keys 采用选择语义而不是全值冲突比较：credential
  存在时只读取 credential，legacy secret 仅按 key presence 记为
  `plaintext_shadow_detected`，不读取/比较其值，也不阻断 preflight/canary；secure
  mode 只在需要回退到明文时返回 `insecure_secret_source`。对非 secret 的 App ID/
  open_id 继续做值冲突检测。新增迁移测试：新 credential + 不同 legacy secret
  时选择 credential、输出 shadow warning 且不泄露两者；credential 缺失 + legacy
  secret 时 secure mode 失败；plaintext cleanup 仍是 canary 后独立动作。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-unit 凭据矩阵漏授 conversation，计划实现后现有命令会失败
- **位置**: `systemd and installer contract` credential grant table
- **问题类型**: 架构边界 / 测试缺口
- **当前写法**: cash-flow scan 和 API service 只加载 Bitable credential；plan
  断言 scan 只 enqueue receipts、API receipt delivery 由 dispatcher 独占。
- **反例/失败场景**: `cmd_cash_flow_effects_scan()` 在 `scan(...,
  enqueue_receipts=True)` 后立即构造 `CashFlowEffectReceiptService` 并调用
  `dispatch_pending()`；API 也可调用会在请求内发送 Futu/NAV receipts 的
  `PortfolioService` use cases。secure mode 下这两个 unit 没有 conversation
  credential，已有调用从成功/排队语义退化为 missing secure credential。
- **为什么有问题**: least privilege 必须从真实 call graph 推导，不能从组件名称
  猜测。当前 plan 把“durable dispatcher owns retries”误写成“只有 dispatcher
  能发送”。
- **直接证据**: `scripts/pm.py:912-928` 的 cash-flow scan 直接
  `dispatch_pending()`；`src/service/application.py` 的 Futu/NAV use cases 持有
  receipt services，API facade 可进入这些路径。
- **影响**: 定时 cash-flow scan 的回执和部分 API 写流程在部署后失败；如果用共享
  fallback 修补，又破坏双角色隔离和 secure-mode 目标。
- **建议改法和验证点**: 基于命令/endpoint call graph 修正矩阵：cash-flow scan
  至少加载 Bitable + conversation；API 若保留可触发 receipt 的 endpoints，也加载
  两者，或另开 work unit 收窄 API（本 work unit 不应顺带改业务语义）。测试每个
  unit 的最小必要集合，并用 secure-mode command tests 证明实际入口可解析所需角色。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-03-未修复-中-S2 验证命令引用不存在的测试文件，无法按计划验收
- **位置**: `S2 — Move all Feishu call paths to the two canonical roles`
- **问题类型**: 不可直接实施 / 测试缺口
- **当前写法**: S2 validation 列出
  `tests/test_holdings_receipt_service.py` 和
  `tests/test_cash_flow_receipt_service.py`。
- **反例/失败场景**: implementation agent 原样执行计划，pytest 在收集阶段以
  `file or directory not found` 退出，无法证明角色迁移，也可能错误删掉验证项只求
  通过。
- **为什么有问题**: code-generation-ready plan 的命令必须能运行；receipt tests
  目前分布在 workflow/outbox 等实际文件中，不能用假定文件名代替。
- **直接证据**: 当前仓库存在 `tests/test_futu_sync_receipt_service.py` 和
  `tests/test_nav_history_receipt_service.py`，但上述两个文件不存在。
- **影响**: S2 gate 不可验收，review evidence 不完整。
- **建议改法和验证点**: 用 `rg --files tests | rg 'receipt|workflow|outbox'` 确认
  真实测试 ownership，将命令替换为现存文件；若缺少服务级覆盖，再明确新增测试文件
  及断言，而不是引用不存在的预期文件。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### PR-04-未修复-中-credential 文件上限和 systemd 能力门槛未定义，仍需实施者现场设计
- **位置**: `Runtime credential names`; `systemd and installer contract`;
  `S1`; `S3`
- **问题类型**: 契约缺失 / 最佳实践偏离 / 不可直接实施
- **当前写法**: resolver 要拒绝 oversized value，但没有字节上限；installer 直接
  渲染 `LoadCredentialEncrypted`，没有定义最低 systemd 能力或缺失
  `systemd-creds` 时的 fail-closed preflight。
- **反例/失败场景**: 实施者任意选择上限导致测试/部署不一致；较旧 Linux 生成 unit
  后才在 daemon reload/start 时失败，installer 已经写入其它资产，形成 partial
  apply。
- **为什么有问题**: 这是公开运行契约和 installer sequencing，不能留给实现阶段
  猜测。当前生产的 systemd 255 只证明单一主机可行，不证明广泛安装环境。
- **直接证据**: plan 只有“oversized”和“operator-provisioned encrypted
  credential files”，没有数值、feature detection、版本/命令门槛或写入前检查。
- **影响**: 跨环境安装不可预测，失败可能发生在已写 unit 之后；测试也无法形成
  精确边界。
- **建议改法和验证点**: 定义 App Secret 最大 4096 bytes；S3 在任何写入前检查
  `systemd-creds` 可用且目标 systemd 支持 `LoadCredentialEncrypted`，否则返回
  redacted blocker。渲染测试覆盖 4096/4097 边界和 unsupported preflight；真实
  unit 语法验证列为部署 gate，不能由本地 macOS 测试冒充。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Special lens conclusions

- **Architecture boundary**: exactly two identities is correct, but the unit
  capability matrix must follow actual call paths.
- **Best practice**: credential-first, redacted source metadata, explicit
  migration, and per-unit grants are sound after findings are fixed.
- **Optimal solution**: using systemd credentials for the current self-hosted
  Linux edition is more practical than adding a network secret service now.
- **Overengineering**: the hosted/multi-tenant provider is correctly deferred;
  the preflight oneshot is justified only if direct operator commands cannot
  receive credentials safely.
- **Overcoupling**: role resolution remains centralized in configuration and does
  not leak into holdings/cash-flow business rules; no material issue beyond the
  incorrect unit matrix.
