- Work unit: `holdings-validation-completion-conflict-receipts`

- Scope: holdings field authority, native-currency evidence, raw Feishu reads,

## Reviewed plan summary

The reviewed plan proposes:

- `pm holdings reconcile` as a read-only default scan, with `--record-id` for
  one row and `--apply --confirm` for explicit completion;
- validation from raw Feishu fields so missing values are not hidden by
  `Holding` defaults;
- no `CNY` fallback for missing holdings currency;
- native currency resolved from the underlying security, using Futu OpenD for
  Futu rows and quote/security metadata for other rows;
- filling missing fields only, while treating a populated value that differs
  from evidence as a conflict rather than an automatic correction;
- a durable `pending_confirmation` conflict, a Feishu receipt, and CLI
  resolution by accepting evidence or keeping the current value with a reason;
- confirmation bound to record and evidence fingerprints, fresh reread before
  apply, supersession on drift, readback verification, and a closure receipt;
- account-scoped NAV blocking for unresolved conflicts without cross-account
  inference; and
- outbound Feishu receipt plus CLI confirmation in the first slice, with
  interactive card callbacks deferred.

## Assumptions tested

### Architecture boundary review

- Tested whether pricing payloads are authoritative security metadata or merely
  valuation outputs.
- Tested whether raw Feishu validation can coexist with the current typed
  holdings repository and its persistent cache.
- Tested whether conflict state and receipt delivery belong in the existing
  `OperationStateStore`, and whether the current dispatcher can route a new
  receipt type without leaking holdings semantics into the NAV sender.
- Tested whether Futu remains the authority for its own position facts and
  whether a generic holdings reconciler would duplicate Futu sync logic.

### Best-practice review

- Tested compare-and-set, idempotency, readback, partial failure, durable
  notification, retry, unknown delivery outcome, operator audit, and
  account-scoped failure behavior.
- Tested whether a manual override remains auditable and whether it can be
  invalidated when facts or policy change.
- Tested whether the proposed default-dry-run surface prevents ordinary reads
  or scheduled NAV from silently mutating holdings.

### Optimal-solution review

- The combination of raw validation, explicit completion, conflict receipts,
  and CLI confirmation is more credible than a background auto-fixer.
- Reusing the existing operation-state and receipt patterns is preferable to a
  second standalone database or an interactive callback service in the first
  slice.
- A single `reconcile` command is consistent with current cash-flow operations,
  provided it does not absorb Futu source synchronization or correction
  authority.

### Overengineering review

- Interactive Feishu buttons, a general security-master platform, a generic
  workflow engine, and automatic correction are not required by the current
  goal.
- A durable conflict state is justified because confirmation and receipt retry
  cross process lifetimes; an in-memory plan would be unsafe.
- A new general-purpose notification abstraction is not justified unless the
  plan proves it is the smallest way to route holdings conflict receipts
  through the existing dispatcher.

### Overcoupling review

- Tested whether the plan couples holdings validation to pricing normalization,
  Futu sync, NAV orchestration, local cache schema, SQLite state, Feishu
  transport, and CLI confirmation without explicit one-way contracts.
- Tested whether validation can be independently unit-tested from external
  providers and receipt delivery.
- Tested whether NAV consumes exactly the holdings snapshot that passed
  validation instead of rereading mutable state.

### Validation review

- Sought tests for missing raw fields, provider-derived false currency,
  persistent-cache upgrade, duplicate normalized identity, conflicting
  evidence, same-conflict deduplication, changed-record supersession,
  concurrent confirmations, Feishu-write/local-state partial failure, unknown
  receipt delivery, account isolation, Futu ordering, and validated-snapshot
  consumption.
- The reviewed plan states several expected behaviors but does not yet define
  code-generation-ready slices or exact assertions for these paths.

## Findings

### PR-HOLD-01-未修复-高-非富途币种“证据”没有可信来源契约，可能把市场启发式当作标的事实
- **位置**: native currency resolution、evidence priority、missing-field completion、conflict detection
- **问题类型**: 架构边界 / 契约缺失 / 最佳实践偏离 / 不可直接实施
- **当前写法**: 富途使用 OpenD `position.currency`；其他标的使用“行情或证券元数据明确返回的币种”，仅代码或市场启发式不自动写入。
- **反例/失败场景**: 实现 Agent 直接复用现有 `PriceFetcher` payload 作为证券元数据。当前香港、美国和中国 provider 分别在适配器内硬编码 `HKD`、`USD` 和 `CNY`，而公共 pricing normalizer 对缺失 currency 仍回退为 `CNY`。这类值可能是市场路由推导或默认值，并非 provider 返回的标的级原生币种；缓存 payload 还会延续该派生结果。reconcile 随后可能把错误币种补进 holdings，或对正确人工值制造冲突。
- **为什么有问题**: 用户已经明确要求 currency 必须按标的判断，不能默认 CNY。方案虽然表述了该意图，却没有定义哪些 source/field/provenance 可以证明“按标的”，也没有禁止 normalizer、market_type、FX route 或 cache-derived currency 进入权威层。
- **直接证据**: `src/pricing/payload.py:65-76` 对缺失 currency 使用 `CNY`；`src/pricing/providers/hk.py:70-88`、`src/pricing/providers/us.py:109-125`、`src/pricing/providers/cn.py:75-92` 在 provider adapter 中按市场写死币种。现有 Futu snapshot 才携带逐标的 `position.currency` 和 source snapshot identity。
- **影响**: 错误 native currency 会进入估值和 FX 链路，可能产生无明显 missing warning 的错误 NAV；冲突回执也会把非权威建议伪装为证据。
- **建议改法和验证点**: Plan 必须给出字段级 authority matrix。至少区分 `authoritative_explicit`、`manual_confirmed`、`heuristic_suggestion`、`defaulted_forbidden`；只有 raw provider/OpenD 明确返回且带 source/as-of 的 instrument currency 或受审计的人工确认可写入/裁决。现有 pricing normalized payload 默认不能直接作为 authority。测试必须构造：provider raw currency 缺失但 normalized payload 变 CNY、HK/US adapter hardcode、cache payload、OpenD explicit currency，以及无权威来源时 `currency_unresolved` 且不写。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-HOLD-02-未修复-高-NAV 校验门的时序没有与 Futu 同步和估值快照对齐
- **位置**: daily NAV read-only blocker、Futu authority、validated snapshot consumption、implementation sequencing
- **问题类型**: 状态机漏洞 / 架构边界 / 过度耦合 / 不可直接实施
- **当前写法**: 每日 NAV 前对目标账户执行 holdings 校验；发现待补或冲突就阻断。富途事实仍由 OpenD/Futu sync 管理。
- **反例/失败场景**: 实现 Agent 仿照 `_cash_flow_blocker()`，在 `DailyNavJobService._run_account()` 中、进入 account runner 前增加 `_holdings_blocker()`。当前可选 Futu CASH/MMF 同步发生在更深层的 `AccountNavRecorderService.record()`，且估值 snapshot 又在同步之后单独读取 holdings。这样校验会看到同步前状态，可能为本应由同一次 Futu 同步消除的差异创建冲突并阻断；反过来，即使 preflight 通过，后续同步或人工编辑也可能改变 holdings，估值读取的并不是已验证的快照。
- **为什么有问题**: “校验通过”只有在估值消费同一份不可变 holdings bytes/objects 时才有意义。当前方案没有决定 validation、可选 Futu sync、fresh raw read、conflict materialization、typed conversion 和 valuation 的顺序，也没有规定同一 account lock 的覆盖范围。
- **直接证据**: `src/app/daily_nav_job_service.py:217-265` 在 account runner 前只做 duplicate/cash-flow/existing-NAV checks；`src/app/account_nav_recorder_service.py:97-129` 在 runner 内先执行可选 Futu CASH/MMF sync，随后 `build_snapshot()` 重新读取数据。Futu portfolio sync 本身使用 account process lock，但当前 NAV preflight 没有共享一份 validated holdings snapshot。
- **影响**: 误报冲突、漏报晚到修改、同一次任务校验与估值事实不一致，最终可能错误阻断或错误写入 NAV。
- **建议改法和验证点**: Plan 必须选定单一顺序并定义 snapshot handoff。推荐在 account runner 内完成受控 Futu 同步后，fresh-read raw holdings，一次性校验/物化 conflict，再将同一 validated typed holdings snapshot 显式传给 `build_snapshot()`；或者明确忽略由同-run Futu sync 管理的字段并证明安全。锁、deadline、dry-run 行为和跨账户 quote sharing 也要写清。测试应模拟同步前冲突、同步后消失、校验后外部修改、两个账户并行，以及断言 valuation 收到与 validation digest 相同的数据。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### PR-HOLD-03-未修复-高-确认写入跨 Feishu 与本地状态的部分失败没有恢复状态
- **位置**: `pending_confirmation -> resolution` 状态机、accept-evidence、keep-current、readback、closure receipt
- **问题类型**: 状态机漏洞 / 并发恢复风险 / 契约缺失 / 测试缺口
- **当前写法**: confirmation 先 fresh reread 并核对 record/evidence fingerprints；接受证据后更新 Feishu、readback、失效 cache、标记 resolved 并发送关闭回执；漂移则 supersede。
- **反例/失败场景**: Feishu `update_record()` 已成功，但进程在本地 conflict 状态提交前崩溃，或 SQLite 提交失败。冲突仍是 `pending_confirmation`，操作者重试；另一种情况是 Feishu 响应超时，写入结果未知。当前方案没有 `applying`、`apply_outcome_unknown`、`already_applied`、recovery scan 或补偿状态，无法区分安全重试与需要人工检查。
- **为什么有问题**: Feishu 和本地 SQLite 不可能原子提交。仅说“readback verification”不能覆盖进程崩溃、响应丢失或本地终态写失败。确认流程必须以绝对目标、幂等判定和可恢复状态处理跨系统边界。
- **直接证据**: `src/feishu/repositories/holdings_repository.py:443-478` 的 replacement 是远端写后更新 cache，没有与本地 operation state 事务绑定；现有 NAV receipt dispatcher 已专门定义 delivery-attempt 后本地状态失败为 unknown，说明项目承认该类跨边界结果未知问题。
- **影响**: 重复操作、永远 pending 的已修复冲突、错误关闭冲突、无法可靠审计人工确认，或在结果未知时盲目重试。
- **建议改法和验证点**: Plan 必须定义完整 transitions：`pending_confirmation -> applying -> resolved_accept / resolved_keep / superseded / apply_outcome_unknown / failed`。写入使用 exact `record_id` 和 field-level compare-and-set digest；恢复时 fresh-read，若目标值已存在则幂等收敛为 `already_applied`，若仍是 before 值可安全重试，其他值 supersede；unknown 状态不得自动重复写。测试在远端成功后本地提交失败、远端超时但实际成功、readback 失败、并发双确认、进程重启后恢复。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### PR-HOLD-04-未修复-高-冲突回执的 durable outbox、事务边界和 dispatcher 路由未被规格化
- **位置**: conflict persistence、receipt enqueue、deduplication、delivery retry、closure receipt
- **问题类型**: 架构边界 / 并发恢复风险 / 过度耦合 / 不可直接实施
- **当前写法**: 冲突先持久化，再写 durable outbox；同一冲突只发一次；发送失败由现有 dispatcher 重试；完成后再发关闭回执。
- **反例/失败场景**: 实现 Agent 复用 `FutuSyncReceiptService.send()`，得到 best-effort 丢失；或把 holdings payload 塞入 `nav_receipt_outbox`，现有 dispatcher 却固定使用 `NavHistoryReceiptService` 渲染。若 conflict insert 与 receipt enqueue 不在同一 SQLite transaction，进程可在两者之间崩溃，留下永不通知的 pending conflict。若 send 成功、mark sent 失败，现有 lease 重试还可能重复通知。
- **为什么有问题**: “durable outbox”不是一个足够具体的实现契约。当前项目同时存在 best-effort Futu receipt、NAV-specific durable outbox 和另一数据库中的 cash-flow receipt outbox；选错一个会直接破坏回执可靠性或模块 ownership。
- **直接证据**: `src/app/futu_sync_receipt_service.py:11-77` 是 best-effort 直接发送；`src/app/operation_state_store.py:255-425` 的表和方法都是 NAV-specific；`src/app/nav_receipt_outbox_service.py:11-109` 固定绑定 `NavHistoryReceiptService`，并对 claim/lease/unknown local state 有专门语义。当前 `receipts dispatch` timer 只覆盖该链路。
- **影响**: 冲突未通知、重复通知、错误模板、dispatcher 无法处理、receipt 与 conflict 状态不一致，导致“要求人工确认”在事故时失效。
- **建议改法和验证点**: Plan 必须选择并写死最小边界：在 `OperationStateStore` 中增加 typed operation receipt outbox，或安全泛化现有 outbox；定义 `receipt_type` renderer registry、deterministic receipt key、claim lease、retry/unknown 语义。conflict/event 与 discovery receipt 必须同一 SQLite transaction 插入。closure receipt 使用不同确定性 key。更新既有 dispatcher/timer 路由而不影响 NAV payload。测试 atomic rollback、restart、two dispatchers、payload/key collision、send-success/mark-fail、discovery/closure dedupe 和 NAV regression。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-HOLD-05-未修复-中-冲突指纹同时承担去重和授权失效会产生重复回执或永久错误覆盖
- **位置**: conflict identity、evidence fingerprint、same-conflict deduplication、keep-current invalidation
- **问题类型**: 状态机漏洞 / 契约缺失 / 可观测性 / 测试缺口
- **当前写法**: 同一冲突指纹只发一次；confirmation/keep-current 绑定记录快照和证据指纹；记录或证据变化后自动失效。
- **反例/失败场景**: 如果 evidence fingerprint 包含 `observed_at`、fetch time 或完整 provider payload，同一 `CNY vs USD` 冲突每次刷新都会得到新指纹并反复发回执。如果排除这些动态字段但也不包含 authority/policy version，provider mapping 或 validator policy 更新后，旧 `keep-current` 可能永久压制本应重新确认的冲突。
- **为什么有问题**: 去重 identity、证据实例 identity 和人工授权 scope 是三个不同概念；用一个未定义的 hash 同时承担三者会在“不过度打扰”和“事实变化必须重审”之间失控。
- **直接证据**: 当前方案只描述了“record/evidence fingerprint”和“一次回执”，没有 canonical fields、policy version、freshness window 或 supersession key。项目现有 receipt keys 依赖稳定 run/digest，并在同 key 不同 payload 时明确拒绝碰撞。
- **影响**: 回执风暴、人工确认反复失效、旧覆盖永久存活，或同一 key 对应不同事实导致不可审计。
- **建议改法和验证点**: Plan 分开定义：`conflict_key = record_id + field + normalized current + normalized proposed + authority_id + policy_version`；`evidence_instance_id` 保存 source snapshot/as-of/raw hash；`confirmation_scope` 绑定 conflict key、record digest、authority/policy version，并规定 evidence freshness。刷新相同事实只更新 latest evidence、不重复 discovery receipt；current/proposed/authority/policy 变化才 supersede。测试时间戳变化、source payload 非语义字段变化、政策升级、值变化和 receipt-key collision。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### PR-HOLD-06-未修复-高-移除 `currency=CNY` 默认仍不能清除持久缓存中的伪造值，且坏行的账户隔离行为未定义
- **位置**: raw validation、typed conversion、persistent holdings cache、deployment compatibility、account-scoped blocking
- **问题类型**: migration hazard / 状态不一致 / 架构边界 / 测试缺口
- **当前写法**: validation 直接读取 raw Feishu fields；普通 holdings conversion 移除缺失 currency 的 CNY fallback，使坏行 fail closed；冲突只阻断相关账户。
- **反例/失败场景**: 升级前的本地 holdings index 已把 Feishu 空 currency 物化并持久化成 CNY。升级仅删除 `_dict_to_holding()` fallback 后，启动仍从磁盘恢复带 CNY 的旧 entry，普通读和估值继续看见伪造值；或者严格 conversion 在全量 preload 时遇到一个无 account/broker 的坏行后整体抛错，使 `lx` 的孤立坏行阻断 `sy`。
- **为什么有问题**: raw reconciler 可以发现问题，但方案同时承诺普通读 fail closed 和账户隔离，却没有 cache schema/version invalidation、freshness precedence、orphan row ownership 或 per-row parse error contract。实现 Agent 无法从当前描述推导正确兼容行为。
- **直接证据**: `src/feishu/repositories/holdings_repository.py:47-72` 启动时恢复 persistent index，并再次 `setdefault('currency', 'CNY')`；`:96-131` 让缓存优先于远端；`:146-176` preload 会逐条 typed-convert。现有 cache payload 没有 schema/policy version。`DailyNavJobService` 明确逐账户执行，用户要求不能从一个账户推断另一个账户结果。
- **影响**: 发布后旧错误继续静默生效，或一条不可归属的坏行造成跨账户服务失败；验证结果与估值读取不一致。
- **建议改法和验证点**: Plan 必须定义 holdings index schema version bump/invalidation 或禁止旧 cache 为 validation/valuation authority；部署后首次读取从 raw Feishu 重建。逐行 parse errors 先保留 record_id/raw account，再按明确规则归属：可归属行只阻断该账户，orphan 行进入全局待处理但不得伪装成任何账户。测试旧 cache 迁移、missing currency、orphan row、一个账户坏行另一个账户正常，以及 validation digest 与 valuation holdings digest 一致。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

## Open Questions

  authority？如果没有，第一版是否接受 `manual_confirmed` 为唯一写入依据？
- `keep-current` 是否仅凭本机 CLI 的 `--confirm + reason` 就能解除官方 NAV

  明确标记 `trusted_identity=false`。
- 对缺少 account 的 orphan holdings row，期望只发全局数据质量回执，还是阻断

- first slice 是否仅支持单 `record_id` apply？若允许 account/all batch apply，
  还需要 frozen plan、逐行 CAS、部分成功和恢复契约。

## Residual Risks and suggested tracking

- Feishu record metadata (`created_time`) is not currently preserved by
  `FeishuClient.list_records()`; deriving historical `created_at` needs a
  separately specified metadata contract or must remain unresolved. Track in
  this work unit only if timestamp completion is a success signal.
- Provider coverage may not supply authoritative currency for every non-Futu
  security. Treat unresolved rows as manual-required; do not add a general
  security-master service without a separate evidence-backed work unit.
- Interactive Feishu confirmation buttons remain a later authenticated-callback
  work unit. They are not needed for the CLI-confirmed first slice.
- Production row inspection, correction, Release, and deployment are outside
  this review and require separate authorization.
- A live Feishu visual canary remains operator-owned after a future release; it
  cannot substitute for deterministic renderer/outbox tests.

## Conclusion

`fail`

The direction is sound and appropriately avoids automatic correction, but the
plan is not code-generation-ready. It must first define an authoritative
native-currency source contract, align validation with Futu sync and the exact
valuation snapshot, specify cross-system resolution recovery, choose a typed
durable outbox transaction/dispatcher design, separate conflict identity from
evidence and confirmation hashes, and close the persistent-cache migration and
account-isolation behavior.
