## Findings

### DR-S4-01-未修复-高-失效 dedup 缓存可把另一笔现金流当作本次回放并跳过创建

- **入口/函数**: `CashFlowRepository.add_cash_flow()` → `_find_by_dedup_key()` → `get_cash_flow()` → `CompletedCashFlowFacts.require()`
- **文件(行号)**: `src/feishu/repositories/cash_flow_repository.py:55-75`; `src/feishu/repositories/transactions_repository.py:108-133`
- **输入场景**: 进程内 `cash_flow:<old-dedup>` 缓存指向 `record_id=cf_changed`；飞书中该记录随后被人工改成另一金额，并且已有与新事实一致的另一 dedup key。此后直接写入原金额的 `CompletedCashFlowFacts`。
- **实际分支**: 通用 dedup 查找在命中缓存时只使用 strict get 确认 record 仍存在，不比较它当前的 `dedup_key`。`add_cash_flow()` 确实将返回行验证为一条内部完整的现金流，但也没有把其 key 与本次请求 key 比较，随即标记 `replayed=True` 并返回。
- **预期行为**: 回放成立必须同时证明远程行完整且其 observed canonical dedup 等于请求 key。缓存映射失效时应清除它并做一次服务端精确 dedup 查询；查无匹配才可创建。
- **实际行为**: 请求 100 CNY 时返回了已改为 200 CNY 的行，且 `list_records.call_count=0` 、`create_record.call_count=0`。
- **直接证据**: 故障注入输出为 `requested_key=48f60ffec7e0b873`, `returned_key=bc7dd69c36aca8fb`, `returned_amount=200.0`, `was_replayed=true`，但本次请求 amount 是 100。
- **影响**: 一笔真实入出金可被静默漏记，调用者还会收到“已回放”的错误成功证据。这不是只发生在创建瞬间的竞态；一次已完成的人工修改可以让失效映射持续到进程结束。
- **建议改法和验证点**: 把“存在”与“可回放”分开。精确读回后首先比较 observed key；不等则驱逐缓存、重做 filtered lookup，并对第二次返回仍不匹配的源响应 fail closed。回归覆盖“失效缓存后找到真实匹配行”和“失效缓存后查无匹配则创建”。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### DR-S4-02-未修复-中-直接创建的热缓存增量仍用 float 求和，与 Decimal 唯一计算口径分叉

- **入口/函数**: `CashFlowRepository.add_cash_flow()` → `LocalCashFlowAggCache.append_flow()` / `_MemoryAccountCache.append_flow()`
- **文件(行号)**: `src/feishu/repositories/cash_flow_repository.py:91-102`; `src/local_cache.py:695-728`; `src/feishu_storage.py:92-114`
- **输入场景**: 账户热缓存已含 0.10 CNY，直接创建一条已通过契约的 0.20 CNY 现金流。
- **实际分支**: row 契约使用分位 `Decimal`，fresh aggregate 也以 `Decimal` 累加；但 hot-cache append 把 `float(facts.cny_amount)` 交给旧 helper，对 daily/monthly/yearly/cumulative 都做二进制浮点加法。
- **预期行为**: 同一组 validated facts 无论来自 fresh rebuild 还是 direct-create incremental update，都应使用同一 Decimal 口径并发布相同结果。
- **实际行为**: 增量路径的四个聚合值均为 `0.30000000000000004`，fresh rebuild 为 `0.3`。
- **直接证据**: 故障注入对同一 account/day/month/year 打印的 daily/monthly/yearly/cumulative 均为 `0.30000000000000004`。S4 的完成契约和 fresh aggregate 已经使用 Decimal，只有 hot append 仍绕过。
- **影响**: 同一行在进程内创建后与重启/fresh refresh 后产生不同的财务聚合值；下游再以 `Decimal(str(cache_value))` 消费时会把该偏差当作十进制事实。
- **建议改法和验证点**: 在 repository 的 completed-fact 边界内以 Decimal 同时更新 daily/monthly/yearly/cumulative，再一次性发布整个 payload；不调用 float-only append helper。增加 0.10 + 0.20 回归，并断言热缓存等于 fresh 聚合。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### DR-S4-03-未修复-中-新 dedup 文本格式未完整保留旧版指纹语义

- **入口/函数**: `make_cf_dedup_key()` / `expected_cash_flow_dedup_key_from_values()` → `_decimal_text()`
- **文件(行号)**: `src/models.py:464-478`; `src/domain/cash_flow_contracts.py:441-480,702-709`; base `8ef9c8c` 中 `src/models.py` 的旧 `make_cf_dedup_key()`
- **输入场景**: 一条历史合法金额在 Python float 文本中使用科学计数法，例如 `100000000000000000000.00` 经旧 `CashFlow` 量化后为 `1e+20`。
- **实际分支**: 旧 key 对 `str(cf.amount)` 做哈希，原文是 `1e+20`；新 `_decimal_text()` 固定输出 `100000000000000000000.0`。两个字符串表示同一金额，却生成不同 key。
- **预期行为**: 在没有授权历史修复/迁移的前提下，S4 声明的 legacy-compatible serializer 必须对所有旧模型可表示金额产生与 `str(float(cent_quantized_amount))` 相同的指纹文本。
- **实际行为**: 同一手工事实的旧 key 是 `4e804eab0c9f5f63`，新 key 是 `23d8561bd58806cf`。
- **直接证据**: 反例使用项目原量化常量 `0.01`和旧 key 公式计算，可稳定复现上述两个值；当前回归只覆盖 `100.00 → 100.0`。
- **影响**: 已有行会被判为 `DEDUP_KEY_MISMATCH`，相同手工事实也可绕过精确查找并创建第二条记录。出现概率低于常规金额，但后果是财务行重复。
- **建议改法和验证点**: 将指纹专用文本明确定义为旧版“分位量化后的 Python float 文本”，计算与 CNY 公式仍保持 Decimal。增加普通整数、小数和科学计数法边界的旧/新 key 对照回归。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
