## Findings

### DR-S2-RR2-01-未修复-中-`init_db` 的 create-only 意图仍会在竞态中退化为增量 upsert

- **入口/函数**: `skill_api.init_db()` → `HoldingsRepository.upsert_holding()`
- **文件(行号)**: `skill_api.py:725-747`; `src/feishu/repositories/holdings_repository.py:813-847`
- **输入场景**: `init_db(initial_cash=100, broker="IBKR")` 的第一次 exact-fresh read 确认现金行不存在；在随后写入边界的第二次 fresh read 前，外部 writer 创建了同一业务键记录。
- **实际分支**: `init_db` 将 `Holding` 交给兼容性 `upsert_holding()`；后者的第二次 fresh read 看到新行后，计算 `base.quantity + canonical.quantity` 并发出增量更新。
- **预期行为**: 数据库初始化只有 create-only 权威；应构造 `HoldingTarget(base=None, ...)`，如果写入前 fresh proof 发现 base 已出现，应以 `HoldingMutationConflictError` fail closed，且本调用不产生任何写入。
- **实际行为**: 外部新建行会被加上 `initial_cash`，create-only 意图被扩张为对既有数据的数值修改权威。
- **直接证据**: `skill_api.py:747` 调用 `storage.upsert_holding(holding)`；`upsert_holding()` 在 base 存在时明确以 `base.quantity + canonical.quantity` 构造 target，而不是拒绝已出现的 base。
- **影响**: 一个并发初始化或外部编辑窗口可令初始现金重复叠加；这违反 S2 已确认的 absolute target/CAS 语义。
- **建议改法和验证点**: 从领域唯一真源导入 `HOLDING_REQUIRED_VALUE_FIELDS` 和 `HoldingTarget`，使用 `HoldingTarget.from_holdings(base=None, target=holding, owned_fields=required | {"asset_class", "industry"})` 调用 `replace_holding()`；单测断言 target 的 base 为空、identity/owned fields 完整，且从不调用 additive upsert。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
