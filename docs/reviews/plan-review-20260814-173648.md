# Plan Review — NAV Valuation Evidence Replay

- Reviewed target: `docs/gateflow/nav-valuation-evidence-replay/implementation-plan.md`
- Scope: evidence capture, trusted rehydration, daily-job replay, historical
  preparation, CLI/API boundaries, tests, and residual risks
- Review artifact: `docs/reviews/plan-review-20260814-173648.md`
- Conclusion: `fail` pending two plan fixes

## Assumptions tested

- A typed cash-flow refusal always represents a recoverable gate blocker.
- The replay path can reconstruct the existing daily report snapshot without
  adding or changing an ownership boundary.
- Artifact identity plus fresh holdings/cash-flow checks prevent cross-run or
  stale-source replay.
- Historical retrieval never falls back to a current quote or implicit FX.
- Existing NAV and holdings-snapshot persistence remains the sole writer.

## Findings

### PR-PLAN-01-未修复-高-证据保存条件过宽，会把 scope/integrity 缺陷包装成可重放事实

- **位置**: S1 exact changes and immutable evidence capture
- **问题类型**: 状态机漏洞 / 契约缺失
- **当前写法**: 在 typed `CashFlowDatasetRefusal` branch 保存证据，没有限定 refusal reason 或先验证 dataset scope。
- **反例/失败场景**: `record_nav` 因 account、date、run id、window 或 dataset fingerprint 不匹配抛出 `CASH_FLOW_DATASET_SCOPE_MISMATCH`。当前计划仍会给该失败生成 `valuation_ref`，让操作员误以为它是“修复 effect gate 后可重放”的有效估值。
- **为什么有问题**: scope/integrity mismatch 表示传输链本身不可信，不是业务 gate blocker；为它签发 recovery capability 会把程序缺陷降格成可恢复业务状态。
- **直接证据**: `CashFlowDatasetSnapshot.assert_official_scope()` 对 scope mismatch、embedded blockers、effect gate incomplete 都抛同一异常类型，但 reason code 分别为 `CASH_FLOW_DATASET_SCOPE_MISMATCH`、`CASH_FLOW_DATASET_BLOCKED`、`CASH_FLOW_EFFECT_GATE_INCOMPLETE`。
- **影响**: 错误证据被持久化、恢复语义误导、integrity failure 难以被发现。
- **建议改法和验证点**: 只允许 `CASH_FLOW_DATASET_BLOCKED` 或 `CASH_FLOW_EFFECT_GATE_INCOMPLETE` 保存证据；保存前要求 dataset account/date/run id 与当前请求严格相等且存在 financial fingerprint/effect revision。新增 scope mismatch 不写 artifact 的测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-PLAN-02-未修复-中-Replay 成功后的 report snapshot 构造没有明确 owner

- **位置**: Replay state transition step 5, S1 affected files
- **问题类型**: 架构边界 / 不可直接实施
- **当前写法**: “project its compatibility valuation/report snapshot”，但没有说明由哪个现有 owner 构造 `holdings_data`、`position_data` 和 `snapshot_time`，affected files 也不含 `PortfolioReadService`。
- **反例/失败场景**: 实现者在 `AccountNavRecorderService` 手写一份 snapshot 字典。它会复制 `PortfolioReadService.build_snapshot()` 的分类、value 和 ratio 语义；以后正常 run 与 replay report 可悄然分叉。
- **为什么有问题**: `DailyReportPayloadService` 明确消费 `PortfolioReadService` 定义的 snapshot shape。跨层复制会引入第二个 report projection owner。
- **直接证据**: `PortfolioReadService.build_snapshot()` 当前唯一组装 `valuation`、`holdings_data`、`position_data`、`holdings_snapshot`；`DailyReportPayloadService.build()` 直接消费这些字段。
- **影响**: 日报展示与持久化 NAV 可能不一致，测试只能靠大集成链发现漂移。
- **建议改法和验证点**: 在 `PortfolioReadService` 提取一个最小的 normalized-valuation-to-snapshot helper，正常构建和 replay 共用；把该文件加入 S1 scope，并测试相同 normalized valuation 的两种入口产生相同 report-relevant projection。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
