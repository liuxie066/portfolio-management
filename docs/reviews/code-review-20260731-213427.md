## Findings

### 1-未修复-高-`recover` 可把从未进入 apply 的待处理 case 错误关闭

- **入口/函数**: `HoldingsWorkflowService.recover()`
- **文件(行号)**: `src/app/holdings_workflow_service.py:240-321`
- **输入场景**: 对 `pending_apply`、`pending_confirmation` 或 `pending_manual_edit` case 直接执行 `pm holdings recover --case-key ... --confirm`；这些 case 没有 durable `apply_attempt_id`、`target_json`、`before_json` 或远端尝试。
- **实际分支**: 当前代码只排除四个 terminal state，对所有其他状态继续拿 `target=None` / `before=None` 与飞书当前值比较。空值可能被判断为 `resolved_accept`，非空值可能被判断为 `superseded`。
- **预期行为**: `recover` 只接受 `applying`、`failed_retryable`、`apply_outcome_unknown` 且具有一致 durable apply attempt 的 case；普通待处理/待确认/人工编辑 case 必须拒绝，不能借 recovery 绕过原确认入口。
- **影响**: 未执行任何补全或人工冲突决策时，case 可能被错误标成 terminal，破坏人工确认和后续 NAV 阻断语义。
- **建议改法和验证点**: 在锁前和锁内都校验可恢复状态、`apply_attempt_id` 及 target/before durable facts；增加 pending apply/conflict/manual case 调用 recover 必须失败且状态不变的测试。
- **修复风险**: 低
- **严重程度**: 高

### 2-未修复-高-已闭环的同语义问题再次出现时 case 仍保持 terminal

- **入口/函数**: `OperationStateStore.materialize_holding_cases()`、`materialize_and_prepare_holding_apply()`
- **文件(行号)**: `src/app/operation_state_store.py:640-850, 1050-1280`
- **输入场景**: 一个 missing case 经人工修复变成 `resolved_external` 或经补全变成 `resolved_accept`，之后同一记录、字段、当前值、建议值和策略精确回退到原问题；稳定语义会生成相同 `case_key`。
- **实际分支**: 已有 `case_key` 只刷新 evidence/record digest，不把 `resolved_external`、`resolved_accept` 或旧 `superseded` 重新变为当前 pending state。发现回执也不会重建。
- **预期行为**: `resolved_keep` 在 confirmation scope 相同期间可继续有效；其他 terminal case 再次成为当前 actionable case 时至少必须重新进入对应 pending state并追加 `reopened` 审计事件。根据计划的确定性回执约束，可以不重发相同 discovery key，但不能保持已解决状态。
- **影响**: 复发的数据缺失/冲突在 durable workflow 中看起来仍已闭环，cases CLI 和未来 NAV gate 可能消费错误状态，且人工不会看到当前待办。
- **建议改法和验证点**: 对相同 case key 的 terminal recurrence 建立明确 reopen transition；保留历史事件，清除旧 apply 临时字段；增加 resolved external/accept 后精确回退的测试。新语义出现时也应让旧 `resolved_keep` 显式 superseded，避免过期决策看似仍有效。
- **修复风险**: 中
- **严重程度**: 高

### 3-未修复-高-Recovery 只比较目标字段且未验证记录身份已漂移

- **入口/函数**: `HoldingsWorkflowService.recover()`
- **文件(行号)**: `src/app/holdings_workflow_service.py:252-300`
- **输入场景**: apply 后状态未知，随后同一 Feishu record 被移动到账户、改了 asset id 或 broker，但目标字段仍恰好等于 target；或者账户从 `lx` 改为 `sy`。
- **实际分支**: recovery 按 case 中旧账户获取 account lock，fresh-read 后只比较 `case[field]` 与 before/target，不校验当前 account/asset/broker identity。目标字段相等即 `resolved_accept`。
- **预期行为**: Recovery 必须在旧账户锁和 record lock 下 fresh-read，并在终态分类前验证 frozen canonical identity；身份漂移应 `superseded`，不能把旧确认应用到新 scope。
- **影响**: 旧账户/标的范围的人工确认可能被错误归因到已经变更身份的记录；同时所持 account lock 与当前写入账户不一致。
- **建议改法和验证点**: durable case 保存 canonical identity 或可等价校验的冻结字段；recovery 先比较 identity，再比较绝对 before/target。增加 account、asset id、broker 各自漂移且字段等于 target 的测试。
- **修复风险**: 中
- **严重程度**: 高

### 4-未修复-中-未知的更高 holdings feature schema 在拒绝前已执行本版本 DDL

- **入口/函数**: `OperationStateStore._initialize()`
- **文件(行号)**: `src/app/operation_state_store.py:55-190`
- **输入场景**: 数据库已有 `holdings_workflow_schema_version=2`，当前二进制只支持 v1。
- **实际分支**: 当前代码先执行本版本全部 `CREATE TABLE/INDEX` 与 NAV claim-column migration，再读取 feature marker 并抛错。SQLite `executescript()` 有自己的事务/提交行为，不能依赖后续异常完整撤销先前 DDL。
- **预期行为**: 在任何 holdings workflow DDL 前只读检查已有 feature marker；高于支持版本立即 fail closed，不触碰数据库。缺失/较低版本才在单一 migration transaction 中创建 v1 表并提升 marker。
- **影响**: 不兼容二进制启动可能改变未知新版数据库的 schema，违反“拒绝高版本且不降低/重置”的迁移边界。
- **建议改法和验证点**: 将 feature-version preflight 移到 `executescript()` 前；测试高版本数据库在构造失败后 sqlite schema 和所有 meta 值逐字节/逐项不变。
- **修复风险**: 低
- **严重程度**: 中
