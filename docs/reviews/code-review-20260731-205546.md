### DR-S1-01-未修复-高-预加载绕过原始校验并把重复持仓静默折叠为一条缓存

- **入口/函数**: `get_holdings()` -> `preload_holdings_index()` ->
  `_put_holding_cache()`
- **文件(行号)**: `src/feishu/repositories/holdings_repository.py:152-190`;
  `src/app/holdings_validation.py:304-313,848-878`
- **输入场景**: Feishu 同一账户返回两条都能转成 `Holding`、但
  `(asset_id, account, broker)` 相同的行；或可选原始字段包含需要报告的
  非法值。
- **实际分支**: 预加载先调用会改写值的 `_from_feishu_fields()`，然后
  只通过 `_dict_to_holding()` 构造模型。它不调用已实现的
  `HoldingsValidator._mark_duplicates()`。两条重复行随后以同一 cache key
  依次 `_put_holding_cache()`，后一条覆盖前一条，并把账户标记为已完整
  加载。
- **预期行为**: cache v2 只能在整个新鲜 slice 通过原始校验后发布；
  重复业务主键必须聚合报错且不发布任何新缓存。
- **实际行为**: 一条任意的重复行成为唯一的缓存事实，调用方看不到
  duplicate blocker；且预加载与 `pm holdings reconcile` 对同一份源数据
  作出不同裁决。
- **直接证据**: `preload_holdings_index()` 的 converted loop 只捕获单行模型
  转换错误；发布 loop 对每条调用 `_put_holding_cache()`。而重复判定
  仅存在另一条未被预加载消费的 validator 路径中。
- **影响**: 持仓数量/币种可以被任意一条重复行决定，普通持仓读取和
  后续估值可在没有阻断信号的情况下使用不完整事实。
- **建议改法和验证点**: 在任何 cache mutation 前对整个 raw slice 执行同一
  份结构/业务主键校验，聚合重复和单行错误后一次性失败；缓存重建
  不得经过会把非法可选值改成空值的 loose parser。新增回归测试：
  两条重复行不发布、不标记 loaded，原缓存保持不变。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-S1-02-未修复-高-Futu 证据匹配丢弃市场限定后可把另一市场的同代码当成精确标的

- **入口/函数**: `HoldingsValidator.validate()` ->
  `HoldingsEvidenceBundle.futu_position()` -> `FutuPositionEvidence.matches()`
- **文件(行号)**: `src/app/holdings_validation.py:74-104,115-143`
- **输入场景**: holdings 的 `asset_id` 带有明确市场后缀，例如
  `AAPL.HK`；当前 Futu 快照只有 `US.AAPL`。
- **实际分支**: `_normalized_futu_asset_id()` 对两个值都剥掉市场，只留
  `AAPL`。`exact_position()` 因此得到唯一“精确”匹配，并把美股币种/类型
  证据提供给该港股限定行。
- **预期行为**: provider-specific normalization 可以统一 `US.AAPL` 与
  `AAPL.US` 的表示，但当两侧都有市场事实时必须要求一致；市场冲突
  应为零匹配而不是精确证据。
- **实际行为**: 市场冲突行可被提议 `USD`/`us_stock`，并产生错误补全
  或错误冲突。
- **直接证据**: `_normalized_futu_asset_id()` 对前缀和后缀市场都只返回
  symbol；`matches()` 不比较 `position.market` 或解析出的市场。
- **影响**: 新工作流可以向人工确认展示错误的权威币种/类型，后续确认
  会把错误事实写回持仓。
- **建议改法和验证点**: 解析成 `(symbol, market?)`；双方有 market 时
  必须相等，只有一方无 market 时才允许在账户快照内进入唯一性裁决。
  覆盖前缀/后缀同市场、显式市场冲突、无市场多匹配。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-S1-03-未修复-中-record digest 直接 hash 原始 JSON，没有实现计划定义的语义归一化

- **入口/函数**: `RecordValidation.as_dict()`
- **文件(行号)**: `src/app/holdings_validation.py:33-44,242-254`
- **输入场景**: 两次新鲜读取的语义值相同，但传输表示为 `" USD "`
  与 `"USD"`、`10` 与 `10.0`，或 enum 大小写不同。
- **实际分支**: `record_digest` 对 `raw.canonical_fields()` 的原始值直接
  `json.dumps(..., default=str)` 后 hash，没有按字段 trim/大小写/Decimal
  归一化。
- **预期行为**: 记录 digest 应对所有 validation-relevant 字段使用稳定
  语义值：文本 trim、enum 小写、currency 大写、有限数 Decimal 字符串。
- **实际行为**: 等价事实产生不同 digest。
- **直接证据**: `_canonical_json()` 只排序 key；`RawHoldingRecord.canonical_fields()`
  只复制 key/value，两者均未根据字段语义归一化。
- **影响**: S2 的 case dedupe/confirmation scope 和 S3 的 same-digest no-op 会因等价
  格式变化重建 case、重发回执或失效人工确认，无法满足稳定身份合同。
- **建议改法和验证点**: 由 validation contract 唯一产生规范化的
  persistent-field payload 和 `record_digest`；不允许后续 workflow 各自二次解释。
  测试语义等价表示 digest 相同，真实字段变化 digest 不同。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### DR-S1-04-未修复-中-账户或记录定向读取不验证返回资源是请求目标

- **入口/函数**: `HoldingsRepository.get_raw_holdings()`
- **文件(行号)**: `src/feishu/repositories/holdings_repository.py:192-226`
- **输入场景**: account-filtered 列表响应混入另一账户的行，或
  record endpoint 响应的 `record_id` 与请求 id 不一致。
- **实际分支**: 方法只验证响应有非空 `record_id` 和 dict `fields`，然后
  把全部响应返回上层。
- **预期行为**: 定向 scope 的 source adapter 必须以响应中的权威字段验证
  scope；不匹配应作为 source integrity failure，不能成为另一账户的校验结果。
- **实际行为**: `reconcile(account="lx")` 可返回 `sy` 的问题并观测 `sy`
  的 Futu 账户；one-record 路径可处理错记录。
- **直接证据**: 列表路径仅将 account 放入 Feishu filter，随后的 loop 不比较
  `fields.account`；单记录路径也不比较 requested/resolved id。
- **影响**: 账户隔离与单记录确认的基础 scope 不是 fail-closed；后续 S2/S4
  可将 case/blocker 归到不对的操作。
- **建议改法和验证点**: 对 account scope 要求每条 raw `account` trim 后
  严格相等；对 record scope 要求 resolved id 等于 requested id。任何不匹配报
  source integrity error，并测试不触发对其他账户的 Futu 观测。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
