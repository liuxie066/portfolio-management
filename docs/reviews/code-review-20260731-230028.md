## Findings

### DR-AGG-01-未修复-高-事件 worker 把 Futu provider 失败当成已完成的业务校验

- **入口/函数**: `HoldingEventInboxService._process_claimed()` ->
  `HoldingsWorkflowService.plan_event_notification()` ->
  `HoldingsReconciliationService.evaluate_records()`
- **文件(行号)**: `src/app/holding_event_inbox_service.py:117-146`;
  `src/app/holdings_workflow_service.py:110-150`;
  `src/app/holdings_reconciliation_service.py:93-116`
- **输入场景**: holdings 的 Futu 账户行产生 edited event；worker fresh-read
  飞书行成功，但 `observe_portfolio()` 因 OpenD/provider 暂时不可用失败。
- **实际分支**: reconciliation 将 provider 异常收集到 `evidence_errors`
  而不抛出；`plan_event_notification()` 仍基于不完整证据构造 cases，仅将
  `prove_external=False`；worker 随后在一个事务中物化这些 case/receipt
  并把 inbox 标记为 `processed`。
- **预期行为**: 已确认方案要求 event transport/provider/read failure
  保留为 `failed_retryable`，不能在缺失当次必需 provider 证据时物化业务
  结论或伪造 apply outcome。NAV 的人工决定 outage fallback 是另一条明确
  合同，不能被事件 worker 暗中复用。
- **影响**: 一次短暂 OpenD 故障可将事件永久消费，还可创建与后续
  完整证据不同的 manual/conflict case 和通知；provider 恢复后原事件不会
  自动重试。
- **建议改法和验证点**: 在 event-only planning boundary 检查
  `evaluation.report.evidence_errors`，若非空则抛出带 account/error 的可重试
  异常；让现有 worker failure transition 回收 claim。新增回归证明 inbox
  `failed_retryable`、零 case/回执，provider 恢复后同一事件可处理成功。
- **修复风险**: 低
- **严重程度**: 高
