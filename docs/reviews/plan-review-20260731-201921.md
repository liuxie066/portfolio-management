## Assumptions tested

1. Raw Feishu reads enter before current typed/cache defaults, so a blank
   currency cannot be converted into CNY before validation.
2. `asset_type` selects a versioned currency resolver, while generic/HK cases
   stay unresolved unless explicit instrument evidence or a scoped human
   decision exists.
3. Event payloads are prompt/transport facts only; validation always fresh-reads
   the current record and the event path has no holdings-field write authority.
4. At-least-once event delivery has a durable `event_id` inbox, bounded callback
   behavior, duplicate-integrity check, leases, replay safety, and a separate
   semantic case identity.
5. Each actionable case creates a deterministic frozen receipt whose action is
   executable for that exact state.
6. New reconciliation completion/correction writes require explicit
   one-record/one-case confirmation without redefining the existing separately
   confirmed Futu synchronization writer.
7. Remote-write uncertainty is owned only by reconciliation cases; the
   transport inbox cannot initiate, represent, or recover a holdings mutation.
8. NAV correctness does not depend on listener health and valuation consumes
   the exact fresh typed snapshot that passed preflight.
9. Schema migration, rollback, receipt fan-out, current CLI compatibility, and
   slice sequencing are concrete enough for an implementation agent.

## Required review lenses

- **Architecture boundary**: transport adapter/inbox, pure validation,
  workflow state, receipt delivery, existing Futu writer, and NAV gate now have
  distinct owners and one-way dependencies.
- **Best practice**: the plan covers raw-source fidelity, fail-closed reads,
  explicit authority, deterministic identity, atomic local state/outbox changes,
  bounded callbacks, idempotency, retry/unknown separation, readback, recovery,
  and focused plus aggregate tests.
- **Optimal solution**: using the record event only for prompt discovery and
  keeping writes human-confirmed is the safest practical design under the
  current update-record API, which exposes no revision/If-Match precondition.
  NAV preflight remains the correctness backstop instead of adding a polling
  scheduler or treating listener health as data evidence.
- **Overengineering**: the one adapter, inbox, worker, and service are justified
  by the external at-least-once/short-deadline protocol. Generic routing,
  interactive cards, Base automation, public webhooks, deletion behavior,
  cross-host locking, and a security master remain explicitly out of scope.
- **Overcoupling**: the revised write rule is scoped to the new reconciliation
  workflow; S1-S4 share narrow domain contracts without forcing the listener,
  Futu writer, receipt transport, and valuation layer into one implementation.

## Residual risks and suggested tracking

- Feishu's current update-record API has no atomic revision/If-Match guard.
  Explicitly confirmed CLI writes therefore retain a narrow external same-field
  race despite locks, fresh preconditions, narrow patches, readback, and
  fail-closed unknown recovery. Keep this visible in S2 implementation review
  and track any future conditional-write capability separately in the Feishu
  adapter backlog. This does not authorize background writes.
- Long-connection app type, publication, event permission, Base subscription,
  and owner/admin access cannot be proven from repository configuration. Keep
  these as fail-closed checks in the later activation runbook; do not add a
  webhook fallback.
- Listener outage and formula-only changes can delay case discovery/receipts.
  Fresh official NAV preflight is the correctness backstop; listener SLO and
  alerting remain a later operations work unit.
- Same-host locks do not serialize a future multi-host writer topology. Track
  cross-host concurrency as a separate architecture work unit if topology
  changes.
- Local CLI operator metadata is audit context rather than cryptographically
  authenticated identity. Interactive Feishu actions or multi-user OS
  authorization remain a separate security decision.

Protocol evidence used for the boundary: the official record-change event is
at-least-once and includes added/edited/deleted action entries, while the
official update-record contract offers incremental field update but no atomic
record-revision precondition. See [Feishu Base record-change event](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/drive-v1/file/events/bitable_record_changed)
and [Feishu update-record API](https://open.feishu.cn/document/server-docs/docs/bitable-v1/app-table-record/update).
