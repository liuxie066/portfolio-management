### DR-S7-01-未修复-高-完整 NAV 读取会静默丢弃无效日期行，把源数据缺口发布为成功缓存

- **入口/函数**: `preload_nav_index()` / `audit_nav_history_duplicates(account=...)` -> `_build_nav_index_payload()` -> `_build_nav_payload_from_cache_rows()` -> `get_nav_history()` / `get_nav_on_date()`
- **文件(行号)**: `src/feishu/repositories/nav_history_repository.py:62-86,125-149,221-259,279-341`
- **输入场景**: 飞书返回一条属于目标账户、但 `date` 缺失或不是 `YYYY-MM-DD`/合法时间戳的 NAV 行；或版本化磁盘缓存中的一行损坏。
- **实际分支**: 两层 builder 都捕获 `_dict_to_nav()` 的 `TypeError`/`ValueError` 并直接 `continue`。远端行数仍可在 audit 结果中计数，但发布的 `nav_history` / `_nav_objects` / `record_count` 已经不包含该行。
- **预期行为**: S7 的完整公共读取必须要么保留 canonical 行，要么对无法构建的行显式 fail closed/报告 invalid source fact；不能用一份已删行的“完整缓存”继续供 audit、repair 和写前判断使用。
- **实际行为**: preload 和 account audit 仍返回成功，后续公共读取看不到该远端事实；写路径还可以在这份缺行索引上做存在性和重复性判断。
- **直接证据**: `_build_nav_index_payload()` 在 137-140 行吞掉远端行的构建错误；`_build_nav_payload_from_cache_rows()` 在 74-79 行再次吞掉同类错误。`preload_nav_index()` 在这之后仍调用 `_store_nav_index_payload()` 并返回 `source=feishu`。现有完整行回归只覆盖合法日期。
- **影响**: 历史 NAV 事实被静默隐藏，duplicate audit 和 repair 输入不完整，最坏情况下可在原始异常行仍存在时创建/覆盖另一行，破坏 S7 的无损公共读取承诺。
- **建议改法和验证点**: 移除两层 builder 的静默 `continue`，将 account/record_id/原因放入稳定的读取完整性异常后 fail closed；新增远端 missing/invalid date 和版本化磁盘行损坏测试，断言不发布部分 payload、不返回成功 audit、不进入写请求。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### DR-S7-02-未修复-中-Stage-aware error 把明确被拒绝的 target 也标成 unknown，`failed_scopes` 反而没有业务目标身份

- **入口/函数**: `_write_nav_full_records()` 的 update-success/create-failure 分支 -> `_fail_closed_if_finality_would_be_dropped()` -> `_stage_aware_batch_error()`
- **文件(行号)**: `src/feishu/repositories/nav_history_repository.py:481-570,808-830`
- **输入场景**: 同一账户 update 已成功；create 请求被飞书以明确 `FieldNameNotFound: details` 拒绝，且 target 含必需 `details.finality`，因此代码拒绝删除 details 重放。
- **实际分支**: 821-830 行把明确 schema rejection 转成 stage-aware error；helper 在 529-532 行无条件把所有未 confirmed create rows 填入 `unknown_scopes.create`，而 558-564 行的 `failed_scopes.create` 只有 operation/chunk/reason，没有 date/record_id target。
- **预期行为**: 显式服务端拒绝且零 confirmed 的 target 应进入 `failed_scopes`；只有超时、传输中断或响应无法映射等不能证明远端结果的 target 才进入 `unknown_scopes`。失败 stage 元数据应与 target scope 分开。
- **实际行为**: 一个代码自身已经当作“服务端明确拒绝、可安全改 payload 重试”的错误，到 receipt scope 却被表达为“可能已创建”；同时 `failed_scopes` 无法告诉恢复器哪个日期 target 失败。
- **直接证据**: FieldNameNotFound 分支只在 `confirmed_results` 为空时允许 compatibility retry，证明当前实现已将该协议结果视为明确未写入；但 helper 不接收 outcome classification，并将所有未 confirmed rows 统一归为 unknown。现有故障测试只使用 `transport outcome unknown`，没有拒绝类样例。
- **影响**: 操作者/恢复器不能依据 scope 区分“修 schema 后安全重试”和“先查重再重试”，降低 F13 修复的可恢复性和可观测性。
- **建议改法和验证点**: 让 helper 显式接收 `failed`/`unknown` target outcome，将带 date/record_id 的未 confirmed target 只放入对应 scope；另存 `failure_stage`/reason 元数据。增加 update-success + finality FieldNameNotFound 回归，并保留现有 transport-unknown 回归，断言两者互斥。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中
