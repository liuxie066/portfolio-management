## Findings

### DR-S2-RR3-01-未修复-高-现金流确认会把已确认 target 重新绑定到后出现的数量事实

- **入口/函数**: `CashFlowEffectService.confirm()` → `_confirm_under_locks()` → `HoldingTarget.from_holdings()`
- **文件(行号)**: `src/app/cash_flow_effect_service.py:1539-1570,1617-1681`
- **输入场景**: confirm 内的 `_build_preview()` 以 fresh quantity=100 重算出并校验了 target=110；在 preview hash 校验通过后、构造 mutation 前，外部 writer 将同键现金改为 120。
- **实际分支**: target 循环再次 fresh-read 得到 120，但没有与 `recomputed["target_rows"][i]["before"]` 比较；它以这个新 base 构造只 own `quantity` 的 target，因此领域检查允许把 120 覆盖为旧的已确认 target=110。
- **预期行为**: mutation 必须绑定到生成该 confirmed target 的同一 before fact；二次 fresh read 若在 record ID、identity 或 quantity 上不同，应在任何状态转换/远程写前 fail closed，要求重新 preview/confirm。
- **实际行为**: 窗口内的新现金事实被视为新 base，但 target 仍来自旧 base，把 CAS 契约退化为对并发数量的静默覆盖。
- **直接证据**: `_build_preview()` 已把每行 before 放入 `target_rows`；但 line 1621 只遍历 `recomputed["targets"]`，line 1628 用新 fresh row 作 base，line 1629-1641 对既有行只 own quantity，全路径没有对新 before 与 hash-bound before 做一致性判定。
- **影响**: 确认后的并发入金、出金或人工现金修改可被旧 target 覆盖，产生直接财务事实错误。
- **建议改法和验证点**: 在构造 `HoldingTarget` 前将第二次 fresh row 的 canonical record ID/identity/quantity 与同序 `target_rows[].before` 比较；不同就在 `applying` 之前拒绝。添加 fault-injection 测试：confirm 的 preview 重算读 100，mutation-base 读 120，断言零 `replace_holding`、effect 仍未进入 applying/compensation。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### DR-S2-RR3-02-未修复-中-`asset_name` 的必填/不可清空定义没有被读取和写入边界共同执行

- **入口/函数**: `canonical_holding_value()` / `HoldingPatch.from_base()`；`HoldingsRepository._dict_to_holding()`；`validate_write_fields()`
- **文件(行号)**: `src/domain/holding_mutations.py:23-57,163-202,303-337`; `src/feishu/repositories/holdings_repository.py:1214-1265`; `src/feishu/contracts/registry.py:65-103,219-225,344-403`
- **输入场景**: 对现有行构造 `HoldingPatch(..., asset_name="   ")`；或从 Feishu 读到缺少 `asset_name` 的 raw row；或直接 client create 传入空白 identity/name 文本。
- **实际分支**: 领域 canonicalizer 把空白 name trim 成 `""` 但不拒绝；typed reader 以 `str(data.get('asset_name') or '')` 制造空名；registry required check 只比较精确 `""`，空白字符串仍通过。实测中 patch 得到 `{'asset_name': ''}`，update 空串和 create 空白必填文本都通过 registry validation。
- **预期行为**: registry 已声明 `asset_name` 是 create row-required 且 nonclearable；领域 target/patch、typed read 与 direct client 必须对空白值作出同一拒绝决定，raw reader 仍保留缺失供人工校验。
- **实际行为**: 三层对同一必填事实得到不同结果，且标准 typed path 用空字符串隐藏了 missing。
- **直接证据**: registry create required set 包含 `asset_name`，但 `canonical_holding_value('asset_name', ...)` 只返回 `str(value).strip()`；`_dict_to_holding()` 的 `required_text` 独独排除 asset_name；`validate_write_fields()` line 374 只把 `None` 或 exact empty string 当缺失，update clearability 只检查 null。同时 `HOLDING_VALUE_FIELDS` 仍是无完整 registry coverage assertion 的第二张结构列表，未来可再次静默漂移。
- **影响**: 新写入可以产生空名的核心持仓，历史不完整行又可被标准 typed reader 当作合法事实；这会继续分裂 structure/domain/read 真源。
- **建议改法和验证点**: 让 `asset_name` 使用 nonblank canonicalization；typed reader 将它纳入必填检查；registry 对 required text 先 trim 判空，并拒绝 nonclearable 文本的空白 update；添加 registry 字段与 identity/value/system projection 的完整 coverage assertion。覆盖 domain patch、typed raw conversion、single/batch client 零请求和 projection drift 测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### DR-S2-RR3-03-未修复-中-pre-write CAS 冲突会留下已知过期缓存并被 compensation 误分类

- **入口/函数**: `replace_holding()` / `apply_holding_patch()` / bulk target check → `HoldingMutationConflictError`；`CompensationService.retry()`
- **文件(行号)**: `src/feishu/repositories/holdings_repository.py:280-305,678-771,940-958`; `src/app/compensation_service.py:228-249,360-431`
- **输入场景**: cache 中仍是 quantity=1 的 bound base，外部 writer 已把远程行改为 quantity=2；replace/compensation retry 的 fresh-base check 观察到 digest 不同并拒绝写入。
- **实际分支**: `_fresh_base_for_target()` 和 patch/bulk 的冲突分支直接 raise，既不 publish 已读到的 fresh slice，也不 invalidate 旧 cache；随后 exact cached read 仍可返回 quantity=1。compensation 又只将 `CompensationStateConflict` 归类为 `state_conflict`，repository 拋出的 `HoldingMutationConflictError` 被记成 `target_apply_failed`。
- **预期行为**: 一旦 fresh mutation evidence 证明 bound base 过期，必须使该 account 的内存/持久缓存失效，且 durable compensation 应明确记录 `state_conflict`，不得暗示已尝试未知写入。
- **实际行为**: 无写入的安全冲突仍会留下已知错误的本地事实，运维回执又把它与 transport/proof 失败混为一类。
- **直接证据**: `_fresh_base_for_target()` 的四个 conflict raise 前没有任何 cache 处理；`get_holding()` 对完整 broker 键优先直接返回 cache；`retry()` line 229-233 的类型判定不包含 `HoldingMutationConflictError`。
- **影响**: 冲突后的后续查询可显示已知过期持仓，并且 compensation 诊断/重试策略无法区分权威冲突与真正的写入失败。
- **建议改法和验证点**: 在 target/patch/bulk 的 fresh-base 失败出口一致 invalidate 并 flush account cache；将 `HoldingMutationConflictError` 纳入 compensation `state_conflict` 分类。回归测试应预填内存+持久 cache，注入 remote digest drift，断言零 transport、两层 cache 皆空，以及 durable retry 的 `error_type=state_conflict`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
