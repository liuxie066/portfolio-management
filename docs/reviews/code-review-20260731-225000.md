## Findings

### DR-S4-01-未修复-高-全局孤儿修复后正式预检不关闭旧 case，也不验证 workflow state 可用性

- **入口/函数**: `HoldingsNavPreflightService.scan_global_orphans()`
- **文件(行号)**: `src/app/holdings_nav_preflight_service.py:267-300`
- **输入场景**: 一次正式 NAV 预检已为缺失 account 的行建立全局
  `pending_manual_edit` case；随后人工在 holdings 表补齐 account，再跑正式预检。
- **实际分支**: 新扫描无 orphan 时在 `plan["case_keys"]` 为空处直接
  返回 `valid`，不访问 operation state，也不将旧全局 case 转为
  `resolved_external` 并队列化关闭回执。
- **预期行为**: 正式 fresh scan 证明 orphan 已消失时，应按既有状态机
  关闭 synthetic global case；该过程任何 SQLite 失败必须阻断 NAV。演练仍必须
  零状态写入。
- **影响**: 人工已修复的全局阻断在 cases/receipts 中长期显示为待办；
  同时 operation-state 库不可用时，无当前 orphan 的正式 NAV 反而可继续，
  违反 fail-closed 验收条件。
- **建议改法和验证点**: 增加一个仅正式路径调用的 global fresh-proof
  transition，复用现有 `resolved_external` 事件/关闭回执事务；演练不得
  打开可写 store。覆盖修复后关闭、空库成功、store 失败阻断和 dry-run
  零写入。
- **修复风险**: 中
- **严重程度**: 高

### DR-S4-02-未修复-高-匹配的 keep-current 在 Futu 暂时不可用时被无条件失效

- **入口/函数**: `HoldingsNavPreflightService.prepare_account()` ->
  `HoldingsWorkflowService.plan_evaluation()`
- **文件(行号)**: `src/app/holdings_nav_preflight_service.py:328-408`;
  `src/app/holdings_workflow_service.py:152-190`
- **输入场景**: 操作员已对一个 Futu 精确证据产生的币种/类型冲突选择
  `keep-current`，原始行、identity、current value、policy 和 confirmation
  scope 都未变；之后一次 NAV 预检遇到 OpenD 暂时不可用。
- **实际分支**: 只在当前 validation 重建出同一 `case_key` 时读取
  `resolved_keep`；然后只要 `evaluation.report.evidence_errors` 非空就立即
  `holdings_evidence_unavailable`。
- **预期行为**: 方案已定义 active manual decision 为最高优先级，并明确
  允许它在后续 Futu outage 中继续有效，前提是按当前 raw facts 重算的
  confirmation scope 仍匹配。新的语义 Futu 证据变化仍应创建新 case。
- **影响**: 已完成人工裁决的账户因短暂 provider 故障无法记录 NAV，
  实际行为与已确认方案相反；但若简单忽略整个账户的证据故障，
  又会让未确认的其他行错误放行。
- **建议改法和验证点**: 仅在 provider outage 分支读取当前账户的
  durable `resolved_keep`，对每个 case 用当前 raw record 重算 identity、current、
  authority inputs、policy 和 confirmation scope；只屏蔽精确匹配字段的临时
  evidence blocker，其他 blocker 仍 fail closed。覆盖匹配放行、raw/current/identity/
  policy 漂移失效，以及同账户未确认行仍阻断。
- **修复风险**: 高
- **严重程度**: 高
