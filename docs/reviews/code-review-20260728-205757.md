## Findings

### 1-已修复-高-Outbox 没有原子 claim，定时重试与任务内即时投递可重复发送同一条回执

- **入口/函数**: `NavReceiptOutboxService.enqueue_and_dispatch()` / `dispatch_pending()` -> `OperationStateStore.list_due_nav_receipts()` / `mark_nav_receipt()`
- **文件(行号)**: `src/app/nav_receipt_outbox_service.py:20-31,54-74`; `src/app/operation_state_store.py:259-320`; `src/service/application.py:733-741`
- **输入场景**: 一个真实 NAV job 刚把 `nav:<run_id>` 写入 outbox 并开始即时投递；与此同时每五分钟的独立 receipt timer 进程也查询到该行。另一个等价场景是消息发送成功后，本地 `mark_nav_receipt()` 因 SQLite I/O/锁/磁盘异常失败。
- **实际分支**: `list_due_nav_receipts()` 只是查询所有 `pending/failed` 行，没有在同一事务中把行 claim 为某个 dispatcher；两个进程都能读到同一行，并在任何状态更新之前分别调用 `sender.send()`。发送发生在第 67 行，状态更新到第 69 行以后才开始。若发送成功而状态更新抛错，`PortfolioService.daily_nav_job()` 的宽泛异常分支又直接调用同一个 sender 一次，原 outbox 行仍保持可重试。
- **预期行为**: 一个 due row 在任一时刻只能被一个 dispatcher 持有；并发 worker 不应在无故障条件下重复发送。发送成功但本地落状态未知时，也不应由应用层立即无条件重发并留下仍可再次重试的原行。
- **实际行为**: 即使 Feishu API 没有“成功但响应丢失”，两个正常进程也可以发送两次；若 `mark_nav_receipt()` 失败，则应用层 fallback 会立即再发，timer 后续还可能继续发送。`receipt_key` 只防止重复插入，不防止重复投递。
- **直接证据**: outbox schema 只有 `pending/failed/sent` 的自由文本状态，没有 `sending`、claim owner、lease 或 claim token；due 查询和发送之间没有事务/CAS。systemd 的 `flock` 只序列化 receipt timer 自身，任务内的 `enqueue_and_dispatch()` 不使用同一把锁。现有测试 `tests/test_operation_state_store.py:32-84` 只覆盖单 dispatcher 的失败、重启和重试，没有并发 claim 或“send 成功、mark 失败”用例。
- **影响**: 失败回执可能重复到达，且重试次数和最终状态不再能准确表示实际发送次数。对于运维告警，这会制造重复处置、误判多次失败，并破坏本次改动宣称的 dedup/durable delivery 语义。
- **建议改法和验证点**: 在 SQLite 事务内用 CAS 将 due row 从 `pending/failed` 变为带 `claim_id`、`claimed_at`、lease 的 `sending`，dispatcher 只发送自己成功 claim 的行；完成更新必须校验同一 claim token，超时 claim 可恢复。应用层不要在可能已经调用过 sender 的异常后直接再发；区分 enqueue 前失败、发送失败和发送后落状态未知。增加两个独立 store/dispatcher 并发竞争测试，以及 sender 成功但 mark 抛错的回归测试，断言一次正常投递最多调用 sender 一次。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高
- **修复证据**: outbox schema 升级为 v2，新增 `claim_id/claimed_at`；dispatcher 通过 `BEGIN IMMEDIATE` + CAS claim due rows，并以 claim token 完成状态更新，过期 claim 才可恢复。发送后本地落状态异常现在返回 `status=unknown`，应用层不再立即调用 sender。新增跨两个 store 的原子 claim 测试、v1 schema 升级测试和 send 后 mark 失败不重发测试。

### 2-已修复-高-全新 root 安装会让非 root receipt service 无法创建 operation-state 数据库

- **入口/函数**: `scripts/install.sh --apply --enable-timer` -> `install_linux.apply_install()` -> `portfolio-receipt-dispatch.service` -> `OperationStateStore.__init__()`
- **文件(行号)**: `scripts/install.sh:22,109-128,192-221`; `scripts/install_linux.py:335-348,496-510,596-624`; `src/app/operation_state_store.py:31-55`
- **输入场景**: 按部署文档在一台新 Linux 主机执行 `sudo scripts/install.sh --apply --enable-timer`。安装进程是 root，`RUN_USER` 默认取 `SUDO_USER`，例如 `liuxie`；数据目录默认是 `/var/lib/portfolio-management/.data`。
- **实际分支**: `apply_install()` 以 root 用 `Path.mkdir()` 创建 data/reports 目录，但从未将其 ownership 或写权限交给 `run_user`。新 receipt unit 明确以 `User={run_user}` 执行；`OperationStateStore` 随后需要在 data dir 内创建 `pm_operation_state.sqlite3` 及 WAL 文件。
- **预期行为**: 安装器启用 timer 前，应确保运行用户能创建、读写和锁定新的 operation-state SQLite，同时保持数据库 `0600`。
- **实际行为**: 在标准 root-owned `0755` 父目录下，非 root service user 无法创建数据库。即时 NAV job 会进入 outbox 异常 fallback，失去 durable queue；receipt timer 自身会直接失败，无法恢复未送达回执。
- **直接证据**: `_mkdirs()` 仅调用 `mkdir(parents=True, exist_ok=True)`；仓库安装路径中没有 `chown`/`install -o`/tmpfiles 规则。新 unit 第 343 行切换到 `run_user`，而 store 第 39、52 行分别要求在父目录建文件和打开 SQLite。安装测试只断言 unit 文本与 timer interval，没有验证安装后目录 ownership 或以目标用户初始化 store。
- **影响**: 文档推荐的全新生产安装路径无法提供本次新增的 durable failure receipt 能力；更糟的是服务仍可能通过直接发送 fallback 看似工作，直到一次网络失败后才暴露没有持久重试。
- **建议改法和验证点**: 安装阶段显式创建 runtime data/reports 目录并设置为目标 `run_user` 可写（目录建议最小权限，DB 继续 `0600`）；在启用 timer 前以该用户执行一次 operation-state 初始化/健康检查。增加安装测试验证 ownership 操作被生成/执行，并做一个 root installer + 非 root service-user 的集成检查，确认 SQLite、WAL、SHM 均可创建和重启读取。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高
- **修复证据**: root apply 现在显式把 data/reports 目录以及既有 operation DB/WAL/SHM ownership 交给 `run_user`，runtime 目录设为 `0750`，DB 仍由 store 设为 `0600`。新增安装器测试验证 chown target 和目录 mode。

### 3-已修复-高-升级后旧 FX 确认不会迁移到新权威，已有外币现金流会突然阻断 NAV

- **入口/函数**: `NavRecordService._assert_cash_flow_ready_for_write()` -> `OperationStateStore.latest_fx_confirmation()`；旧入口 `CashFlowEffectStore.record_fx_confirmation()`；人工迁移入口 `cmd_cash_flow_fx_import_legacy()`
- **文件(行号)**: `src/app/nav_record_service.py:118-158`; `src/app/cash_flow_effect_store.py:843-895`; `src/app/operation_state_store.py:157-227`; `scripts/pm.py:491-504`; `docs/cash-flow-effects-runbook.md:8-54`
- **输入场景**: 从已有版本升级；`cash_flow_effects.sqlite3` 中已经存在合法的 USD/HKD FX confirmation，飞书 generated fields 也已写好。升级后直接按现有 runbook 启动 scan/NAV/timers。
- **实际分支**: 新 NAV gate 只读取新文件 `pm_operation_state.sqlite3`。旧 effects store 的确认表和写 API仍存在，但没有兼容读取。虽然新增了显式 `fx-evidence import-legacy` CLI，安装/升级流程不调用、不预检，激活 runbook 也完全没有该步骤。
- **预期行为**: 权威切换必须包含可验证的升级迁移或 fail-closed preflight，确保已有有效确认在启用新 NAV gate 前进入新 store；旧 writer 随后应停用，避免双权威继续分叉。
- **实际行为**: 新 store 自动初始化为空，旧确认被静默忽略；同一条此前可写 NAV 的外币 cash flow 会得到“未经本地确认或已失效”，daily NAV 被阻断。操作者只有读源码才会知道需要额外执行 import 命令。
- **直接证据**: 新 gate 第 133-137 行只实例化/查询 `OperationStateStore`；旧 store 第 843-895 行仍可写可读同名确认表。迁移函数和 CLI 都存在，但 `rg import-legacy README.md docs scripts src tests` 只找到 CLI/测试，没有安装器、upgrade hook 或 runbook 调用。现有迁移测试 `tests/test_operation_state_store.py:87-112` 只证明手工调用幂等，不证明升级路径会执行或阻断遗漏。
- **影响**: 带历史外币 cash flow 的部署升级后会发生可预期的 NAV 中断，表现为“服务在线但 NAV 不更新”；这正是本 work unit 要消除的运维盲区之一。
- **建议改法和验证点**: 在版本升级/启用 timer 的受控流程中加入显式迁移与 readback，或在启动/NAV preflight 检测旧库存在且含记录、新库缺记录时返回带唯一修复命令的硬错误；迁移完成后移除/拒绝旧 store 的 FX 写 API。增加从旧 DB fixture 升级后直接跑 NAV gate 的测试，并验证遗漏迁移时部署预检失败而不是运行日才失败。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高
- **修复证据**: 默认 operation-state 的 NAV preflight 会从默认 legacy effects DB 幂等导入 FX confirmations；自定义旧 DB 保留显式 import 命令，并已补入 activation runbook。新增默认路径升级迁移测试，同时保留显式 import 幂等测试。

### 4-已修复-中-Provider FX apply 仍可写飞书但没有任何生产路径保存本地确认

- **入口/函数**: `FeishuStorage.reconcile_cash_flows(..., fx_rates=..., dry_run=False)` -> `CashFlowRepository.reconcile_cash_flows()` -> 后续 NAV gate
- **文件(行号)**: `src/feishu/_cash_flow_mixin.py:71-97`; `src/feishu/repositories/cash_flow_repository.py:270-329,365-415,461-502`; `scripts/pm.py:427-484`; `src/app/nav_record_service.py:124-158`
- **输入场景**: 调用仍公开支持的 provider 路径，为历史 USD/HKD row 注入带 `rate/date/source` 的 `fx_rates`，并以 `dry_run=False` 应用 reconcile。
- **实际分支**: repository 校验证据并把 `exchange_rate`/`cny_amount` 写入飞书，只把三项 provider evidence 放在返回值 `row["fx_evidence"]`。它不做 readback，也不写 `OperationStateStore`。CLI 编排只在 `manual_evidence` 分支创建 store、readback 并记录确认，且 CLI 没有 provider rates 的应用入口。
- **预期行为**: 任何受支持的 provider apply 路径都应在飞书写入成功并 readback 后，将同一 source hash/rate/date/source 保存到新的本地唯一权威；或者在该编排尚未实现前拒绝 provider 的真实 apply。
- **实际行为**: provider apply 可以返回 `success=true` 且真实修改飞书，但后续 NAV 必然因缺少本地 confirmation 被拒绝。调用方若自行补写 store，会绕过当前 CLI 的 readback/操作者上下文约束，形成另一个隐式契约。
- **直接证据**: repository 第 488-492 行只做 Feishu batch update/cache invalidation，第 494-503 行随后直接返回；整个 production code 中 `OperationStateStore.record_fx_confirmation()` 的唯一调用者是 `scripts/pm.py` 的 manual 分支。现有 provider 测试覆盖 dry-run evidence 生成，没有 provider apply + readback + local confirmation + NAV gate 的闭环测试。
- **影响**: 保留下来的 public provider contract 处于“业务字段已写、技术证据未落”的部分成功状态，会再次导致 NAV 滞后，并要求调用者猜测内部补偿步骤。
- **建议改法和验证点**: 将 reconcile 提升到一个拥有 Feishu write、fresh readback 和 `OperationStateStore` 的 application service，对 manual/provider 共用同一确认落盘流程；在此之前对 provider `dry_run=False` fail closed。新增 provider apply 成功闭环、readback 不匹配不落确认、SQLite 落盘失败返回可恢复状态，以及完成确认后 NAV gate 通过的测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中
- **修复证据**: 在 application readback + local confirmation workflow 尚未实现前，repository 现在对携带 `fx_rates` 的真实 apply fail closed，dry-run evidence 仍保留；测试确认拒绝发生在任何 Feishu batch update 之前。
