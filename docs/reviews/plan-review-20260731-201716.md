# Plan Review

## Reviewed target and scope

- Target: `docs/gateflow/holdings-validation-completion-conflict-receipts/implementation-plan.md`
- Review mode: adversarial re-review after event-trigger and human-confirmation fixes
- Base: `origin/main@49c99e5`
- Branch: `plan/holdings-validation-event-trigger`
- Included: raw holdings validation, asset-type currency policy, durable cases and
  receipts, exact Feishu record-event ingress, explicit confirmation, official
  NAV preflight/snapshot handoff, implementation slices, tests, and rollout
  boundaries
- Excluded: implementation, live Feishu configuration/subscription, production
  data inspection or mutation, commit/push, release, and deployment

## Assumptions tested

- The event listener is a prompt trigger and has no holdings-field write
  authority.
- Human confirmation is actionable from the frozen receipt and maps to exactly
  one documented CLI mutation path.
- The new reconciliation write boundary does not redefine or break the existing
  Futu holdings synchronization writer.
- Event acceptance is durable before acknowledgement and fails within Feishu's
  callback budget when SQLite cannot accept work.
- Transport identity, workflow identity, retries, and remote apply uncertainty
  have one unambiguous owner.
- NAV preflight remains independent of event delivery and valuations consume the
  exact snapshot that passed validation.
- S1-S4 stay within the requested holdings-validation/event/NAV boundary and do
  not introduce a generic event platform, public webhook, polling timer, or
  Base automation.

## Required review lenses

- **Architecture boundary**: the listener/worker separation and transport-only
  inbox are sound, but one stale apply-uncertainty sentence leaks business-write
  ownership back into the inbox.
- **Best practice**: bounded callback durability, fresh source reads, deterministic
  identities, explicit confirmation, readback, and unknown-outcome recovery are
  appropriate. The receipt action contract is incomplete for missing-field
  confirmation.
- **Optimal solution**: validation-and-notification-only event processing is the
  safest current design because the Feishu update-record contract has no atomic
  revision precondition. Reusing the validator/case/outbox path is preferable to
  a second event-specific workflow.
- **Overengineering**: one SDK adapter, inbox, and singleton are justified by
  at-least-once delivery and the short callback deadline; no unsupported generic
  event abstraction is proposed.
- **Overcoupling**: the plan mostly separates transport, workflow, and NAV, but
  its absolute wording about every holdings write conflicts with the existing
  Futu writer that the same plan promises to preserve.

## Findings

### PR-HOLD-EVENT-04-未修复-高-绝对写权限表述与现有 Futu holdings writer 冲突
- **位置**: Sections 2, 3, 8.1, 13, and S3 acceptance
- **问题类型**: 架构边界 / 范围漂移 / 契约缺失
- **当前写法**: Section 2 says every holdings write operates on one record/case
  and requires a one-record/one-case CLI command with `--confirm`; Section 3 says
  no populated holdings field is automatically corrected from any path. The
  same plan says the existing Futu synchronization writer is unchanged and runs
  before NAV validation.
- **反例/失败场景**: A confirmed daily NAV run enables real Futu synchronization.
  The existing service may update multiple position/MMF rows before validation,
  without invoking the new reconciliation CLI once per record. An implementation
  agent must either violate the new absolute rule or redesign/disable the
  existing writer despite the explicit non-goal.
- **为什么有问题**: The user decision removed write authority from the event and
  reconciliation background path; it did not revoke the separately confirmed,
  existing Futu synchronization workflow. The current wording crosses that
  ownership boundary and makes acceptance internally contradictory.
- **直接证据**: Plan lines 66-78 and 112-120 state the absolute rule and also
  preserve the Futu writer; plan lines 753-762 explicitly run real Futu sync
  before validation; `src/app/daily_nav_job_service.py:254-264,371-388` passes
  real sync mode into the account runner; `src/app/futu_balance_sync_service.py:747-771,793-820`
  reports real writes and partial-write outcomes.
- **影响**: Implementation may accidentally break current NAV/Futu behavior,
  broaden the work unit into a sync redesign, or ship a contract that cannot be
  satisfied by its own acceptance tests.
- **建议改法和验证点**: Scope the rule explicitly to the new holdings
  reconciliation/event workflow: event processing never writes; completion or
  correction proposed by this reconciler requires one-record/one-case explicit
  confirmation. State that the existing separately confirmed Futu sync writer
  retains its current authority and must be tested unchanged. Keep post-sync raw
  validation as the safety gate.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-HOLD-EVENT-05-未修复-中-发现回执没有给 missing_completable 的确认命令
- **位置**: Section 9 discovery receipt payload; Sections 8.1 and 11 CLI contract
- **问题类型**: 契约缺失 / 不可直接实施 / 测试缺口
- **当前写法**: Event `missing_completable` creates a pending case and frozen
  confirmation receipt, but the discovery payload promises only exact
  `list/resolve` guidance. Missing-only completion is actually authorized by
  `pm holdings reconcile --record-id ... --apply --confirm`, not `resolve`.
- **反例/失败场景**: The listener correctly detects a blank currency and sends a
  receipt. The renderer follows the frozen payload contract and offers only case
  listing or conflict resolution instructions, leaving the user without the
  command that confirms the proposed completion.
- **为什么有问题**: The requested receipt must require and enable human
  confirmation. A command documented elsewhere is insufficient because the
  renderer is required to use only the frozen payload and not reread mutable
  state.
- **直接证据**: Plan lines 413-445 define the missing-only apply command and
  lines 551-559 define the frozen discovery payload with only `list/resolve`
  guidance; S3 lines 912-915 requires a confirmation receipt but has no renderer
  assertion for the applicable action.
- **影响**: Correctly discovered missing fields become operationally stranded or
  cause implementers to invent inconsistent message actions.
- **建议改法和验证点**: Define action guidance by case kind: `pending_apply`
  includes the exact one-record reconcile/apply/confirm command;
  `pending_confirmation` includes the exact case resolve command and allowed
  decisions; `pending_manual_edit` includes repair and rescan guidance. Freeze
  these values in the payload and add renderer tests for all three states.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### PR-HOLD-EVENT-06-未修复-中-transport-only inbox 仍残留远端写入不确定性的所有权
- **位置**: Section 7.3 `holding_event_inbox`; Sections 8.1 and 10
- **问题类型**: 架构边界 / 状态机漏洞 / 过度耦合
- **当前写法**: The inbox is declared transport-only and the event worker cannot
  call apply/resolve/recover, yet Section 7.3 says a field write reaching
  `apply_outcome_unknown` causes the inbox to record a durable handoff and avoid
  another write.
- **反例/失败场景**: An implementer preserves this legacy clause by coupling inbox
  processing to a reconciliation apply attempt or by adding an inbox outcome for
  a remote write that the event path is now forbidden to initiate. Recovery and
  retry ownership then diverge between event and CLI paths.
- **为什么有问题**: After the confirmed policy change, remote apply uncertainty
  can arise only from an explicitly confirmed reconciliation command. Its case
  and audit event own recovery; the transport inbox neither observes nor hands
  off that write.
- **直接证据**: Plan lines 338-364 call the table transport-only but retain the
  field-write clause; lines 418-423 and 628-654 explicitly prohibit event apply
  and say the worker cannot create a remote apply outcome.
- **影响**: Implementation can reintroduce background write authority, duplicate
  recovery state, or make inbox retry semantics depend on an unreachable state.
- **建议改法和验证点**: Remove the field-write handoff from the inbox contract.
  State that a processed event stores only validation/case/outbox outcome ids;
  CLI apply uncertainty remains exclusively in the semantic case state machine.
  Add a test that no event-processing result contains an apply attempt id or
  remote mutation outcome.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Open Questions

- None. All findings are contract corrections within the confirmed boundary and

## Residual Risks and tracking

- Explicitly confirmed CLI writes still use fresh-read, narrow patch, and
  readback without atomic compare-and-set; keep this in the implementation
  artifact and track future Feishu revision/ETag capability separately.
- App type, publication, event permissions, Base subscription, and singleton
  listener readiness remain later activation-gate checks in deployment docs.
- Formula-only changes and listener outage delay notification; fresh NAV
  preflight remains the correctness backstop.
- Cross-host writers remain outside this same-host work unit and need a separate
  concurrency design if deployment topology changes.

## Conclusion

`fail`

The event write-authority decision is now safe, and the architecture is close
to code-generation-ready. The plan must first narrow its write rule to the new
reconciliation workflow, make every receipt action state-specific and
actionable, and remove the stale remote-write ownership from the transport
inbox. These fixes stay inside the requested boundary.
