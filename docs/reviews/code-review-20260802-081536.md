### DR-S10-01-未修复-高-dry-run 的 planned 状态被上层误判为 snapshot 写入失败
- **入口/函数**: `PortfolioSkill.record_nav()` / `PortfolioService.record_nav()` -> `AccountNavRecorderService.record()` -> `NavRecordService._persist_nav_and_snapshot_locked()`
- **文件(行号)**: `src/app/nav_record_service.py:238-264`; `src/app/account_nav_recorder_service.py:26-39, 279-294`
- **输入场景**: 任一合法官方 NAV 演练，使用默认 `dry_run=True`，normalized valuation、cash-flow dataset 和 snapshot preview 均有效。
- **实际分支**: exact-set dry-run 正确返回 `snapshot_status=planned` 与 `snapshot_persisted=False`；随后 `_snapshot_failure()` 仅因为 `snapshot_persisted is False` 就进入失败分支。
- **预期行为**: planned preview 是成功的演练结果，应返回 `success=True/status=dry_run` 并暴露 mutation preview；只有真实失败或 recovery-required 状态才应成为 failure。
- **实际行为**: 上层把成功 preview 改写为 `success=False/status=failed/error=holdings_snapshot recovery required`。默认 dry-run 的 `record_nav` 以及依赖它的 daily report bundle 因此失败。
- **直接证据**: `_persist_nav_and_snapshot_locked()` 在 dry-run 分支显式构造 planned/false 后正常返回；`_snapshot_failure()` 的第一个条件无视 `snapshot_status=planned`，调用方随后无条件覆盖 success/status/message。现有 S10 tests 只检查 lower-layer preview，没有走真实 application result classification。
- **影响**: 默认安全入口的用户可见回归；无业务写入但所有正常演练被报告为失败，daily bundle 会提前停止。
- **建议改法和验证点**: 把 planned preview 与 failed/partial 状态分开建模；至少让 dry-run 调用跳过 `_snapshot_failure()`，并新增真实 AccountNavRecorder/PortfolioSkill dry-run 回归，断言 preview success、零远端 mutation、无 recovery task。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### DR-S10-02-未修复-高-CLOSED 会把 exact-set partial failure 返回为成功
- **入口/函数**: `close_nav()` -> `AccountNavRecorderService.record_closed()` -> `NavRecordService.record_closed_nav()`
- **文件(行号)**: `src/app/nav_record_service.py:363-418, 888-895`; `src/app/account_nav_recorder_service.py:405-440`
- **输入场景**: 已确认的非 dry-run CLOSED 写入中，NAV 已成功，但 snapshot delete、fresh exact readback、NAV-details patch 或 final readback 失败。
- **实际分支**: lower state machine 捕获异常，把 NAV details 标为 `snapshot_status=failed/snapshot_persisted=False`，记录 durable recovery task，并返回 `nav_record`；`record_closed()` 不检查这些 details，直接构造 `success=True`。
- **预期行为**: CLOSED 与 normal/init 使用同一 completion contract；只要 exact empty remote set 与 complete NAV details 未同时 fresh-read 证实，就必须返回 partial/failed，并包含 task/retry evidence。
- **实际行为**: 调用方收到“已记录清仓净值点”的成功消息，尽管 holdings_snapshot 仍非空或 NAV completion details 未落地。
- **直接证据**: `_persist_nav_and_snapshot_locked()` 的 snapshot exception 分支返回 failed `nav_record` 而不 raise；normal path 调用 `_snapshot_failure()`，CLOSED path at lines 425-440 unconditionally returns success and drops all snapshot evidence.
- **影响**: 外部成功状态与持久化状态不一致，可能把仍需恢复的 CLOSED 终态当作已完成，直接违反 S10 completion signal。
- **建议改法和验证点**: CLOSED 复用同一 snapshot outcome classifier，返回 `status=partial`、task id、retry command 和 snapshot error；新增 delete/readback failure regression，断言 NAV may exist but public success is false and exact recovery remains possible。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### DR-S10-03-未修复-高-账户锁在历史依赖计算之后才获取，串行写仍可持久化 stale NAV
- **入口/函数**: `NavRecordService.record_nav()` and `record_closed_nav()` -> `_persist_nav_and_snapshot()`
- **文件(行号)**: `src/app/nav_record_service.py:179-199, 575-609, 836-845`
- **输入场景**: 同一账户上两个 same-host official writers 并发记录相邻日期，或一个 writer 显式覆盖 while another completes；两者都在首个 writer 持锁前开始计算。
- **实际分支**: 两个请求都先无锁执行 `_load_navs()`、选择 `last_nav`、计算 cash-flow summary、shares/NAV/period metrics 并构造完整 `nav_record`。只有成品进入 `_persist_nav_and_snapshot()` 时才按账户串行。
- **预期行为**: 决定 NAV 的 fresh history facts 与基于它们的计算必须和 NAV+snapshot persistence 处于同一账户临界区，或在持锁后重新 fresh-read/recompute。
- **实际行为**: writer B 等待 A 持久化后仍写入自己在 A 之前计算的 stale record。例如 3/20 与 3/19 并发时，3/20 可漏掉刚写入的 3/19 last NAV，得到错误 shares、NAV、gap flow 与 period bases；锁只保证错误记录按顺序写入。
- **直接证据**: normal history load and all dependent calculations start at lines 575-609, CLOSED equivalent at 836-845; the only new account lock begins inside persistence at lines 191-199. The lock regression asserts only repository actions are under lock and cannot detect stale pre-lock calculation.
- **影响**: 核心 NAV 财务事实可在同主机正常并发下错误持久化，同时 exact snapshot readback仍会成功，造成看似 complete 的错误终态。
- **建议改法和验证点**: 将账户锁 owner 提升到 history fresh-read/calculation through exact-set completion，避免不可重入的二次加锁；或持锁后强制重读并重算。新增 deterministic two-writer regression：第二个 writer 必须观察第一个 writer 的 NAV，normal 与 CLOSED 均覆盖。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-S10-04-未修复-高-exact-set 生成的合法 null clear 会被唯一 registry 拒绝
- **入口/函数**: `SnapshotService.apply_exact_set()` -> `SnapshotsRepository.apply_holding_snapshot_actions()` -> Feishu batch update validation
- **文件(行号)**: `src/feishu/repositories/snapshots_repository.py:84-96, 119-135`; `src/feishu/contracts/registry.py:148-162, 388-402`
- **输入场景**: 远端 snapshot 的 optional `asset_name` 或 `avg_cost` 有旧值，而本次 normalized target 将其变为 `None`；这在成本信息撤销或名称证据缺失时是合法 exact target。
- **实际分支**: repository 正确检测差异并用 `preserve_none=True` 发送显式 clear；S1 registry 只把 `remark` 标为 clearable，因此 Feishu client 在 transport 前抛出 `fields cannot be cleared`。
- **预期行为**: exact-set 可清除其拥有的所有 optional target fields，registry 与 domain target semantics 必须是同一个真源契约。
- **实际行为**: NAV 已写入后 snapshot action 永久失败；相同 compensation retry 会重复构造同一个被 registry 拒绝的 update，无法自动收敛。
- **直接证据**: `_changed_fields()` includes every changed persisted field and `_to_feishu_fields(... preserve_none=True)` retains null; `_SNAPSHOT_FIELDS` marks `asset_name`, `avg_cost`, and `source` optional but nonclearable. Direct contract reproduction raises `ValueError: fields cannot be cleared: asset_name`. The only repository test clears `remark`, so it misses the mismatch.
- **影响**: 真实 optional-field transition makes every new snapshot finality partial and unrecoverable until source/schema contract is changed.
- **建议改法和验证点**: 在 typed registry 中明确 all system-owned optional snapshot fields 的 clearability（至少 `asset_name`、`avg_cost`，并裁定 `source`），然后让 actual client validator participate in repository regressions for each value-to-null transition。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### DR-S10-05-未修复-高-compensation 只比对 binding marker 就整对象覆盖 NAV details
- **入口/函数**: `CompensationService.retry()` -> `_apply_snapshot_target()` -> `_snapshot_nav_binding_matches()`
- **文件(行号)**: `src/app/snapshot_service.py:109-166`; `src/app/compensation_service.py:485-550, 575-596`; original path also `src/app/nav_record_service.py:363-386`
- **输入场景**: durable task 未解决期间，fresh NAV 的 non-binding details（例如 finality、cash_flow_basis、valuation_quality 或 maintenance provenance）被合法维护或外部编辑改变，但原 snapshot run/target/plan/bound-authority markers仍在。
- **实际分支**: matcher 只检查 run id 与四个 snapshot markers，于是把 remote NAV 当作目标行；snapshot exact set 完成后，recovery 用旧 `complete_nav_details` 整对象 patch，覆盖所有后来的 non-binding details。prepared target 本身也没有校验 planned/complete details digest 或 typed semantic invariants。
- **预期行为**: recovery 只能从一个完整受绑定的 NAV before/failed state推进；base details drift 应成为 zero-write state conflict，或 patch 只能修改 snapshot-owned fields without clobbering other owners。
- **实际行为**: snapshot row recovery可以静默回滚或破坏 NAV 的其他真实字段，然后 final readback因为与旧 payload 相等而错误标记 resolved。Original path同样在 snapshot网络操作后直接 full-details patch，没有 pre-patch fresh base comparison。
- **直接证据**: recovery target stores raw `planned_nav_details` and `complete_nav_details` but `parse_recovery_target()` validates neither; `_snapshot_nav_binding_matches()` lines 590-596 ignores every non-marker field; lines 541-548 patches and verifies the entire stale object.
- **影响**: 恢复流程可能造成 NAV audit/finality/cash-flow evidence data loss，并把该覆盖作为成功终态持久化。
- **建议改法和验证点**: 定义 digest-covered snapshot recovery NAV transition contract，验证 current details 属于完整 allowed before/failed/complete states；优先以 snapshot-owned patch merge到 freshly validated current base。新增 non-binding drift regression，断言 conflict、zero snapshot/NAV mutation，并覆盖 original pre-patch drift。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-S10-06-未修复-中-NAV overwrite flag 与 bound authority 的 overwrite scope 可分叉
- **入口/函数**: public `PortfolioManager.record_nav()` / `record_closed_nav()` -> `NavRecordService._persist_nav_and_snapshot_locked()`
- **文件(行号)**: `src/app/nav_record_service.py:179-233, 688-708`; `src/domain/snapshot_contracts.py:519-562`; `src/portfolio.py:243-276, 297-322`
- **输入场景**: 直接 caller 传 `overwrite_existing=True`，但传入 scope/digest 正确且 `overwrite_existing=False` 的 confirmed `SnapshotWriteAuthority`；目标日期已有 NAV row、snapshot slice 为空。
- **实际分支**: authority bind 只在 `plan.before` 非空时检查自己的 overwrite flag，所以空 snapshot slice 会通过；NAV preview/actual write消费独立函数参数 `overwrite_existing=True` 并覆盖同日 NAV。
- **预期行为**: 一个 bound top-level authority 应唯一决定该 account/date cross-table overwrite scope；任何 flag mismatch 都应在 preview和durable prepare前失败且零 mutation。
- **实际行为**: caller 可用未授权 snapshot authority 搭配另一个布尔值完成 NAV overwrite；durable evidence随后声称 `overwrite_existing=False`，与真实副作用矛盾。
- **直接证据**: authority digest covers its own flag, but `_persist_nav_and_snapshot_locked()` neither compares it to the method parameter nor checks existing NAV against it; lines 229-233 pass the independent parameter to the repository. Official top-level callers happen to duplicate the same value, but the public manager boundary does not enforce that invariant.
- **影响**: 直接/未来 caller 可绕过 cross-table overwrite authority，且 audit evidence不能证明真实覆盖权限。
- **建议改法和验证点**: 在任何 plan/read/write前强制 authority overwrite scope等于 effective NAV overwrite intent，并校验 issuer/run context consistency；新增 mismatch both directions、existing NAV with empty snapshot、zero-write regressions。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Residual Risk
