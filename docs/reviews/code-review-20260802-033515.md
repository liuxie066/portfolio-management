## Findings

### 1-未修复-高-写后未收敛或出现重复时 apply 仍返回 success=true，CLI 可用成功退出码结束

- **入口/函数**: `CashFlowRepository.reconcile_cash_flows()` → `_public_cash_flow_reconcile_result()` → `pm cash-flow reconcile --apply --confirm`
- **文件(行号)**: `src/feishu/repositories/cash_flow_repository.py:531-570,949-978`; `scripts/pm.py:53-63,740-822`
- **输入场景**: 飞书接受 batch update，但 fresh readback 仍返回旧 generated fields；或写入和 readback 之间新增了一条 canonical expected-dedup 相同的记录；或目标记录在 readback 中消失。
- **实际分支**: readback row 会正确保持 `pending/error` 且 `readback_verified=false`，但 `_public_cash_flow_reconcile_result()` 无条件返回 `success=True`。非人工 FX 的 CLI 分支直接返回该 payload，`pm.main()` 因而退出 0。
- **预期行为**: apply 只有在 fresh readback 中所有目标行都是唯一、完整、无待写 patch 的 `CompletedCashFlowFacts` 时才成功；否则应返回稳定失败状态和非零 CLI 退出码，同时保留 `updated_count` 与部分写证据。
- **实际行为**: 操作者或自动化可把“远端发生写入但没有完成证明”误判为成功；这直接违背 S5 的 optional write → fresh readback → completed validation completion signal。
- **直接证据**: `_public_cash_flow_reconcile_result()` 第 963 行固定写入 `"success": True`，而同一返回体第 973-975 行已经能计算 `readback_verified=false`；现有兼容测试的 stale mock readback 也没有断言失败。
- **建议改法和验证点**: 区分 dry-run transport success 与 apply completion success；exact-record 缺失、任一 error/pending、post-write duplicate 或 fingerprint 未观察到时 apply 返回 `success=false` 和稳定 reason code。新增 stale readback 与 post-write duplicate 的非零结果测试；保留空 account-scope 的合法 no-op。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-高-batch update 抛错时跳过缓存失效和 fresh readback，部分远端写入后仍可继续消费旧聚合

- **入口/函数**: `CashFlowRepository.reconcile_cash_flows()` → `client.batch_update_records()` → `_invalidate_cash_flow_agg_cache()`
- **文件(行号)**: `src/feishu/repositories/cash_flow_repository.py:516-530`
- **输入场景**: 飞书或网络在 batch 请求中途超时：服务端可能已经接受一个或多个更新，但 SDK/HTTP 客户端向调用方抛出异常。
- **实际分支**: `batch_update_records()` 在第 519 行抛出后，控制流不会到达第 524 行的 cache invalidation，也不会执行第 531 行后的 fresh readback。
- **预期行为**: 一旦发出可能改变远端的请求，相关 account 聚合缓存必须立即失效；异常应显式标记 `partial_write_possible`，不能继续保留旧缓存权威。无法取得 readback 时保持失败并要求 fresh retry/audit。
- **实际行为**: 远端事实可能已改变，本机 memory/local aggregate cache 却仍被标记为已加载；后续读取可能继续返回旧现金流累计。
- **直接证据**: cache invalidation 位于 batch 调用正常返回之后，且当前异常分支没有 `finally` 或写尝试标记。现有测试只覆盖正常返回计数，不覆盖 timeout-after-accept。
- **建议改法和验证点**: 在发起非空 batch 前保存 affected accounts，并在调用的 `finally` 中无条件失效缓存；捕获异常后返回/抛出包含 `partial_write_possible=true` 的稳定错误，不伪造 updated count。新增 client 抛错断言：cache 被清空、没有 confirmation、结果不宣告完成。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### 3-未修复-中-可追溯 rate_source 没有 canonical validator，unknown/n-a 等含糊证据可被写入并通过 gate

- **入口/函数**: `_validate_manual_cash_flow_fx_evidence()` → CLI confirmation write → `evaluate_cash_flow_fx_confirmation()`
- **文件(行号)**: `src/feishu/repositories/cash_flow_repository.py:865-904`; `src/app/cash_flow_fx_confirmation.py:88-106`; `scripts/pm.py:740-818`
- **输入场景**: 用户执行 manual FX apply，提供 `--rate-source unknown`、`n/a` 或 `-`；rate/date/amount 其余字段合法。
- **实际分支**: repository 只拒绝空字符串和精确的 `manual`；confirmation evaluator 只检查 source 非空。因此这些含糊字符串会在 readback 后进入本地 confirmation，并被后续 FX gate 接受。
- **预期行为**: “可追溯来源”应由一个共享定义校验；明显 placeholder 不得写 confirmation，也不得通过 evaluator。provider/manual-supplement 两条入口应使用同一规则。
- **实际行为**: source 字段存在但没有调查价值，无法证明 flow_date 对应汇率来自哪里；这弱化了本切片要求的 fully evidenced 条件。
- **直接证据**: repository 条件是 `not resolved_source or resolved_source.lower() == "manual"`；evaluator 条件是 `not source`。两处定义不同且都接受 `unknown`/`n/a`/`-`。
- **建议改法和验证点**: 在 cash-flow domain 建立唯一 `normalize/require_traceable_rate_source`，至少拒绝 blank、manual、unknown、n/a、na、none、null、`-` 等 placeholder；repository 和 evaluator 复用。新增 apply 零写入/零 confirmation 与 evaluator stale 测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Residual Risk

- Feishu 不提供 compare-and-swap；initial scan 与 batch write 之间的外部编辑只能由 fresh readback 检出，不能原子阻止。
- `OperationStateStore.source_hash` 保留旧列名承载 generated-field fingerprint；公共 evaluator 暂时接受 row/confirmation 的 `source_hash` 兼容别名。真实 S5 repository 始终产生 `generated_fingerprint`，后续 S6 dataset 接管 NAV gate 时应移除仅靠旧别名通过的可能性。
- duplicate audit 是只读阻断，不删除、合并或自动选择记录。
