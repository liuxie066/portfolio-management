### DR-S2-01-未修复-高-`replace_holding(Holding)` 仍会静默忽略显式 null/空 tag clear

- **入口/函数**: `replace_holding()` → `_legacy_replace_target()`
- **文件(行号)**: `src/feishu/repositories/holdings_repository.py:771-809`
- **输入场景**: 调用者仍使用对外保留的 `Holding` 兼容入口，且在 Pydantic `model_fields_set` 中明确携带 `avg_cost=None` / `asset_class=None` / `industry=None` 或 `tag=[]`，目标是清空远端旧值。
- **实际分支**: 代码已计算 `explicit_holding_owned_fields(holding)`，但 nullable 字段只在值“不是 None”时加入 `owned`，`tag` 只在列表 truthy 时加入。因此明确 null/空列表与未提供被再次压成同一状态。
- **预期行为**: 未提供字段不修改；由 `model_fields_set` 证明的显式 None 应对三个授权 nullable 字段发送 null，显式 `tag=[]` 应清空 tag。
- **实际行为**: 这些字段不进入 payload 和写后 owned-field 比对；只要其他 owned 字段读回成功，方法就返回成功，远端旧成本/分类/tag 保留。
- **直接证据**: `explicit` 已能区分“未提供”和“显式提供”，但 `if optional_field in explicit and getattr(...) is not None` 与 `if 'tag' in explicit and holding.tag` 丢掉了两种显式 clear 状态；现有 clear 回归只覆盖 bulk 路径。
- **影响**: 原审计 F05 在仍公开的单条 replace 兼容入口上未闭环，调用者会获得虚假的 absolute-target 成功语义。
- **建议改法和验证点**: 对 `avg_cost/asset_class/industry` 以“是否在 `explicit`”决定所有权，保留显式 None；对 `tag` 以显式携带决定所有权，允许 `[]`。新增“显式 clear 发送 null/`[]` 且 fresh readback 为空”与“省略默认不 clear”对照测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### DR-S2-02-未修复-中-`HOLDING_ZERO_DELETE` 补偿可删除同业务键下的新记录

- **入口/函数**: `CompensationService.retry()` → `_apply_holding_target()` 的 `HOLDING_ZERO_DELETE` 分支
- **文件(行号)**: `src/app/compensation_service.py:336-349,359-413`
- **输入场景**: 任务记录时的零持仓是 `record_id=rec-old`；重试前该行已被删除，另一写入者在相同 `(asset_id, account, broker)` 下创建了新的零数量行 `record_id=rec-new`。
- **实际分支**: target 因携带可解析 `HoldingTarget` 而被标记 supported；重试 fresh read 得到 `rec-new`，只要 `quantity` 接近零就直接调用 `delete_holding_if_zero()`。
- **预期行为**: 删除必须绑定任务中的 `base_record_id` 和 fresh base digest；记录身份或 base 状态变化时应转为 state conflict，不得扩大删除授权。
- **实际行为**: `rec-new` 被删除，任务可继续标记 RESOLVED。
- **直接证据**: 分支已解析 `mutation`，却在删除前完全不比较 `mutation.base_record_id` / `mutation.base_digest` / `before`；它仅检查当前 quantity。
- **影响**: 补偿重试可删除不属于原始任务的新数据。当前生产代码没有新建该 target type 的路径，但公开 `record()`/retry 协议仍宣告它 supported，且该分支正在本切片中修改。
- **建议改法和验证点**: 删除前先要求 current 与 recorded `before` 匹配，并且 record ID 与 digest 等于 mutation base；不等则 `CompensationStateConflict`。覆盖“原行已消失”为 already applied、“同键新 record ID”为 conflict 且零 delete 调用。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### DR-S2-03-未修复-中-修复 patch 写成功后的 proof 异常会留下已知过期缓存

- **入口/函数**: `patch_holding_record()`
- **文件(行号)**: `src/feishu/repositories/holdings_repository.py:471-548`
- **输入场景**: 账户缓存已预载；reconciliation patch 的 `update_record` 成功，单行 readback 也匹配，但随后完整账户切片读取/转换因超时或另一条非法行失败。
- **实际分支**: 只有 transport update 抛异常和单行值 mismatch 两个分支会 invalidate account cache；`get_raw_holdings()` 异常、不完整 readback shape，以及 `_read_fresh_holding_account_slice()` / publish 异常都直接逸出。
- **预期行为**: 一旦 remote update 已尝试，任何无法形成完整 fresh proof 的路径都应失效该账户缓存；只有完整读回才可发布新切片。
- **实际行为**: 方法抛错，但 memory/persistent cache 仍可返回 patch 前旧值；后续非官方 exact read 可继续看到已知与远端不同的状态。
- **直接证据**: `records = get_raw_holdings(...)` 和 `fresh = _read_fresh_holding_account_slice(...)` 不在 post-write `try/except` 中，而方法进入时也没有先失效旧 cache。
- **影响**: 远端修复结果和本地读模型分叉，故障恢复/重试期间的证据变得更难判断。
- **建议改法和验证点**: 将 update 之后的所有 readback + full-slice publish 放入统一 proof `try`；任何异常都 flush 失效 account cache 后原样抛出。测试 update 已改变 fake remote、full-slice read 失败时旧 cache 被清除。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
