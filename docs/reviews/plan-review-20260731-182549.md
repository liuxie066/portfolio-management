## Reviewed goal and boundaries

The plan makes a newly added holdings row observable before it can influence an
official NAV. It separates raw Feishu facts from typed models/cache defaults,
allows only evidence-backed missing-field completion, persists populated-field
conflicts for explicit human resolution, and passes the exact validated
holdings snapshot into valuation.

The first phase intentionally excludes batch correction, HTTP mutation,
interactive callbacks, a general security master, a new proactive scheduler,
and cross-host locking. Every business-data mutation remains single-record or
single-case and explicitly confirmed.

- Tested that the pure validator consumes an injected evidence bundle rather

### Best-practice review

- Tested raw missing-versus-zero semantics, finite Decimal canonicalization,
  stable authority identity, evidence-instance identity, narrow confirmation
  scope, idempotency, readback, lock order, and field-level partial outcomes.
- Tested explicit remote-attempt markers, stale-applying recovery, remote

- Tested durable receipt claim-versus-send states, deterministic key collision,

- Tested additive feature-schema initialization and an honest rollback boundary

The existing project already uses absolute targets, fresh readback, explicit
confirmation, and durable receipt leasing in adjacent cash-flow/NAV workflows;
the plan reuses their safety properties without treating those implementations
as interchangeable domain state.

### Optimal-solution review

- A raw analyzer plus single-record confirmed patch is safer and smaller than a
  background auto-fixer.
- Using `asset_type` to select a versioned resolver is practical, while the plan
  correctly refuses to treat HK market identity alone as trading currency and
  leaves generic unsupported instruments manual.
- A separate additive typed operation outbox is lower-risk than migrating or
  renaming the live NAV outbox, and explicit dispatch fan-out preserves current
  NAV behavior.
- Passing a frozen holdings snapshot through the existing valuation holdings
  parameter is smaller than redesigning pricing or the portfolio model.

### Overengineering review

- Durable cases/events are justified because confirmation and recovery cross
  process lifetimes and Feishu/SQLite cannot commit atomically.
- The three hash concepts are independently necessary for semantic dedupe,
  observation audit, and authorization invalidation.
- The plan avoids unsupported non-Futu metadata integration, grouped
  interactive cards, batch apply, a workflow engine, and a new scheduler.
- `ValidatedHoldingsSnapshot` is a narrow internal handoff, not a new public
  domain model.

### Overcoupling review

- Repository, evidence acquisition, pure validation, workflow persistence,
  delivery, CLI, NAV orchestration, and valuation have one-way contracts.
- Receipt renderers consume frozen payloads and do not reread holdings.
- Futu sync retains write ownership; the reconciler consumes observations or
  post-sync Feishu rows.
- Account-then-record lock order aligns confirmation with existing account
  writers and avoids a record-lock/account-lock cycle.
- NAV consumes private copies of one validated persistent-field snapshot rather
  than coupling validation success to a later repository read.

### State-machine and recovery review

- Tested direct apply without prior notification materialization, multiple
  missing fields in one Feishu patch, mixed readback, crash before versus after
  durable remote-attempt start, timeout with actual success, manual reversion to
  the before value, double confirmation, source drift, and restart recovery.
- Tested manual edit resolution, scope-preserving `keep-current`, policy/value
  supersession, nonblocking descriptor cases, and blocking financial cases.
- Tested one missing-account row against multiple target accounts and an
  already-final NAV that should remain idempotently skipped.

### Validation and implementation-slice review

- S1 establishes raw facts, resolver policy, strict conversion, and cache v2
  before any workflow or NAV integration depends on them.
- S2 adds durable cases, confirmed writes/recovery, and delivery before S3 can
  materialize cases from an official NAV run.
- S3 owns orchestration order and frozen snapshot consumption after the lower
  contracts exist.
- Focused tests cover the main failure branches, and the aggregate gate retains
  full pytest plus compile validation. No live mutation is required for test
  acceptance.

## Residual Risks and suggested tracking

- **External Feishu write race**: the current client has no atomic conditional
  update. The plan fails closed on readback mismatch/unknown and records the
  consumed NAV snapshot, but cannot prove no external same-field write occurred
  between pre-read and patch. Track an ETag/revision work item only if Feishu
  exposes that capability.
- **Unsupported/special currency coverage**: non-Futu HK counters and generic
  funds/bonds/crypto may remain manual. This is an intentional correctness-over-
  coverage tradeoff; track new authority adapters as separate evidence-backed
  work units.
- **Operator authentication**: local CLI audit context remains
  `trusted_identity=false`. Authenticated Feishu callbacks or OS-level
  multi-user authorization are a later security work unit.
- **Rollback enforcement**: an older binary preserves additive tables but does
  not enforce holdings cases. A future rollback must disable official NAV
  writers until a compatible binary is restored; this belongs in the separately
  authorized release/upgrade runbook.
- **Discovery latency and message volume**: there is no new scan timer and the
  first phase sends one receipt per case. Track proactive cadence/grouping only
  after observing real operator noise and latency.
- **Cross-host concurrency**: account/record locks are same-host only. Revisit
  if PM gains multiple concurrent writer hosts.
