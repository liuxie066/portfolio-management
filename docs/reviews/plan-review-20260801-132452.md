## Assumptions tested

- The Feishu writer and schema genuinely define `tag` as JSON text.
- The raw preflight must preserve source values rather than normalize them in
  storage.
- JSON text acceptance can be added without changing workflow case identity.
- Typed holding construction can consume exactly the validator's normalized
  value.
- One production-module slice is sufficient.
- No schema migration, repository change, or general JSON codec is required.

## Findings

### PR-01-未修复-高-共享 normalizer 会改变缺失 tag 的 record digest 和 durable case identity

- **位置**: `Strict tag normalization`, `Digest and typed-holding consistency`,
  and S1 steps 1-2.
- **问题类型**: 契约缺失 / 状态机漏洞 / 测试缺口 / 过度耦合
- **当前写法**: Plan proposes one helper that normalizes `None`, `""`, native
  `[]`, and text `"[]"` to a valid empty list, then reuses that helper in
  `canonical_record_payload()`.
- **反例/失败场景**: A row with a missing `tag=None` currently canonicalizes to
  JSON `null`; a native or text empty array canonicalizes to `[]`. Reusing the
  proposed helper would canonicalize the missing value to `[]`, changing the
  row's `record_digest` even though no source fact changed.
- **为什么有问题**: `record_digest` participates in holding case identity,
  precondition checks, supersede/closure decisions, and confirmation validity.
  A warning-only parser repair could therefore reopen or supersede unrelated
  durable cases for rows whose tag remains missing.
- **直接证据**: Current `canonical_record_payload()` parses JSON text lists but
  sends non-list values through `_text()`, so `None` remains `None`, `""`
  becomes `None`, and `[]`/`"[]"` remain `[]`. The plan's helper contract erases
  that distinction. The existing digest-equivalence test only compares native
  and text nonempty arrays, so it would not detect the broader missing-value
  identity change.
- **影响**: Unrelated workflow case churn, stale manual-confirmation evidence,
  unexpected case lifecycle receipts, and a repair whose state impact exceeds
  the user-approved scope.
- **建议改法和验证点**: Leave `canonical_record_payload()` unchanged because it
  already canonicalizes native and JSON-text arrays correctly. Decode JSON text
  only in `_optional_tag()`, put the normalized list in `FieldOutcome.current`,
  and consume that outcome in `to_holding()`. Add a regression asserting
  canonical tag output remains `None` for missing/blank values and `[]` for
  native/text empty arrays.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

## Special review lenses

- **Architecture boundary**: Validation remains the right owner; changing raw
  Feishu reads or repository serialization would cross the transport boundary.
- **Best practice**: Strict decode plus negative-shape tests is appropriate,
  but digest stability needs an explicit regression.
- **Optimal solution**: Updating `_optional_tag()` and `to_holding()` is smaller
  and safer than sharing a helper with the already-correct digest path.
- **Overengineering**: A general JSON codec or schema migration has no evidence
  basis and remains correctly excluded.
- **Overcoupling**: Coupling parser normalization to workflow identity is the
  material defect captured in PR-01.

## Open questions

- None. PR-01 has a local, code-generation-ready correction.

## Residual risks

- Stale production cases remain owned by the existing formal-preflight
  lifecycle: `outside implementation; already classified in the plan`.
- Production behavior remains unchanged until a separately authorized release
  and upgrade: `operator-owned deployment boundary`.

## Review conclusion

`fail`. The goal and validation ownership are sound, but the plan must remove
digest canonicalization from the implementation scope and add an explicit
missing-value digest stability regression before implementation.
