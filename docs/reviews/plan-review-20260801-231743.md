## Findings

### PRR2-01-未修复-高-backfill 仍可在无历史估值快照时直接创建/替换 NAV，和 v2 exact-set 契约冲突
- **位置**: S8 Exact changes 6-9、Non-goals；S10 Exact changes 10；direct NAV writer inventory
- **问题类型**: 数据损坏 / 架构边界 / 状态机漏洞 / 契约缺失 / 不可直接实施
- **当前写法**: S8 要求 backfill 使用同一 mapping/invariants 和 fresh cash-flow dataset，但仍保留 backfill/repair 生产路径；S10 说只有新/rewrite 行需要 v2，同时又把历史 exact-set rewrite 列为 non-goal。
- **反例/失败场景**: backfill 输入只含 NAV 汇总值，可能缺 cash/stock/fund/region。当前代码会默认补值、构造 holdings 为空的 `PortfolioValuation`，之后直接 `write_nav_records(mode=replace|upsert)`。即使 S8 修正基金双计数，它仍没有目标日期 holdings、unit prices 或 normalized snapshot，无法创建 v2 holdings_snapshot，也无法证明重写后的历史 NAV 与任何 snapshot 一致。
- **为什么有问题**: 对既有 legacy 行的派生字段修补与创建/替换历史基准事实是两种权限和证据等级。当前计划混在 backfill 一条路径里，并且 S10 明确不做历史 exact-set，实施者无法同时满足两边。
- **直接证据**: `src/maintenance/nav_history_repair/backfill.py:74-105` 接受不完整 JSON；`:130-157` 缺分解时默认全现金并构造空 holdings valuation；`:223-257` 在计算后覆盖基准字段；`:286-292` 直接 bulk replace/upsert。S10 计划同时声明 new/rewrite 需要 v2 和 no historical exact-set rewrite。
- **影响**: 历史 NAV 可在没有日期绑定估值证据时被创建/替换，legacy/v2 finality 被错误升级或彼此矛盾；“每个计算唯一真源”和 snapshot replay 无法验收。
- **建议改法和验证点**: 本 work unit 将 maintenance 收窄为唯一既有行的 derived/details field patch：fresh full read，基准字段只读，输入差异即 blocker；missing date/upsert-create/replace base fields 在 apply 前 fail closed，提示需要单独授权的 historical reconstruction bundle/work unit。patch/backfill/rollback 均调用 field-level patch API，不再调用 full `write_nav_record(s)`；保留 `evidence_version=legacy`，不能设置 v2 complete。测试覆盖 missing row、base drift、duplicate date 均零写，derived-only apply/readback/rollback 保留全部非目标字段和 legacy evidence。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高
