## Findings

### DR-S2-RR4-01-未修复-中-cash-flow 与 compensation 用完整快照而不是 owned fields 判定完成

- **入口/函数**: `CashFlowEffectService._confirm_under_locks()` / `_finalize_compensation_if_resolved()`; `CompensationService._apply_holding_target()`
- **文件(行号)**: `src/app/cash_flow_effect_service.py:1617-1702,1835-1860`; `src/app/compensation_service.py:367-438`
- **输入场景**: 一个已有 CASH 行的 target 只 own `quantity`；数量 target 已达成，但人工在预览后修改了 `tag` 或其他未授权 metadata。
- **实际分支**: repository 正确地只按 `owned_fields` 证明 quantity，但上层随后用 `serialize_holding(readback) == target_data` 比较整行。compensation 的 already-applied 判定也要求整行等于旧 target。
- **预期行为**: 已验证的 mutation object 是完成语义唯一真源；identity 一致且所有 `owned_fields` 匹配即可完成，未 owned 的并发人工值必须保留。
- **实际行为**: 已成功的 quantity 写入可被误报为 `compensation_pending` / `state_conflict`，且确认路径在构造 target 时可因新 manual metadata 与旧完整 target 不同而拒绝。
- **直接证据**: repository `_prove_holding_targets_and_publish()` 已使用 `holding_owned_fields_match()`；三个上层完成分支却重新序列化并比较 11 个业务字段，从而建立了第二套更宽的完成定义。
- **影响**: 可恢复的成功写入会长期留在失败/补偿态，同时将人工 metadata 编辑误当成资金 target 失败，违反 S2 的字段所有权与完成信号。
- **建议改法和验证点**: 现有行的 cash target 从最后 fresh base carry forward 未 owned 字段；confirm、compensation already-applied/readback 和 compensation finalization 全部复用 `holding_owned_fields_match()`。故障注入 tag 并发变更，断言 quantity 成功、tag 保留、无多余写入且补偿可 resolved。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### DR-S2-RR4-02-未修复-中-确认的 raw holdings repair 在写边界重绑新 base

- **入口/函数**: `HoldingsWorkflowService._execute_patch()` → `HoldingsRepository.patch_holding_record()`
- **文件(行号)**: `src/app/holdings_workflow_service.py:758-821`; `src/feishu/repositories/holdings_repository.py:481-556`; `src/feishu/_holdings_mixin.py:90-99`
- **输入场景**: 操作者根据 raw record digest A 确认将 `currency` 改为 `USD`；在 case 准备后，外部编辑将同一 record 的 `currency` 改为 `HKD`。
- **实际分支**: workflow 只向 repository 传 `record_id + fields`。repository 虽然立即 fresh-read 了当前行，却没有收到/比较操作者确认的 digest A；它把 HKD 行当成新 base 并覆盖为 USD。
- **预期行为**: 无法转成 typed `Holding` 的历史异常行需要独立但唯一的 raw-repair mutation contract，其携带 record ID、完整 identity、确认时 base digest 和显式 fields；不一致必须在 transport 前失败。
- **实际行为**: 这个修复入口继续使用未绑定 base 的字典，绕过 `HoldingPatch`/`HoldingTarget` 的主要 CAS 不变式。same-host lock 不能阻止飞书人工编辑。
- **直接证据**: workflow 已持久化 `validation.record_digest` 和 `case_precondition_digest`，但 line 817 调用丢弃了该事实；repository line 494 的新鲜行只用于推导 identity，没有与任何 expected base 比较。
- **影响**: 已确认的历史修复可静默覆盖确认后的人工修正，并且保留了 holdings 写入的第二套权威边界。
- **建议改法和验证点**: 定义 immutable `HoldingRepairPatch`，从操作者看到的 `RawHoldingRecord` 与显式 target fields 构造，并携带 raw base digest。workflow 传该对象；repository 在任何 update 前 fresh-read 并校验 record/identity/digest。注入同 record ID 字段变更，断言 `HoldingMutationConflictError`、零 update 和两层 cache 失效。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中
