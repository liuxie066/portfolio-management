## Assumptions tested

- A single file-level long connection can safely fan out holdings and cash-flow
  table events without weakening exact-target validation.
- A separately durable cash-flow inbox can recover remote-write/local-commit
  splits through fresh idempotent reconciliation.
- CNY fields are deterministic and confirmed foreign rows can be classified
  using the same FX confirmation authority as NAV.
- A semantic receipt key can suppress event-redelivery noise without hiding a
  material user edit.
- The proposed retry lifecycle eventually produces an operator-visible outcome
  rather than remaining invisible forever.
- Additive schema and CLI changes can preserve the existing holdings listener.

## Findings

### PR-01-未修复-高-方案承诺重试耗尽后发回执，但状态机没有耗尽或人工介入终态

- **位置**: `Event states`, `Record outcomes`, S2 error handling, and receipt
  coverage
- **问题类型**: 状态机漏洞 / 并发恢复风险 / 不可直接实施
- **当前写法**: Transient exceptions advance `failed_retryable`; receipt coverage
  includes a write outcome requiring attention "after retry policy is
  exhausted". The listed state machine contains only `pending`, `claimed`,
  `failed_retryable`, and `processed`.
- **反例/失败场景**: Feishu patch or readback fails persistently because a
  credential, schema, or permission problem is not transient. The inherited
  holdings retry implementation caps the delay at 60 minutes but increments
  attempts indefinitely; no branch makes the promised attention receipt.
- **为什么有问题**: The listener can silently retry forever while NAV remains
  blocked. An implementer must invent an attempt limit, terminal state, receipt
  content, and manual recovery path, so the plan is not code-generation-ready.
- **直接证据**: `OperationStateStore.mark_holding_event_failed()` computes
  `retry_index = min(attempt - 1, len(_RETRY_MINUTES) - 1)` and always returns
  the row to `failed_retryable`; the proposed cash-flow state list copies those
  states but the plan separately promises an exhausted-retry receipt.
- **影响**: Permanent listener failures remain hidden, retry traffic continues
  indefinitely, and the user's no-manual-memory objective is not met.
- **建议改法和验证点**: Specify an exact retry budget and terminal transition.
  On the final failed attempt, atomically enqueue a semantic attention receipt
  and mark the event `processed` with `attention_required`; document the
  recovery command. Test the attempt immediately before and at the limit,
  receipt deduplication, lease expiry, and no subsequent automatic claim.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-组合监听缺少配置目标唯一性校验，同一表可被两个业务处理器同时接收

- **位置**: Architecture decision 1, S3 fan-out, listener status/startup
- **问题类型**: 架构边界 / 契约缺失 / 测试缺口
- **当前写法**: Each acceptor independently validates its configured target and
  the plan assumes exactly one accepts a known table.
- **反例/失败场景**: `feishu.tables.holdings` and
  `feishu.tables.cash_flow` are accidentally configured to the same
  `app_token/table_id`. Both exact validators accept one event into independent
  inboxes. The holdings handler interprets a cash-flow record as a holding and
  the cash-flow handler may attempt generated-field writes against the configured
  cash-flow repository target.
- **为什么有问题**: "Exactly one accepts" is an unproven configuration
  assumption. `config.get_feishu_table_ref()` validates syntax and token
  presence but does not enforce cross-table uniqueness.
- **直接证据**: The current target classes compare app ID, event type, file
  token, file type, and table ID. Two target objects with the same values both
  pass. The proposed fan-out deliberately invokes both acceptors.
- **影响**: Wrong-domain classification, misleading receipts, or financial-field
  writes can occur under one plausible configuration error.
- **建议改法和验证点**: Add a startup/status preflight that requires distinct
  `(app_id, file_token, table_id)` targets and refuses `listen` or `subscribe`
  on collision. Unit-test same-table collision, same token/different table, and
  different token/same table ID.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-03-未修复-中-语义回执指纹未定义正规化输入，无关系统字段变化可导致重复通知

- **位置**: Architecture decision 5 and S2 receipt tests
- **问题类型**: 契约缺失 / 最佳实践偏离 / 测试缺口
- **当前写法**: Receipt keys use record ID, "current record/error digest",
  and reason code instead of event ID.
- **反例/失败场景**: An invalid row is unchanged in the manual fields, but
  Feishu updates `updated_at` or a generated field. If the digest covers the
  repository error row or all projected fields, a new digest and new receipt
  are created for the same unresolved operator action. Conversely, an
  underspecified digest might ignore a meaningful manual-field edit.
- **为什么有问题**: The current repository error row may include parsed fields and
  projection metadata. Without an explicit canonical field set and
  normalization, the implementer must invent notification identity and tests
  cannot prove noise suppression.
- **直接证据**: `CASH_FLOW_RECONCILE_FIELDS` includes generated fields and
  `updated_at`; parse-error results expose a `fields` dictionary. The plan does
  not state which values enter the digest.
- **影响**: Receipt storms or, in the opposite direction, failure to notify after
  a materially different user edit.
- **建议改法和验证点**: Define the receipt issue fingerprint as canonical
  `record_id + reason_code + normalized manual inputs
  (flow_date/account/broker/amount/currency)` plus FX evidence identity when the
  reason is FX-specific. Explicitly exclude `updated_at`, generated fields,
  event ID, revision, and delivery time. Test unchanged redelivery, generated-
  field-only edits, each manual-field edit, and changed FX confirmation.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Architecture boundary review

The plan correctly keeps SDK payloads as triggers, generated-field formulas in
the repository, FX evidence in local operation state, and CASH holding effects
in their existing service. The target-collision assumption in PR-02 is the
material boundary failure that must be closed before implementation.

## Best-practice review

Durable acceptance, leased workers, fresh reads, idempotent convergence, and
asynchronous outbox delivery match project-local patterns. PR-01 prevents the
failure lifecycle from being operationally complete, and PR-03 leaves durable
notification identity underspecified.

## Optimal-solution review

One shared SDK connection plus separate domain inboxes/handlers is a practical
minimum-risk alternative. Replacing the existing holdings inbox with a generic
migration would add compatibility risk without improving this work unit. No
broader rewrite is warranted.

## Overengineering review

No unsupported workflow engine, cross-table transaction protocol, or new FX
authority is proposed. The multi-target adapter is justified by the explicit
requirement to share one file-level listener.

## Overcoupling review

Transport and business decisions remain separable. The future combined CLI and
unit couple process lifecycle but not state machines; separate worker failures
must remain isolated as planned. No additional finding beyond target uniqueness
is supported.

## Open Questions

- None after applying the three required plan corrections.

## Residual Risks and suggested tracking

- Live long-connection behavior, subscription permissions, and actual receipt
  delivery remain release/upgrade canary risks owned by a separately authorized
  rollout.
- Cross-host external writers remain outside the same-host lock and are
  mitigated, not eliminated, by fresh convergence checks.
- A file-subscription call can partially succeed when holdings and cash flow use
  different file tokens. The command must report per-token outcomes and remain
  safe to retry; live remediation belongs to the authorized subscription step.

## Conclusion

`fail`

The architecture direction is viable, but PR-01 and PR-02 are blocking and
PR-03 must be specified before an implementation agent can safely generate code.
