## Findings

### 1-已修复-高-Read-only status 会执行 SQLite 初始化和迁移

- **入口/函数**: `pm holdings events status` ->
  `OperationStateStore()` -> `_initialize()` / `_validate()` / `chmod()`
- **文件(行号)**: `scripts/pm.py:439-463`;
  `src/app/operation_state_store.py:52-63`
- **输入场景**: 操作者在未初始化的 data dir 执行方案声明为只读的
  readiness 检查。
- **实际行为**: status 创建目录/数据库，运行 schema DDL 和完整性检查，并
  改变文件权限。
- **预期行为**: status 仅解析配置并用 read-only SQLite 连接读取已存在
  inbox；不存在时报告 `initialized=false`，不创建任何文件。
- **影响**: 违反已确认的 CLI 只读边界，也使激活前审计本身成为状态变更。
- **修复证据**: 新增 `resolve_db_path_read_only()` 和
  `inspect_holding_event_status()`；CLI 不再构造 store。回归测试确认缺失
  DB 时连父目录都不会创建。
- **修复风险**: 低
- **严重程度**: 高

### 2-已修复-中-事件发现回执未冻结 event/action/revision 来源

- **入口/函数**: `plan_event_notification()` ->
  `_discovery_receipt()`
- **文件(行号)**: `src/app/holdings_workflow_service.py:96-140,742-798`;
  `src/app/holding_event_inbox_service.py:117-149`
- **输入场景**: 飞书编辑事件触发 currency 冲突或缺失补全 case。
- **实际行为**: case event 保存 trigger，但发送给人工的冻结发现回执只有
  record/case/evidence，没有 event id、action 和 revision。
- **预期行为**: 事件触发回执在入箱事务中冻结最小 trigger provenance，
  不读取可变数据，不包含密钥或完整事件体。
- **影响**: 人工确认和事后审计无法从已发送的冻结回执证明触发来源。
- **修复证据**: event worker 现在传入 `event_id` / `actions` / `revision` 及精确
  target；`_discovery_receipt()` 仅对 event path 附加冻结 `trigger`。
- **修复风险**: 低
- **严重程度**: 中

### 3-已修复-中-Worker cycle 异常可静默杀死后台线程

- **入口/函数**: `run_worker_loop()` -> `process_due()` -> SQLite
  claim/failure transition
- **文件(行号)**: `src/app/holding_event_inbox_service.py:77-104,157-174`;
  `scripts/pm.py:476-502`
- **输入场景**: SQLite claim 失败，或处理失败后的
  `mark_holding_event_failed()` 再失败。
- **实际行为**: daemon worker 线程退出，主线程的 Feishu 长连接仍然存活，
  systemd 看不到进程失败。
- **预期行为**: 一次 worker cycle 底层失败必须写入 journald 并保持循环，
  让持久化 inbox 在本地状态恢复后继续处理。
- **影响**: 服务可能看似 healthy，但新事件只入箱不校验、不发回执。
- **修复证据**: worker loop 在 cycle 边界记录 stderr 并继续；测试证明
  首次异常后第二次 cycle 仍执行。
- **修复风险**: 低
- **严重程度**: 中
