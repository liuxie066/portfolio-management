## Findings

### 1-未修复-高-派生字段维修会把已有 final NAV 降级为 maintenance，导致日终任务和质量门禁不再承认该记录

- **入口/函数**: `patch.run()` / `backfill.run()` →
  `recompute_derived_row()` → `maintenance_details()` →
  `patch_nav_maintenance_fields()` → `evaluate_nav_finality()`
- **文件(行号)**:
  `src/maintenance/nav_history_repair/common.py:163-195,252-285`;
  `src/app/nav_finality.py:104-141`;
  `src/app/daily_nav_job_service.py:147-168`;
  `src/app/quality/service.py:557-561`
- **输入场景**: 目标行是由 `daily-nav-job` 或已验证
  `nav-repair` 写入的合法 `status=final` NAV；用户只授权修复
  `cash_flow`/shares/PnL/details 中的计算证据。
- **实际分支**: `recompute_derived_row()` 固定构造
  `status=maintenance, writer=nav-repair`；`maintenance_details()` 把
  `finality` 和顶层 `run_id` 列为精确覆盖字段，因此即使
  原记录是可信 final，维修 patch 也会把它改成 maintenance。
  `evaluate_nav_finality()` 只接受 `status=final`，直接返回
  `status_not_final`。
- **直接证据**: 当 existing finality 是
  `{status: final, writer: daily-nav-job}` 而 calculated finality 是
  `{status: maintenance, writer: nav-repair}` 时，当前
  `maintenance_details()` 的输出为后者；将该输出交给
  `evaluate_nav_finality()` 得到 `eligible=False, reason=status_not_final`。
  现有回归测试 `test_daily_nav_job_skips_validated_repair_finality`
  则明确证明 `writer=nav-repair, status=final` 应保持可跳过语义。
- **影响**: 一次派生字段修复会让原本已完成的日净值
  变成阻断状态；后续 timer 报 `existing_nav_not_final`，PM
  quality 也会降级。同时顶层 `run_id` 被维修 run 覆盖，
  而旧 `cash_flow_dataset` receipt 被保留，会在同一 details 中造成
  两套不同的运行身份。
- **建议改法和验证点**: 把“估值写入终态”和“维修操作证据”
  分开。已有可信 finality 和原始顶层 `run_id` 必须保留；
  维修 run_id/writer/dataset fingerprint 放入独立的 maintenance
  provenance。对没有可信 finality 的 legacy 行，只能按明确的
  repair-finalization 规则设为 `nav-repair/final`，否则保持不可信
  分类。新增回归：final 行修复后仍被 daily job 识别为
  `skipped_existing_nav`，顶层原 run_id 不变，维修证据可单独
  追溯。
- **修复风险**: 中
- **严重程度**: 高

### 2-未修复-高-维修计算没有将完整且唯一的 NAV 依赖集验证为真源，会用默认零或任意重复前序行计算

- **入口/函数**: `patch._resolve_patch_targets()` /
  `backfill.run()` → `read_fresh_nav_rows()` →
  `recompute_derived_row()` → `valuation_from_observed()` /
  `NavHistoryIndex.build()` → `NavCalculator.calc_nav_metrics()`
- **文件(行号)**:
  `src/maintenance/nav_history_repair/common.py:101-131,198-233,252-363`;
  `src/maintenance/nav_history_repair/patch.py:250-340`;
  `src/maintenance/nav_history_repair/backfill.py:250-346`;
  `src/domain/nav_history_index.py:10-39`;
  `src/domain/nav_calculator.py:278-302,504-531`
- **输入场景 A**: 目标 legacy 行的 `fund_value` 或区域分解字段
  是 Missing/Null，但 total/cash/stock 存在。
- **实际分支 A**: `valuation_from_observed()` 只要求
  total/cash/stock，把缺失 fund 以及 CN/US/HK 都当作 0；后续
  base projection 校验对非 Value 状态直接跳过。因此它会在
  没有完整历史分解证据的情况下生成可写的派生字段和
  计算证据。
- **输入场景 B**: 目标日本身唯一，但目标日之前有两条
  同日 NAV，或最近前序行的 shares/nav 缺失。
- **实际分支 B**: patch/backfill 只检查请求目标日是否唯一；
  `NavHistoryIndex.build()` 对重复日期保留排序后的一条，
  `find_latest_before()` 直接返回该任意前序。如果前序 nav
  缺失/非正，`calc_nav_metrics()` 则把目标行当作首条 NAV，
  令 `shares=total_value`；最终 invariant 使用同一个默认分支，
  因而仍然通过。
- **直接证据**: 将 fund/CN/US/HK 都标记为 Missing 的完整
  `FreshNavRow` 交给当前 `valuation_from_observed()`，输出四项均为
  `0.0`。对同一日的 `record_id=first` 与 `record_id=second`
  构建 `NavHistoryIndex`，后者被静默选为目标日的前序行；
  改变输入顺序即会改变计算依赖。
- **影响**: 维修可以在历史估值分解不完整或前序不唯一时
  仍写入 shares/nav/PnL/details；它不是从“唯一的新鲜事实集”
  得到的结果，且内部自校验无法发现这个问题。
- **建议改法和验证点**: 在 maintenance common boundary 建立一个
  唯一的、state-aware 的历史依赖预检：目标行要求所有
  `BASE_FIELDS` 为 Value；截止最后目标日的计算链不能有重复
  account/date；每个被引用的 predecessor/period base 必须有有效
  total/shares/nav。任何不完整或歧义都返回
  `historical_evidence_required` 并在 plan/journal 产生前保持零写。
  新增回归：目标 fund/区域 Missing、重复前序日、前序
  shares/nav Missing 均零写；完整唯一链仍可通过。
- **修复风险**: 中
- **严重程度**: 高

### 3-未修复-高-日志 CAS 和 fresh readback 只比对本次变更字段，未变更派生字段漂移后仍会报 completed

- **入口/函数**: `patch.run()` / `backfill.run()` →
  `changed_states()` → journal → `_apply_journal_locked()` →
  `restricted_patch()` → fresh readback
- **文件(行号)**:
  `src/maintenance/nav_history_repair/common.py:366-391`;
  `src/maintenance/nav_history_repair/patch.py:291-321,607-684`;
  `src/maintenance/nav_history_repair/backfill.py:296-336,437-457`
- **输入场景**: plan 时只有 `nav` 需要修复，`mtd_pnl` 当时已等于
  canonical target；plan 之后、apply 之前，外部 Feishu 编辑把
  `mtd_pnl` 改成错值。
- **实际分支**: `changed_states()` 只把差异字段放入
  `original_fields/target_fields`。虽然 plan digest 计算了完整 desired
  maintenance state，写入 journal 的行没有保留这份完整状态。
  apply 前 CAS 只比对 base fields 和 `target_fields/original_fields`，
  apply 后 readback 也只重复同样的子集；不会重跑最终
  invariant。
- **直接证据**: 上述场景的 journal `target_fields` 只含
  `nav`。`_same_row_states(live_row, row["target_fields"])` 对 `mtd_pnl`
  完全无感；`restricted_patch()` 不覆盖它，紧接着的 readback
  仍只校验 nav，最后写入 `STATE=COMPLETED`。
- **影响**: 该工作流可以在已经观测到非目标派生字段漂移的
  情况下仍声明修复完成，留下不满足 canonical invariant 的
  Feishu 行。这不是无法消除的“readback 之后竞态”，而是
  fresh preflight/readback 已经看到了漂移却没有比对。
- **建议改法和验证点**: journal 行同时保存完整的
  original maintenance state 和 complete desired state；rollback 仍只写实际
  changed fields。首次 apply 前要求完整 live state 等于完整
  original 或完整 desired，每次写后要求完整 desired 并对新鲜行
  重跑 canonical invariant。新增回归：一个计划时未变更的
  派生字段在 apply 前漂移时零写失败；在 patch 后漂移时
  readback 报 partial；resume/rollback 仍仅修改 journal 声明的差异字段。
- **修复风险**: 中
- **严重程度**: 高

## Open Questions

- 对没有可信 finality 的 legacy 行，S8 修复完成后是否有权将它
  分类为 `nav-repair/final`？如果没有单独的终态授权，应保持
  `maintenance`/不可信语义，但不得降级已有 final。

## Residual Risk

- Feishu 没有独立的物理 Missing 恢复指令；即使 journal 保存
  Missing/Null/Value，清空后的服务端返回形态仍依赖 Feishu。
- same-host lock 无法阻止外部 Feishu editor 在最后一次 fresh
  readback 之后继续写入；完整 CAS/readback 可以检测已观测到的
  漂移，但不能提供跨主机原子事务。
- 本 review 没有运行 live Feishu canary；修复应通过确定性
  repository/workflow 回归和完整本地 suite 验证。
