## Assumptions tested

1. **Every Feishu holdings write is repository-owned.** Repository search shows
   all `create_record`, `update_record`, `batch_create_records`, and
   `batch_update_records` calls for table `holdings` are in
   `holdings_repository.py`; snapshots use the separate `holdings_snapshot`
   table.
2. **Formatting before `_to_feishu_fields()` is sufficient.** The generic
   serializer passes strings through unchanged and converts only Python
   `datetime`/`date` values to epoch milliseconds. The plan explicitly routes
   every holdings timestamp through a string formatter before that boundary.
3. **Slash dates need explicit typed parsing.** `RecordValidation.to_holding()`
   currently passes valid raw timestamp text to Pydantic, so the plan correctly
   includes shared parsing before constructing `Holding`.
4. **Predecessor compatibility is required.** Production contains both the
   historical slash form and full timestamps written after v0.1.30. A slash-only
   reader would create an inverse outage; accepting exactly the predecessor
   format avoids a production migration while keeping the parser bounded.
5. **Optional timestamp failures must not weaken required facts.** Repository
   cache publication remains strict and atomic, while standalone validation
   keeps malformed optional metadata nonblocking. Required identity, quantity,
   currency, duplicate, and provider rules are explicitly unchanged.
6. **One slice is reviewable.** The formatter/parser, three production consumers,
   focused tests, and one schema paragraph form one atomic contract correction;
   splitting writer and validator work would create an unsafe intermediate
   state.

## Special review lenses

### Architecture boundary review

Pass. A holdings-domain helper is below both application validation and Feishu
repository layers, introduces no reverse dependency, and avoids changing the
global datetime contract.

### Best-practice review

Pass. The plan specifies an allowlist parser, exact output assertions, atomic
cache failure behavior, predecessor skew coverage, full regression validation,
and no production migration hidden inside a code fix.

### Optimal-solution review

Pass. Editing 17 rows alone would leave writer/validator drift; changing global
`DATETIME_FORMAT` would affect unrelated tables; silently discarding timestamp
text would hide malformed values. One canonical writer plus one bounded
predecessor reader is the smallest safe option.

### Overengineering review

Pass. The helper owns two constants and pure parse/format behavior only. There
is no migration framework, timezone layer, registry, protocol hierarchy, or
generic date parser.

### Overcoupling review

Pass. Only the repository and validator depend on the helper. Futu sync, NAV
business state, Pydantic models, generic Feishu serialization, and other table
repositories remain independent.
