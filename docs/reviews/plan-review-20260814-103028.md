- Work unit: `non-futu-cash-holdings-authority`
- Review scope: authority matrix, fingerprint state transitions, cash-flow

  refusal propagation, receipt rendering, implementation slices, tests, and

- Review method: Gateflow `planreview` with architecture, best-practice,
  optimal-solution, overengineering, and overcoupling lenses
- Artifact path: `docs/reviews/plan-review-20260814-103028.md`

## Assumptions tested

- A non-Futu fingerprint drift can always be accepted without weakening a
  recovery workflow.
- Existing `record_only`, `applied`, preview hash, CAS, and fingerprint methods
  are sufficient without schema changes.
- An effect-wide non-Futu action preserves correction, deletion, mixed-broker,
  and historical-apply semantics.
- A typed domain exception can cross the current account/job result chain
  without changing the outbox contract.
- A receipt formatter can remain application-facing and avoid parsing error
  strings or internal record ids.

## Findings

### PR-01-未修复-高-非 Futu 自动接受分支未锁定在补偿保护之后，可能把部分写入误认为人工权威
- **位置**: `Authority and state-machine contract / Manual CASH holding drift`
  and S1 exact changes.
- **问题类型**: 状态机漏洞 / 并发恢复风险 / 不可直接实施
- **当前写法**: 计划要求观测到非 Futu drift 后创建或更新
  terminal `record_only` effect 并 confirm fingerprint，但未明确该分支
  必须在 `compensation_identities` 保护之后，也未禁止转换
  `compensation_pending` effect。
- **反例/失败场景**: cash-flow confirm 已写入一部分 CASH target，后续
  target 写入或 readback 失败，effect 进入 `compensation_pending`。此时
  fresh holding 必然与旧 fingerprint 不同。如果非 Futu auto-accept 先执行，
  它会把部分业务写入接受为“人工维护新基线”，从而失去补偿权威。
- **为什么有问题**: 用户确认的人工权威只适用于非 Futu 外部维护，
  不适用于系统已持有 durable compensation task 的部分写入。后者必须
  继续 fail closed。
- **直接证据**: 当前 `_scan_holding_fingerprints()` 在创建 external
  effect 前先计算 `compensation_identities` 并 `continue`；`_confirm_under_locks()`
  在部分 target 失败时写入 `compensation_pending` 及 compensation task。
- **影响**: NAV gate 可能放行未完成或未恢复的 CASH 写入，导致资产值
  与 effect/compensation ledger 不一致。
- **建议改法和验证点**: 计划显式规定 auto-accept 只能在
  `compensation_identities` 过滤之后执行，且不得转换
  `compensation_pending`。新增回归：非 Futu 部分写入后 scan 不创建/终结
  external effect，fingerprint 不自动确认，NAV 仍被 compensation blocker 阻断。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-中-`historical_apply` 的非 Futu 写入契约与计划文字冲突
- **位置**: `Non-Futu cash-flow preview choice` 末段和 S1 tests。
- **问题类型**: 契约缺失 / 测试缺口 / 公共接口
- **当前写法**: 计划写“Record-only historical effects keep the existing
  early return and require no new action”，但未区分显式
  `historical_apply=True`。
- **反例/失败场景**: cutover 前的 non-Futu effect 以 `mode=record_only`
  存在。操作员使用 `--historical-apply`时，`_build_preview()` 会跳过
  record-only early return，真实计算并写入 holding。若新 action 不在该路径
  强制，会保留无声 `fresh + delta` 的时序风险。
- **为什么有问题**: 该命令是一个显式写入逃生口，不应因 source
  日期较旧就绕过新的双重计入保护。
- **直接证据**: `_build_preview()` 只在
  `effect["mode"] == "record_only" and not historical_apply` 时早返回；显式
  historical apply 会继续进入 `_cash_flow_operations()` 和 target 写入路径。
- **影响**: 旧记录手工补应用时可能重复增减 non-Futu CASH，且计划
  无回归证明该路径与新契约一致。
- **建议改法和验证点**: 计划明确：普通 record-only preview 不要
  action；一旦 `historical_apply=True` 且 operation 触达 non-Futu，必须选
  `apply_delta`/`already_reflected`。新增 focused regression。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Architecture boundary review

The proposed ownership is otherwise sound: broker drift classification remains
in the effect service, durable state remains in the existing store, official
scope refusal remains in the domain contract, application serialization stays
in the account recorder, and user wording stays in the receipt renderer. No new
cross-layer dependency or schema is needed.

## Best-practice and optimal-solution review

The explicit non-Futu action is stronger than timestamp or amount heuristics
and reuses the existing preview hash and CAS boundary. The no-op absolute target
is preferable to a special terminal branch because it preserves standard
readback and the applied correction chain.

## Overengineering and overcoupling review

No unsupported framework or generic broker abstraction is proposed. The two
slices keep the holding-authority state machine separate from receipt wording.
The plan correctly rejects a conflict table and per-target action API absent a
demonstrated mixed-state need.

## Open questions

None after the two plan corrections above are made.

## Residual risks and tracking

- Wrong operator action remains a visible, explicitly confirmed business
  decision and is correctly classified in the current plan.
- Futu external-change/reconciliation overlap remains outside this non-Futu
  work unit; current behavior is unchanged and no current evidence makes it a
  blocker.

## Conclusion

`fail` until PR-01 and PR-02 are incorporated into the implementation plan and
the revised plan is re-reviewed. Both fixes are local plan clarifications plus
targeted regressions; they do not require a design change or schema change.
