### DR-S2-RR-01-未修复-高-holdings 的业务键、create 必填和 clearability 仍有两套真源

- **入口/函数**: `FeishuClient.create_record()` / `batch_create_records()` → `validate_write_fields()`；`HoldingTarget.__post_init__()`
- **文件(行号)**: `src/feishu/contracts/registry.py:65-102,213-220,338-385`; `src/domain/holding_mutations.py:23-42,360-399`
- **输入场景**: 调用底层 holdings create，只传 `asset_id/account/quantity`；或 update 将 `tag=None`。
- **实际分支**: registry 声明业务键是 `(asset_id, account, broker)`，但 create write contract 只要求 `asset_id/account/quantity`；它同时声明 `tag.clearable=yes`。领域层另外硬编码完整 identity、create 必需值和仅三个 null-clearable 字段，因此直接 client create/update 和 canonical mutation 得到不同结果。
- **预期行为**: registry 是表结构、业务键、row-required 和 null-clearability 的唯一真源；领域契约从它派生，任何 holdings create 都需要完整 identity 和必需业务值，`tag` 只能以显式 `[]` 设为空值而不能以 null clear。
- **实际行为**: 底层 client 可在请求前通过不完整 identity create，也不会根据 `clearable` 拒绝 nonclearable null update；而 repository/domain 会拒绝同一数据。
- **直接证据**: holdings `business_key` 含 `broker`，但 `_writes(...required...)` 不含 broker/asset_name/asset_type/currency；`tag` 在 registry 为 `clearable=True`，而 `HOLDING_NULL_CLEARABLE_FIELDS` 明确排除 tag；`validate_write_fields()` 只拒绝 create null，不消费 update clearability。
- **影响**: 用户确认的“分层唯一真源”尚未实现；新的底层调用可绕过 S2 完整键/清空不变量，之后 registry 变更也会与领域常量漂移。
- **建议改法和验证点**: 让 holdings create required fields 包含完整 business key 和 canonical target 必需值；将 tag 声明为 non-null-clearable；update validator 按 registry 拒绝 nonclearable null；`IDENTITY_FIELDS` / required values / null-clearable set 从 registry 派生。覆盖 single/batch create 一致拒绝、tag null 拒绝与 `tag=[]` wire 成功。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-S2-RR-02-未修复-中-create target 会静默丢弃未 owned 的非空 optional 目标值

- **入口/函数**: `HoldingTarget.from_holdings(base=None, ...)` → `_apply_holding_target()`
- **文件(行号)**: `src/domain/holding_mutations.py:360-423`; `src/feishu/repositories/holdings_repository.py:674-737`
- **输入场景**: create target 中 `avg_cost=100` 或 `tag=["manual"]`，但调用者的 `owned_fields` 只包含必需字段。
- **实际分支**: target 保留完整 values 并通过构造，create payload 只发 owned fields，fresh proof 也只比较 owned fields。
- **预期行为**: create 没有 base 可 carry forward；因此任何非中性 optional 值必须显式 owned，否则在任何 transport 前拒绝。
- **实际行为**: 远端创建的行没有该 optional 值，但方法可返回成功；预期值只留在请求对象中。
- **直接证据**: create 分支只校验 `HOLDING_REQUIRED_VALUE_FIELDS.issubset(owned)`；payload comprehension 仅枚举 `target.owned_fields`；没有检查 unowned `avg_cost/asset_class/industry/tag` 是否为中性值。
- **影响**: 公开 canonical contract 可把调用者显示的 absolute target 静默降级为部分 create，违反 Missing/值不得压平和“完整 absolute target”语义。
- **建议改法和验证点**: create target 仅允许未 owned optional 为中性值（三个 nullable 字段为 None，tag 为空列表）；非中性值未 owned 时拒绝并断言零 client 请求。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### DR-S2-RR-03-未修复-中-zero-delete 的最终删除仍从绑定 target 退化为 identity 重查

- **入口/函数**: `CompensationService._apply_holding_target()` → `delete_holding_if_zero()`
- **文件(行号)**: `src/app/compensation_service.py:379-409`; `src/feishu/repositories/holdings_repository.py:1087-1118`
- **输入场景**: compensation 首次 fresh read 验证 `rec-old` 与 recorded digest；在调用 delete 之前，外部 writer 删除 `rec-old` 并用同业务键新建一条零数量 `rec-new`。
- **实际分支**: compensation 把 mutation target 拆回三个 identity 字符串；repository 再 fresh read 后按 identity 选中 `rec-new`，并删除它。
- **预期行为**: 最终 destructive call 仍携带 `base_record_id/base_digest`；旧 record 消失或状态变化都应 fail closed，不得把授权转移给同键新行。
- **实际行为**: 上一轮添加的 record/digest 比较只保护第一次读，并未保护真正的 delete request。
- **直接证据**: line 395-399 仅传 identity；`delete_holding_if_zero()` 重新查找 holding 并使用新查到的 `holding.record_id`，它不接收 `HoldingTarget`或 expected record/digest。
- **影响**: 一个外部编辑窗口仍可让自动补偿删除非原任务行；这是 destructive authority 越界。
- **建议改法和验证点**: 新增或改造为 target-bound zero delete，repository 直接校验 mutation base 并只向 `base_record_id` 发 delete；故障注入在第一次校验后替换同键 record，断言新 record 不被删。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### DR-S2-RR-04-未修复-中-`init_db(initial_cash=...)` 仍无法提供完整 broker identity

- **入口/函数**: `skill_api.init_db()` → `get_holding()` / `upsert_holding()`
- **文件(行号)**: `skill_api.py:695-734`
- **输入场景**: 按公开 docstring 调用 `init_db(initial_cash=100000)`。
- **实际分支**: existence read 省略 broker；无行时构造的 `Holding` 也没有 broker，随后 S2 write boundary 以 `broker is required` 拒绝；有多 broker 行时 read 会以歧义拒绝。
- **预期行为**: 用户可见的初始化入口要求显式 broker，使用 exact fresh read，并将同一 canonical broker 放入 create target。
- **实际行为**: 文档中的 initial-cash 示例无法成功，该入口也未完成 S2 “所有 mutation 完整键”迁移。
- **直接证据**: `init_db` 签名无 broker；line 722 调用 brokerless read；line 724-733 的 `Holding` 不设 broker。
- **影响**: 一个公开 mutation 路径恒定失败或遇到歧义，且用户无参数可表达正确写入权威。
- **建议改法和验证点**: 为 `init_db` 增加显式 broker 参数；仅在 `initial_cash>0` 时要求它；使用 `get_holding_fresh` 和 canonical create；单测覆盖缺 broker 零写、带 broker 正确传递。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### DR-S2-RR-05-未修复-中-`get_holdings()` 只在远端过滤时 trim account，本地筛选仍使用原值

- **入口/函数**: `get_holdings(account=...)` → `preload_holdings_index()` → cache filter
- **文件(行号)**: `src/feishu/repositories/holdings_repository.py:644-665`
- **输入场景**: 调用 `get_holdings(account=" lx ")`，远端有 canonical `account="lx"` 行。
- **实际分支**: `get_raw_holdings` 会 trim 为 `lx`，publish 也以 `lx` 存入 cache；但 loaded-set 判定和 line 653 的 cache filter 继续与原字符串 `" lx "` 比较。
- **预期行为**: 入口只 canonicalize 一次，后续 remote filter、loaded marker 和 cache filter 全部消费同一 account。
- **实际行为**: 远端成功返回的行被发布到 cache 后又被本地过滤掉，最终返回空列表。
- **直接证据**: 方法中没有 `requested_account = str(account).strip()`；两处逻辑直接使用 account 原值，而下游 preload/publish 已 canonicalize。
- **影响**: S2 的“trim identity once”在公开 list read 上不成立；调用者可看到虚假空持仓，并且同一进程里 cache 事实与返回结果矛盾。
- **建议改法和验证点**: 方法进入时对 optional account 做一次 canonicalization/空值校验，后续所有判定仅使用 canonical account；添加空白输入返回 canonical row 的回归。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
