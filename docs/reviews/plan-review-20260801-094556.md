## Assumptions Tested

1. **The fix can preserve semantic case identity. Supported.** The revised plan
   keeps `CASE_CONTRACT_VERSION` and the case-key payload unchanged (plan
   lines 60-69). Current key construction is independent of the precondition
   digest (`src/app/holdings_workflow_service.py:1009-1021`), so the SPY
   timestamp cases do not need replacement lifecycles.
2. **Only `currency` and `asset_class` require raw `asset_type` as a separate
   authority input. Supported by current validation.** The validator passes
   effective asset type only into currency and asset-class decisions
   (`src/app/holdings_validation.py:481-502`); the remaining field validators do
   not read it. The plan also keeps the field's own current value and the stable
   identity in every precondition.
3. **A one-way compatibility transition can stay fail-closed. Supported.** The
   plan accepts only unprefixed legacy SHA-256 to recognized v2, requires exact
   semantic identity, requires exact current-record legacy digest for
   `currency`/`asset_class`, and rejects all v2 mismatches and unknown contracts
   (plan lines 81-131). This is narrower than weakening the current immutable
   comparison globally.
4. **Existing `resolved_keep` decisions need not re-block NAV. Supported.** The
   plan requires validation of the old confirmation scope, read-only recognition
   during planning, and atomic rewrite to the v2 scope during non-dry-run
   materialization (plan lines 140, 157-167, 255-261). This directly covers the
   exact-key lookup in `src/app/holdings_workflow_service.py:172-199` and the
   materialize-before-result behavior in
   `src/app/holdings_nav_preflight_service.py:337-400`.
5. **Migration can avoid user-facing receipt fanout. Supported.** Semantic keys
   stay stable, migration produces one audit event only, and operation receipts
   remain frozen (plan lines 133-146). The exact SPY assertions require one name
   closure and zero timestamp discovery/supersession/closure receipts (plan
   lines 238-245).
6. **All relevant materialization entry points can consume one transition
   implementation. Supported.** Normal notify and NAV call
   `materialize_holding_cases()`; the event inbox calls the same
   `_materialize_holding_cases_tx()` inside its event transaction
   (`src/app/operation_state_store.py:1828-1865`); direct apply uses
   `materialize_and_prepare_holding_apply()`
   (`src/app/holdings_workflow_service.py:780-788`). The plan explicitly covers
   both store paths and their callers.
7. **Old-binary rollback is not transparent after persistence. Correctly
   rejected rather than assumed.** The plan limits binary-only rollback to
   before the first v2 write and requires suspended materializers/outbox plus a
   paired operation-DB restore during the canary window; after the gate it is
   explicitly forward-fix only (plan lines 291-309).

## Previous Finding Disposition

- `PR-01` resolved: no global case-key migration; eligible legacy
  `resolved_keep` remains confirmed and is migrated in place.
- `PR-02` resolved: migration-only transitions emit audit events, not discovery,
  supersession, or closure receipts; exact SPY receipt counts are asserted.
- `PR-03` resolved: rollback is no longer described as a normal binary revert;
  the plan supplies a bounded pre-delivery canary/backup gate and declares the
  post-gate forward-only boundary.

## Architecture, Best-Practice, Optimality, Overengineering, and Coupling Review

- **Architecture boundary:** the pure contract module owns hashing and
  compatibility classification; workflow retains fresh reads, confirmation,
  and provider semantics; the store retains atomic durable transitions. No
  storage layer needs to import the workflow service.
- **Best practice:** state behavior is explicit for pending, resolved,
  terminal/reopen, and in-flight/recovery cases. Atomic failure assertions cover
  case rows, events, apply attempts, and outbox state.
- **Optimal solution:** stable semantic keys plus a one-way precondition
  transition is materially narrower than global v2 case identities and directly
  fixes the observed collision without reclassifying every user-visible case.
- **Overengineering:** the new private module is justified because the current
  formula is duplicated by case construction, outage confirmation, confirmation
  scope checks, and store state authority. No schema, listener, or public API
  abstraction is introduced.
- **Overcoupling:** receipt identity is not coupled to precondition migration;
  NAV confirmation compatibility and store mutation use the same pure predicate,
  avoiding parallel formulas.

## Residual Risks and Suggested Tracking Destination

- Non-`asset_type` fields cannot reconstruct the historical raw `asset_type`
  that produced an old broad digest. The plan's one-way format check, unchanged
  semantic identity, state allowlist, SQLite integrity check, and exact SPY test
  bound this risk. Track in S1 contract tests and the implementation artifact.
- Migrated prefixed digests are incompatible with the previous binary. Track the
  suspended canary, paired DB backup, outbox hold, and forward-only declaration
  as mandatory gates in the separately authorized release/upgrade runbook.
- The field dependency map could drift if validation policy later adds another
  cross-field input. Track the dependency assertions beside
  `holdings_validation.py` and require their update with future policy changes.
- This review validates the plan, not the eventual code. The duplicated store
  materialization paths remain an implementation risk until focused tests prove
  they call the same transition helper.

## Conclusion

`pass-with-risks`

The revised plan is code-generation-ready and stays within the requested bug-fix
boundary. Its remaining risks are explicit, testable, and deferred to the
implementation and separately authorized rollout gates rather than hidden in
normal operation.
