## Findings

### DR-S1-01-未修复-高-resolved_keep Case 被误报为待处理并重复展示处理命令
- **入口/函数**: `HoldingsNavPreflightService.prepare_account()` ->
  `_action_contract()` -> `NavHistoryReceiptService._holdings_scope_rows()`
- **文件**: `src/app/holdings_nav_preflight_service.py`、
  `src/app/nav_history_receipt_service.py`
- **输入场景**: 冲突 Case 已由人工 `keep-current` 精确确认，当前事实和
  confirmation scope 未变化；后续 Daily NAV 再次预检。
- **实际分支**: `plan_evaluation()` 仍把该语义 Case 放入 `case_keys` 和
  `discovery_receipts`，只从 `blocking_case_keys` 排除；新代码从全部
  `discovery_receipts` 生成 action items，并把全部 `case_keys` 数量标成
  “待处理”。
- **预期行为**: 已确认且仍有效的 `resolved_keep` Case 不是待处理项，不应在
  每日聚合回执里重复要求 resolve；其 warning/审计事实可继续保留。
- **直接证据**: `HoldingsWorkflowService.plan_evaluation()` 返回
  `confirmed_case_keys`，而 `_action_contract()` 未消费该集合；renderer 直接
  使用 `case_keys` 计数。
- **影响**: 用户会收到错误行动指令，可能对已闭环 Case 重复操作；每日信息
  噪声重新出现。
- **建议改法和验证点**: 在 preflight contract 中派生
  `pending_case_keys = case_keys - confirmed_case_keys`，action items 只从 pending
  Case 的 frozen discovery payload 生成；renderer 优先消费
  `pending_case_keys`，仅为旧 payload 回退到 `case_keys`。新增 resolved_keep
  回归，断言成功预检不显示待处理或 action command。
- **修复风险**: 中
- **严重程度**: 高

### DR-S1-02-未修复-中-renderer 未自行执行五条上限且可被非整数计数打断
- **入口/函数**: `NavHistoryReceiptService._holdings_scope_rows()`
- **文件**: `src/app/nav_history_receipt_service.py`
- **输入场景**: durable NAV payload 来自旧版本、测试替身或部分升级状态，
  `action_items` 超过五条，或 `action_item_count` 是空串/非整数文本。
- **实际分支**: renderer 遍历全部 `action_items`，上限只依赖 upstream helper；
  同时直接 `int(...)`，可抛 `ValueError`，使整个 NAV 回执构建失败。
- **预期行为**: 用户可见消息边界应在最终 renderer 再次强制最多五条，并对
  可选聚合计数 fail-soft；核心 NAV 回执不能因附加 Holdings 汇总格式异常而
  丢失。
- **直接证据**: `_holdings_scope_rows()` 对 list 未切片，并直接转换两个可选
  count 字段。
- **影响**: 混合版本或异常 payload 可能重新造成长消息，甚至阻止唯一任务
  回执发送。
- **建议改法和验证点**: renderer 对 action items 强制 `[:5]`，使用安全的
  non-negative integer coercion，并根据 total/rendered 数量计算至少正确的
  omitted count。新增 oversized/malformed payload regression。
- **修复风险**: 低
- **严重程度**: 中
