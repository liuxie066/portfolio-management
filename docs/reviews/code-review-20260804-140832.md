## Findings

### DR-01-未修复-[高]-未知回执类型被当作可重试发送失败，100 条 poison rows 会永久阻塞后续有效回执
- **入口/函数**: `pm cash-flow effects scan` -> `cmd_cash_flow_effects_scan()` -> `CashFlowEffectReceiptService.dispatch_pending()` -> `_send()` -> `build_message()` -> `CashFlowEffectStore.mark_receipt()`。
- **文件(行号)**: `scripts/pm.py:979-993`; `src/app/cash_flow_effect_receipt_service.py:54-79, 106-137`; `src/app/cash_flow_effect_store.py:927-965`; `tests/test_cash_flow_effect_receipt_service.py:110-120`。
- **输入场景**: durable outbox 中存在未知 `receipt_type`。这可由持久化数据跨版本保留、部署回滚、未来 producer 新增类型但旧 renderer 读取，或异常写入触发。若累计 100 条早于后续有效回执，则命中默认 dispatch limit。
- **实际分支**: 新 allowlist 在 `build_message()` 抛 `ValueError`；`_send()` 捕获所有异常并统一返回普通 `failed`；`mark_receipt(success=False)` 把状态写为 `failed`。`list_pending_receipts()` 又无条件选择 `pending` 和 `failed`，按最老 `created_at` 取前 100 条，没有 terminal-invalid/dead-letter 状态、最大次数或 next-attempt gate。
- **预期行为**: 未知类型应 fail closed 且被分类为永久 contract failure：保留审计证据、显式告警/隔离，但不能进入网络故障的无限重试队列，更不能阻断后续已知类型的补偿或异常回执。
- **实际行为**: 同一未知 row 每轮重新失败并增加 `attempt_count`；有 `effect_id` 时还会重复追加 `receipt_failed` event。达到 100 条后，每轮都只处理同一批 poison rows，后续有效回执永远没有发送机会。
- **直接证据**: `SUPPORTED_TYPES` 拒绝未知值，但 `_send()` 没有区分 validation error 和 provider error；SQL 查询固定为 `WHERE status IN ('pending', 'failed') ORDER BY created_at LIMIT ?`。本地确定性复现中，同一未知 row 连续两次 dispatch 后仍在队列且 `attempt_count=2`；插入 100 条未知 row 再插入一条有效 `runtime_error` row，连续两轮均 `attempted=100`，有效 row 的 `attempt_count` 仍为 0。新增测试只断言 `build_message()` 抛错，没有覆盖 dispatch/store 收敛。
- **影响**: Cash Flow scanner 每轮持续报告 receipt failure、effect event 无界增长；在版本偏差或批量异常数据下，真正需要人工恢复的 `compensation_pending` 等新回执可被永久饿死，削弱 fail-closed 工作流的运营可见性。
- **建议改法和验证点**: 为 renderer/contract validation failure 增加不可重试的 `invalid`/`dead_letter` outcome，或在 enqueue 边界用同一共享 receipt-type contract 拒绝并持久化独立审计事件；网络/provider failure 才保留 retry。新增 store+dispatcher 回归：未知 row 首次处理后不再入选；其后已知 row 下一轮可以发送；100 条 invalid row 不占 due limit；invalid evidence 可查询且不会重复追加 event。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-02-未修复-[中]-Futu 部分写入失败回执把缺失的 MMF 结果默认成“新增 0，更新 0”
- **入口/函数**: `PortfolioService.sync_futu_holdings()` -> `FutuBalanceSyncService.sync_portfolio()` -> `_sync_cash_snapshot()` -> `FutuSyncReceiptService.build_message()`。
- **文件(行号)**: `src/service/application.py:382-414`; `src/app/futu_balance_sync_service.py:813-835, 839-888`; `src/app/futu_sync_receipt_service.py:92-148`; `tests/test_futu_sync_receipt_service.py:135-180`。
- **输入场景**: 非 dry-run 的 `fund_mmf` 写入或 fresh readback 抛异常，producer 返回 `success=false`、`partial_write_possible=true` 和真实 `error`，但失败 payload 没有 `created`/`updated` 成功计数。
- **实际分支**: outer result 把失败对象放入 `cash_mmf`；renderer 因其为非空 dict 进入 CASH/MMF summary，并用 `cash_mmf.get('created', 0)` / `get('updated', 0)` 把“没有完成证明”改写成确定的 0。随后同一回执又显示“fund_mmf 阶段可能已部分写入”。
- **预期行为**: outcome unknown / partial-write 场景不得从缺失字段推导零变更；只应展示已证明的阶段事实，并把 MMF 写入结果标为“未确认”或省略计数。
- **实际行为**: 用户同时看到“MMF 新增 0，更新 0”和“可能已部分写入”，其中前者是没有来源证据的数值断言。新增 golden test 还把这条矛盾文案固定为预期输出。
- **直接证据**: `_sync_cash_snapshot()` 的 exception 返回仅含 `items`、`error`、`stages` 和 `partial_write_possible`，不含 `created`/`updated`；renderer 明确以默认值 0 补齐；测试构造同样缺字段的失败 payload，并断言完整消息包含“MMF 新增 0，更新 0”。
- **影响**: 在最需要判断写入影响的失败回执里，操作者可能把“计数未知”误读成“没有 MMF 变化”，与 partial-write 警告冲突并增加错误恢复判断风险。
- **建议改法和验证点**: 仅在 `cash_mmf.success=true` 且计数字段存在时显示新增/更新计数；失败时显示“MMF 结果未确认”，保留真实错误、失败阶段和 dry-run 命令。修改 golden test，断言 partial-write 消息不包含任何从缺失字段默认出的零计数；另覆盖明确成功零变更仍显示 0。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
