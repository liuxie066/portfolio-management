# Plan Review — Feishu Agent/Listener Identity

- Reviewed target: `docs/gateflow/feishu-agent-listener-identity/implementation-plan.md`
- Work unit: `feishu-agent-listener-identity`
- Review scope: goal, public configuration migration, credential authority,
  runtime routing, systemd grants, tests, and local-only delivery boundary
- Review timestamp: `20260806-094643`
- Conclusion: `fail`
- Artifact path: `docs/reviews/plan-review-20260806-094643.md`

## Assumptions tested

- Existing Bitable/Conversation/direct/receipt key families can be translated to
  Agent/Listener without knowing the concrete applications behind them.
- Binding the default `FeishuClient` to Agent keys is sufficient to guarantee
  Agent authority for Base API calls.
- Event status needs to prove only Listener ingress credentials.
- Unit-level client routing tests adequately cover the failed Futu MMF path.

## Special review lenses

- **Architecture boundary**: identity authority must be owned by configuration and
  client construction, while event payload routing stays listener-owned.
- **Best practice**: ambiguous auth migrations must fail closed; health/status must
  represent all capabilities required by a combined process.
- **Optimal solution**: explicit canonical migration is safer than guessing old
  role semantics from key names.
- **Overengineering**: the two-role model is justified, but broad compatibility
  inference adds unsafe complexity rather than reducing migration cost.
- **Overcoupling**: the listener process intentionally combines ingress and worker
  execution; its status and systemd grants must expose both independent roles.

## Findings

### PR-01-未修复-高-旧 Bitable/Conversation 键不能安全自动重解释为 Listener/Agent
- **位置**: Public configuration contract / Compatibility mapping / S1
- **问题类型**: 契约缺失 / 迁移风险 / 最佳实践偏离
- **当前写法**: 计划把 v0.1.35 `feishu.conversation.*` 自动映射到 Agent，
  把 `feishu.bitable.*` 自动映射到 Listener，并把 receipt/OM bot 也映射到 Agent。
- **反例/失败场景**: 严格按 v0.1.35 公共文档部署的实例可能使用一个真正的
  Base writer/listener app 作为 Bitable，另一个 receipt-only bot 作为 Conversation。
  自动映射后，Base writer 被降成 Listener，而 receipt-only bot 获得 Agent Base
  写入职责。配置值本身可以完全合法且互不冲突，resolver 无法发现语义错误。
- **为什么有问题**: 旧 key 名只证明旧合同中的角色，不证明新合同的应用能力；
  当前生产的特殊映射不能被推广为公共兼容规则。
- **直接证据**: 当前 `docs/deploy-linux.md` 明确规定 Bitable 负责 Base API 与事件，
  Conversation 只发消息；旧 Gateflow closeout也记录同一合同。
- **影响**: 其它安装可能静默把写权限交给错误应用，或在升级后重复本次 HTTP 400。
- **建议改法和验证点**: 只保留语义确定的 `feishu.app_* -> Agent` 兼容；
  v0.1.35 Bitable/Conversation、receipt 和 OM bot 输入只能作为迁移诊断，不能自动组成
  新 Agent/Listener。生产 secure mode 必须显式配置 canonical Agent/Listener App ID
  和新 credential 文件。增加旧配置 fail-closed 与显式 canonical 成功测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-feishu.user_token 可绕过 Agent 应用身份
- **位置**: Runtime ownership / S1 / S2
- **问题类型**: 架构边界 / auth 权限边界 / 测试缺口
- **当前写法**: 计划只把 `FeishuClient` 默认 App ID/Secret 改为 Agent，未处理
  现有 `feishu.user_token` 配置与 constructor 分支。
- **反例/失败场景**: 配置中遗留 `FEISHU_USER_TOKEN` 或 YAML user_token 时，
  `_get_headers()` 仍使用个人 Bearer token，Base 读写不会经过 Agent tenant token。
- **为什么有问题**: 这直接违反“所有 Base API 读写由 Agent 身份执行”的成功信号，
  secure preflight 也可能在 Agent credential 完整时漏报旁路。
- **直接证据**: `src/feishu_client.py` 保存 config-provided user token，并在
  `_get_headers()` 中优先使用它；`src/config.py` 仍公开 `FEISHU_USER_TOKEN`。
- **影响**: 写入审计身份不可信，个人 token 可绕过应用权限与 credential 生命周期。
- **建议改法和验证点**: 默认生产客户端不再从配置读取 user token；secure mode
  对任何 user-token shadow fail closed。仅保留显式 constructor injection 给隔离测试或
  明确的非生产调用，并测试默认 Base path 永不读取该配置键。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-03-未修复-高-events status 只验证 Listener 会误报 combined process 健康
- **位置**: S1 / event status assertions / systemd matrix
- **问题类型**: 状态机漏洞 / 可观测性缺口 / 过度耦合
- **当前写法**: 计划要求事件 status 报告 Listener readiness，但 listener unit 同时
  运行需要 Agent Base 访问的 worker。
- **反例/失败场景**: Listener credential 完整而 Agent credential 缺失时，长连接
  能启动并接受事件，worker 随后无法 fresh-read 或写 generated fields；status 却成功。
- **为什么有问题**: combined process 的 success 必须证明 ingress 和 worker 两条
  独立能力链，而不仅是 transport。
- **直接证据**: `cmd_events_listen()` 在同一进程构造 `PortfolioService().storage`
  以及 holdings/cash-flow workers；计划的 systemd matrix也要求该 unit加载两份凭据。
- **影响**: 事件被持久接收后处理失败，健康检查掩盖积压与业务延迟。
- **建议改法和验证点**: `events status` 输出独立 `listener` 与 `agent_worker`
  credential readiness，顶层 success 要求两者都满足；保留 remote subscription/
  connection 为 unverified。覆盖 Listener-only、Agent-only、两者齐全三种测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-04-未修复-中-缺少失败路径的 MMF 身份回归测试
- **位置**: S2 tests
- **问题类型**: 测试缺口
- **当前写法**: 计划测试 Base client 和 receipt/event modules 的默认 key 请求，
  但没有覆盖本次实际 `FutuBalanceSyncService -> CashService -> HoldingsRepository
  -> FeishuClient.update_record` 路径。
- **反例/失败场景**: 默认 Client 测试通过，但 service/storage factory 在组合路径中
  注入 Listener client 或旧 role client，本次回归仍会复现。
- **为什么有问题**: 事故入口是 scheduled MMF update；只测叶子构造器无法证明组合
  入口使用正确 authority。
- **直接证据**: 生产 receipt 的 `positions` 成功而 `fund_mmf` 更新失败；当前测试计划
  没有命名该组合调用链的身份断言。
- **影响**: 修复可能在单元测试中通过，却没有覆盖真实故障入口。
- **建议改法和验证点**: 增加不发网络的组合回归，构造 Futu/MMF sync 所需 storage
  factory并捕获 Feishu client的角色解析，断言更新请求只由 Agent client发出；同时断言
  Listener adapter不参与该路径。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Open questions

None. All findings can be resolved within the approved local work unit.

## Residual risks

- Live tenant scopes and document access remain a later deployment canary.
- New encrypted credential file provisioning and disclosed Agent Secret rotation
  remain explicitly outside local implementation.
- Existing third-party installations, if any, must perform explicit canonical role
  mapping; track this in migration documentation rather than unsafe aliases.

## Final conclusion

`fail`. The plan must remove semantic guessing from legacy aliases, close the
user-token bypass, make event status prove both halves of the combined process,
and add a regression around the actual MMF update path before implementation.
