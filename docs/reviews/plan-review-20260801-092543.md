# Plan Review — Bitable Subscribe Request

## Reviewed target and scope

- Target: `docs/gateflow/bitable-subscribe-request/implementation-plan.md`
- Work unit: `bitable-subscribe-request`
- Base: `main@2a1ae72`
- Review mode: adversarial implementation-plan review
- Included: combined and holdings-only subscription request builders, exact
  request tests, CLI compatibility, public result metadata, and validation
  boundaries
- Excluded: production subscription mutation, listener restart, business-data
  writes, permissions redesign, and SDK upgrade

## Assumptions tested

- Confirmed from the installed `lark-oapi==1.7.1` source that
  `SubscribeFileRequestBuilder.event_type()` writes an `event_type` query
  parameter.
- Confirmed both repository adapters currently call that method for
  `file_type=bitable`.
- Challenged whether the fix might accidentally alter long-connection event
  registration; the plan limits changes to the request builder chains and
  retains the existing callback-registration tests.
- Challenged whether the two public commands can drift; the plan includes exact
  request assertions for both adapters.
- Challenged whether a shared helper is required; two direct call sites plus
  exact tests are simpler and avoid an unnecessary new ownership boundary.
- Challenged whether the JSON result must change; retaining the existing shape
  avoids an unrelated public-contract change, while the request maps become the
  authoritative wire-level regression evidence.
- Challenged failure, retry, durability, and state transitions; the patch does
  not change response handling or local state, and production subscription or
  retry is explicitly excluded.

## Architecture boundary review

The plan keeps the change in the Feishu transport adapters. Domain event
normalization, workers, inbox durability, receipts, and Base repositories do not
gain SDK request knowledge. Dependency direction remains unchanged.

## Best-practice and optimal-solution review

Exact built-request assertions are the narrowest deterministic regression for
an invalid query parameter. An SDK upgrade, raw HTTP client, or new request
factory would add dependency or abstraction risk without improving the known
wire request.

## Overengineering and overcoupling review

The plan rejects a new shared request abstraction and does not bind subscription
success to listener startup or business-data validation. The compatibility
adapter is included only because it implements the identical public request
contract.

## Residual risks

- The existing JSON key `subscription_event_type` names semantic application
  event configuration rather than a query parameter after this correction.
  It is retained for compatibility and is explicitly not request evidence.
  Any rename/removal belongs to a separate public-contract cleanup work unit.
- External Feishu protocol drift remains possible. The exact request tests and
  recorded production failure/success evidence cover the known defect; live
  re-subscription is outside this code-review work unit.
- The unrelated untracked review artifact remains outside scope and must be
  excluded by path-scoped staging.

## Conclusion

`pass-with-risks`

The plan is code-generation-ready. Its residual risks are classified and do not
block the single implementation slice.
