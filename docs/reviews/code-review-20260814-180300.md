### 1-未修复-高-通用 FUND 类型的场内基金会错误使用 Eastmoney 净值而非 OpenD 收盘价

- **入口/函数**: `build_historical_price_snapshot()` provider routing
- **文件(行号)**: `src/app/nav_valuation_evidence_service.py:345-359, 389-479`
- **输入场景**: Holdings 中 `159941`、`513500`、`563020`、`588150` 等场内基金保留兼容类型 `AssetType.FUND`，代码本身明确属于沪深场内基金。
- **实际分支**: 只有 `AssetType.EXCHANGE_FUND` 进入 OpenD；所有 `AssetType.FUND` 都在 413-415 行进入 Eastmoney 历史基金净值。
- **预期行为**: 已有 code classifier 能识别 5xx/15x 场内基金；无论兼容类型是 `FUND` 还是精确类型是 `EXCHANGE_FUND`，这些代码都必须使用目标日不复权交易所收盘价。
- **实际行为**: 兼容 Holdings 可得到基金单位净值而不是交易所收盘价，且仍生成 official valuation artifact。
- **直接证据**: `fund_types` 包含 `AssetType.FUND`，路由不调用已有 `is_etf()`；测试只覆盖显式 `AssetType.EXCHANGE_FUND`，没有覆盖真实兼容类型。
- **影响**: 本次 `lx/2026-08-13` 恢复涉及多个场内基金，错误路由会直接改变总资产和正式 NAV。
- **建议改法和验证点**: 复用 `src.pricing.classifier.is_etf()`，让场内代码优先进入 OpenD，并校验 provider 推导币种与 Holdings 币种一致；增加 `AssetType.FUND + 159941` 回归测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-中-evidence load 只验 hash 未对称校验关键审计字段

- **入口/函数**: `NavValuationEvidenceStore._validate_artifact()`
- **文件(行号)**: `src/app/nav_valuation_evidence_service.py:220-253`
- **输入场景**: runtime root 中存在重新计算过 digest、但 `source_run_id` / `snapshot_time` / `captured_at` / `source_effect_store_revision` / `preparation` 为空或非法的 JSON。
- **实际分支**: load 校验 version、account/date、两个 digest 和 valuation，但未重放 `prepare()` 对上述字段的 schema 校验。Digest-addressed 只能证明内容与引用一致，不能证明内容符合契约。
- **预期行为**: immutable store 的 load 边界必须对称执行完整 schema 校验；错误 artifact 在进入 replay preflight 前即被拒绝。
- **实际行为**: 例如空 `snapshot_time` 可被投影为 replay snapshot，最终 finality 缺少有效 `valuation_as_of`；空审计 provenance 也可能进入正式记录。
- **直接证据**: `prepare()` 在 90-122 行校验这些字段；`_validate_artifact()` 在 220-253 行没有对应检查。
- **影响**: 手工损坏、旧生成器缺陷或本地错误文件可削弱 replay 的审计完整性，部分情况可能写出不可识别为 final 的 NAV。
- **建议改法和验证点**: load 对称校验非空字段、时间格式和 preparation 枚举；构造一个重新 hash 的非法 artifact 回归测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
