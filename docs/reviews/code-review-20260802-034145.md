## Findings

### 1-未修复-中-readback 请求自身抛错时丢失 partial-write 结果，人工 FX CLI 也会把结构化 apply 失败改写成裸异常

- **入口/函数**: `CashFlowRepository.reconcile_cash_flows()` post-write readback；`cmd_cash_flow_reconcile()` manual confirmation branch
- **文件(行号)**: `src/feishu/repositories/cash_flow_repository.py:563-602`; `scripts/pm.py:769-822`
- **输入场景**: batch update 正常返回并已失效缓存，但紧接着 fresh `get_raw_cash_flows()` 因网络/Feishu 暂时错误抛出；或 repository 已结构化返回 `success=false, partial_write_possible=true`，且命令带 manual FX evidence。
- **实际分支**: readback 异常直接越过 repository result，调用方只看到原始异常，已知 `updated_count`/partial-write 信息丢失。第二种情况下 CLI 不先检查 `result.success`，仍从 pending rows 提取目标，最后抛出通用 readback mismatch `RuntimeError`，同样丢掉 repository reason code 和 partial-write 标志。
- **预期行为**: 所有“写请求已发出但 fresh completion proof 不可得”的路径都返回稳定 `success=false`、`partial_write_possible=true`、原 reason/error 与已知 count；CLI 原样输出该失败并以非零退出，不写 confirmation。
- **实际行为**: 最危险的网络边界仍没有 durable/structured impact evidence，操作者无法区分零写入与可能已写入。
- **直接证据**: batch 后第一个 readback 调用没有异常处理；CLI manual branch 在 `result` 返回后立即筛 row，没有 `success is False` 的短路。
- **建议改法和验证点**: 捕获 post-write scan/plan 异常并返回 `cash_flow_readback_failed` + partial flag；manual CLI 在任何 confirmation 判断前原样返回 failed result。新增 readback-exception fault test和 CLI partial-result preservation test。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
