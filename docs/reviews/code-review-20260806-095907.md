### S1-DR-01-未修复-高-v0.1.35 旧角色检测不完整，部分旧配置被误报为普通缺失

- **入口/函数**: `validate_deploy_config()` -> `resolved()` -> `_resolve_canonical_non_secret()` / `_resolve_canonical_secret()` -> `_legacy_role_candidates()`
- **文件(行号)**: `src/config.py:108-123, 346-379, 392-465`
- **输入场景**: 升级节点只有 v0.1.35 的 `feishu.bitable.app_id/app_secret`，没有新的 `feishu.agent.*`；或只有旧 `feishu.conversation.*` / `feishu.receipt.*`，没有新的 `feishu.listener.*`。
- **实际分支**: `AMBIGUOUS_LEGACY_ROLE_KEYS` 只把 Conversation/receipt 旧键关联到 Agent，只把 Bitable 旧键关联到 Listener。解析另一个 canonical role 时 `_legacy_role_candidates()` 返回空，随后走 `default`，doctor 只报告普通 `missing required value` / `missing_secure_credential`。
- **预期行为**: 已接受的迁移契约要求 Bitable/Conversation/receipt/OM 旧角色都只能作为歧义迁移证据；缺少任何 canonical Agent/Listener 时，应明确 fail closed 为 `ambiguous_legacy_role_configuration`，而不是把已存在的旧拓扑伪装成全新缺失配置。
- **实际行为**: Bitable-only 节点的 Agent 缺口和 Conversation-only 节点的 Listener 缺口丢失迁移语义，operator 无法区分“需要映射旧身份”与“从未配置身份”，也无法按承诺的升级停止条件处置。
- **直接证据**: `AMBIGUOUS_LEGACY_ROLE_KEYS["feishu.agent.app_id"]` 没有 `feishu.bitable.app_id`，Agent Secret 同样缺失；Listener 两项只包含 Bitable。解析器仅检查当前 canonical key 对应的该集合，没有全局旧角色证据回退。现有参数化测试也只证明 Conversation/receipt/OM -> Agent 和 Bitable -> Listener，没有覆盖反向缺口。
- **影响**: 生产版本迁移诊断不准确，可能让 operator 依据错误的 missing-credential 信号重建或错误映射身份；这是本改动要消除的权限拓扑歧义，直接影响升级安全。
- **建议改法和验证点**: 将全部旧 App ID role keys 作为 Agent 与 Listener App ID 的歧义证据，将全部旧 App Secret role keys作为两个 Secret 的歧义/明文 shadow 证据；`open_id` 仍只关联旧 Conversation/receipt/OM。增加 Bitable-only -> Agent ambiguous、Conversation/receipt/OM-only -> Listener ambiguous 的配置与 doctor 回归，并确认 canonical 值存在时只输出 redacted shadow warning。
- **修复风险（低/中/高）**: 低
