The implementation preserves the byte-identical `holdings-case.v1` key payload,
moves only field preconditions to a recognizable v2 token, and retains raw
`asset_type` only for `currency` and `asset_class`, which are the validation
decisions that consume that cross-field input. The compatibility predicate is
one-way and state-gated: unknown contracts, v2 mismatches, relevant legacy
digest mismatches, changed semantic facts, stale keep scopes, and in-flight or
recovery states remain fail-closed.

migration helper inside their existing `BEGIN IMMEDIATE` transaction. A valid
migration updates only the digest (and a validated `resolved_keep` scope), adds
one audit event, and does not create an operation receipt. Subsequent immutable
comparison, reopen/apply preparation, closure resolution, event-inbox
completion, and receipt inserts therefore commit or roll back with it. Notify
and event paths retain their no-holdings-write boundary.

The tests exercise the exact SPY failure shape, stable v1 case-key golden,

keep migration, in-flight rejection, atomic combined apply, direct resolve and

## Residual Risk

- For non-`asset_type`-dependent fields, the old broad digest cannot prove which
  historical raw `asset_type` produced it. The implementation bounds that known
  migration limitation with exact semantic identity, recognized legacy shape,
  an eligible-state allowlist, and a one-way transition. This is the same
  explicitly accepted residual risk from the reviewed plan.
- Once a v2 digest is persisted, the preceding binary cannot interpret it.
  Any later rollout therefore remains forward-only after first migration unless
  the operation database is restored with the old binary. Release and remote
  upgrade were not part of this review or implementation authorization.
