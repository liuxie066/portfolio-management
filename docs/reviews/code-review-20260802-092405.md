## Findings

### 1-未修复-中-`error` 的行可选性被误写成 schema 可选，严格结构校验会放行无法承载错误状态的镜像表
- **入口/函数**: `compare_live_schema()` -> `FieldContract.schema_required` -> `CompensationService.record()` -> `FeishuStorage.mirror_compensation_task()`
- **文件(行号)**: `src/feishu/contracts/registry.py:19-38,192-210,276-287,427-478`; `src/app/compensation_service.py:134-161`; `src/feishu_storage.py:441-499`; `docs/schema.md:174-189`
- **输入场景**: 可选 `compensation_tasks` 表已配置，但线上结构缺少 `error` 字段；运行 schema check 后记录一个带错误原因的可操作 PENDING/FAILED 补偿任务。
- **实际分支**: S12 为了从 create row-required 列表移除 `error`，同时把 `_field(... required=False)` 写入结构合同。`_field.required` 实际映射为 `schema_required`，因此 live comparator 只把缺失的 `error` 放入 `missing_optional` 并仍返回 `ok=True`。之后镜像会把本地非空 `error` 发给不存在该字段的表，远程写失败。
- **预期行为**: “字段在表结构中必须存在”和“每个 create row 必须提供非空值”应独立建模。`error` 可以不是 create row-required，但仍应是配置表的 schema-required 字段，并允许 RESOLVED update 显式清空。
- **实际行为**: 严格 schema gate 对不完整的已配置镜像表报告成功，而真实任务写入才以 best-effort 失败回执暴露问题。
- **直接证据**: `_field()` 第 36 行把 `required` 直接传给 `schema_required`；`compare_live_schema()` 第 439-448 行分开 required/optional missing，第 478 行的 `ok` 不包含 `missing_optional`；create row-required 则在第 281-287 行的独立 `WriteContract` 定义。当前生成文档也已把 `error` 标为 schema `optional`。
- **影响**: 结构审计可以给出假阳性健康；可选镜像一旦启用，最需要观测的 PENDING/FAILED 原因无法写入，镜像持续滞后而只在本地日志中报错。
- **建议改法和验证点**: 保持 `error.schema_required=True`，仅保留 `clearable=True` 并从 create `required_fields` 移除；重新生成 schema 文档。增加合同断言：缺 `error` 的已配置表必须 `ok=False/missing_required`，而 create 无 `error` 及 RESOLVED update `error=None` 仍合法。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 2-未修复-中-公共状态入口允许已镜像任务回退到 `PREPARED`，必然产生本地与飞书不可收敛的状态
- **入口/函数**: `CompensationService.record()` -> `update_status(task_id, "PREPARED")` -> `_append_status()` -> `mirror_compensation_task()` -> `validate_write_fields()`
- **文件(行号)**: `src/app/compensation_service.py:35-36,134-161,199-207,321-341`; `src/feishu/contracts/registry.py:192-199,276-287,385-423`; `src/feishu_storage.py:536-556`
- **输入场景**: 一个带受支持 recovery target 的任务已通过 `record()` 以 PENDING 创建并成功镜像；任何公共调用方随后执行 `update_status(task_id, "PREPARED")`。
- **实际分支**: `COMPENSATION_STATUSES` 包含 `PREPARED`，而 `update_status()` 只检查成员资格，不检查 current->next transition。本地 STATUS 事件先 fsync，且已经为 true 的 `mirror_eligible` 保持不变；随后镜像 update 带 `status=PREPARED`。但注册表 SingleSelect 只允许 PENDING/RUNNING/FAILED/RESOLVED，因此 client write validation 必然拒绝，并只留下 failed mirror receipt。
- **预期行为**: `PREPARED` 只能由 `prepare()` 创建，不能从已可操作/已镜像的状态回退；本地 lifecycle 应在 append 前拒绝非法转换。本地状态和镜像 select options 应从一个 domain-owned lifecycle contract 投影，而不是两处独立字符串集合。
- **实际行为**: 本地权威状态变成 PREPARED，远程仍保留旧状态；后续查询显示任务退回到瞬时 intent，而每次镜像都无法表示当前 fold。
- **直接证据**: app 第 35-36 行独立定义全部状态；registry 第 196-199 行又独立定义可镜像 options；`update_status()` 第 202-207 行没有转换检查；`_append_status()` 第 325-341 行对 eligibility 只做 false->true，不会因 PREPARED 恢复 false；write validator 会对不在 select options 的值 raise。
- **影响**: 新增的“当前状态镜像”承诺可被公共方法稳定地破坏；本地虽不丢事件，但任务分类、操作员判断和远程可观测状态互相矛盾。另外，同一组 lifecycle 值的两处手写真源会在下次状态扩展时重现此类偏移。
- **建议改法和验证点**: 新建小型 domain compensation lifecycle contract，集中定义全部 local 状态、可镜像状态及允许转换；service 和 registry 分别消费它的投影。在 fsync 前验证 current->next，并增加 PENDING/FAILED/RESOLVED->PREPARED 被拒绝、本地事件不变、飞书零请求的回归；同时断言 registry options 来自同一 contract。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中
