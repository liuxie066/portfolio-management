## Reviewed goal and boundary

The existing plan is intended to make a newly added `holdings` row safe before
it affects official NAV: raw missing values remain observable, `asset_type`
selects an evidence-bounded currency resolver, populated conflicts require
human confirmation, and valuation consumes the exact validated snapshot.

The new requirement does not broaden that business boundary. It adds one
discovery/trigger path for the same `holdings` validator and reconciler:
Feishu's `drive.file.bitable_record_changed_v1` event for the configured Base
and `holdings` table. This review does not treat the event payload as a new
financial authority and does not propose a second completion implementation.

## Assumptions tested

### Architecture boundary review

- Tested whether the event entry can call the existing planned raw-read ->
  validator -> cases/outbox -> NAV-gate path without making the listener a
  holdings fact source.
- Tested whether the current plan identifies ownership for event receipt,
  durable acceptance, background processing, reconciliation, and message
  delivery.
- Tested whether one exact Feishu resource can be handled without introducing a
  generic webhook/event-bus abstraction.

### Best-practice review

- Tested the official at-least-once delivery, three-second handler deadline,
  duplicate event behavior, resource filtering, durable-before-ack ordering,
  replay/restart recovery, fresh record read, and self-generated edit loop.
- Tested that `record_added` and `record_edited` can be bounded to the current
  work unit. `record_deleted` semantics are not added to this scope.
- Tested that NAV preflight remains the correctness backstop when event delivery
  is unavailable or an event type does not carry all authoritative facts.

Official protocol evidence:

- [Base app record changed](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/drive-v1/file/events/bitable_record_changed)
  defines `drive.file.bitable_record_changed_v1`, `file_token`, `table_id`,
  `record_id`, revision, before/after values, and added/edited/deleted actions;
  formula-value changes do not trigger this event.
- [Event subscription overview](https://open.feishu.cn/document/server-docs/event-subscription-guide/overview?lang=zh-CN)
  documents long-connection and developer-server delivery and at-least-once
  duplicate delivery; the v2 `event_id` is the idempotency identity.
- [Long-connection receiver](https://open.feishu.cn/document/server-docs/event-subscription-guide/event-subscription-configure-/request-url-configuration-case?lang=zh-CN)
  requires completion without exception within three seconds, supports only
  enterprise custom apps, and delivers one event to one randomly selected
  client rather than broadcasting to all clients.

### Optimal-solution review

- Reusing the planned raw reader, validator, workflow cases, and receipt outbox
  is smaller and safer than Base automation or a listener-specific fixer.
- A single exact-resource long-connection ingress is smaller than exposing a
  public HTTP callback and its verification/decryption surface, assuming the
  existing app is an enterprise custom app.
- NAV preflight is an adequate no-new-timer backstop; a second polling cadence
  is not needed for this requirement.

### Overengineering review

- Rejected a general event framework, multi-table router, event-sourced holdings
  model, new message renderer family, interactive cards, and standalone scan
  timer as unsupported scope expansion.
- A minimal durable inbox is justified only because acknowledging before a
  durable handoff can lose work, while processing the full reconciliation in
  the callback can exceed the protocol deadline and cause redelivery.

### Overcoupling review

- The listener must depend on a narrow reconciliation command/service boundary;
  the validator and domain workflow must not depend on the Feishu SDK event
  class.
- Event transport state and semantic reconciliation cases serve different
  identities: `event_id` deduplicates delivery, while `case_key` deduplicates a
  stable business conflict. Collapsing them would couple transport retries to
  business state.
- Receipt dispatch remains the existing typed outbox path. The event handler
  must not call the concrete Feishu message sender.

### State-machine and recovery review

- Tested duplicate delivery, out-of-order revisions, crash before durable
  acceptance, crash after acceptance and before processing, listener restart,
  missing/deleted record at worker read, Feishu read failure, fresh evidence
  failure, and PM's own completion patch causing a new `record_edited` event.
- Tested the difference between transport completion and field completion. The
  current plan specifies recovery for Feishu/SQLite field writes but no event
  inbox lifecycle.

### Validation and slice review

- S1 supplies the required raw reader and pure validator.
- S2 supplies cases, confirmation, recovery, and the typed outbox.
- The current S3 covers only official NAV gating and frozen snapshot handoff.
- No approved slice currently owns Feishu event SDK integration, subscription
  filtering, durable acceptance, worker processing, service lifecycle, or their
  tests.

## Findings

### PR-HOLD-EVENT-01-未修复-高-用户确认的事件触发入口被现有 plan 明确排除
- **位置**: sections 1, 3, 10, 13, and 16
- **问题类型**: 范围/目标不一致 / 契约缺失 / 不可直接实施
- **当前写法**: Goal says a newly added row must be validated, but missing
  fields can be written only through an explicitly selected `record_id` with
  `--apply --confirm`. The CLI and confirmed NAV run are the only discovery
  paths. Section 3 excludes a new scheduler, section 16 says there is no
  proactive timer, and S1-S3 assign no event-listener ownership.
- **反例/失败场景**: An operator adds a holdings row and neither runs the CLI nor
  starts a confirmed NAV run. PM receives no trigger, creates no case, performs
  no safe completion, and sends no conflict receipt. An implementation agent
  following the current slices can complete every acceptance test while
  omitting the newly confirmed entry entirely.
- **为什么有问题**: The plan's stated success signal is no longer reachable by
  the agreed normal entry. Treating the listener as an undocumented future
  enhancement would preserve the old latency behavior rather than the requested
  flow.
- **直接证据**: Plan lines 14-28, 70-72, 306-326, 458-476, 546-637, and 709-711.
  A repository-wide search finds no Feishu event subscription, long-connection
  client, `drive.file.bitable_record_changed_v1` handler, or event SDK
  dependency in the current codebase.
- **影响**: Implementation can pass while failing the user-visible trigger and
  receipt behavior; later listener work would have to reopen workflow and slice
  boundaries.
- **建议改法和验证点**: Amend the same work unit, not a generic new subsystem.
  Add one narrowly scoped event-ingress slice after raw validation and durable
  cases/outbox exist. It must accept only the configured Base plus `holdings`
  table and reuse the same reconciler. Preserve NAV preflight as the fallback
  and do not add a polling timer, other tables, Base automation, or public HTTP
  mutation surface. Add acceptance tests proving one added/edited record reaches
  the same validator/case/outbox path and unrelated resources are ignored.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-HOLD-EVENT-02-未修复-高-“触发补全”是否授权后台自动写入没有收敛
- **位置**: success signal 3, sections 8.1 and 10, confirmed product decisions
- **问题类型**: open question 未收敛 / 写入授权 / 状态机契约缺失
- **当前写法**: Every missing-field patch requires an operator-selected
  `record_id`, `--apply`, and `--confirm`. The event discussion calls the
  message a completion trigger, but the plan does not say whether the background
  worker may execute a missing-only patch or may only validate, materialize
  cases, and notify.
- **反例/失败场景**: One implementation interprets “trigger completion” as
  automatic `missing_completable` writes and silently bypasses the explicit
  confirmation boundary. Another preserves `--apply --confirm`, sends a receipt
  for every safe missing value, and never performs the expected automatic
  completion. Both can claim consistency with part of the current wording.
- **为什么有问题**: This is not an implementation detail. It determines who is
  authorized to mutate Feishu, which transitions are legal, whether
  `pending_apply` needs human confirmation, what a discovery receipt says, and
  what the acceptance tests prove.
- **直接证据**: Plan lines 26-28, 304-326, 355-358, and 468-476. The user has
  separately required populated conflicts to be returned for human
  confirmation, but has not yet selected the background-write policy for safe
  missing-only proposals.
- **影响**: The implementation agent must invent a product and safety policy;
  the wrong choice can either create unauthorized writes or fail the automatic
  completion expectation.
- **建议改法和验证点**: Obtain one explicit product decision and encode it in
  success signals, authority boundaries, case states, receipts, CLI/event
  parity, and tests. If background apply is allowed, limit it to
  `missing_completable` fields on one event record and require the existing
  fresh read, account/record locks, fresh evidence, durable attempt marker,
  narrow patch, readback, and unknown-outcome recovery. Populated conflicts,
  `missing_manual`, invalid rows, and orphans must never be auto-written. If the
  listener is discovery-only, rename the behavior accordingly and retain
  explicit CLI confirmation for every patch.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-HOLD-EVENT-03-未修复-高-事件传输与业务幂等之间缺少耐久交接契约
- **位置**: sections 6-9, 13, and validation gates
- **问题类型**: 状态机漏洞 / 并发恢复风险 / 架构边界 / 测试缺口
- **当前写法**: The plan has semantic `case_key` idempotency and durable
  receipt delivery, but no event `event_id` inbox, handler deadline, durable
  acknowledgement point, retry state, resource filter, worker handoff, or
  self-generated event suppression.
- **反例/失败场景**: If the callback performs raw reads, Futu observation,
  validation, SQLite materialization, and optional Feishu patch before returning,
  it can exceed three seconds and be redelivered. If it returns before durable
  storage, a process crash loses the only prompt trigger. If a PM completion
  patch produces another edited event, transport-level dedupe cannot stop the
  new event id; without a fresh-digest no-op rule the service can loop or resend
  work. Multiple records in one `action_list` can also be partially accepted
  without a defined transaction boundary.
- **为什么有问题**: `case_key` identifies a semantic reconciliation condition,
  not delivery acceptance. The Feishu contract is at-least-once, and the
  listener service lifecycle is absent from the current repository. The plan
  cannot guarantee prompt processing, no loss, or no feedback loop.
- **直接证据**: Plan sections 6-9 define case/evidence/receipt identities but no
  transport inbox. The official event overview requires v2 `event_id`
  idempotency and documents duplicate delivery; the long-connection guide
  requires completion within three seconds. The record-change event includes
  a list of record actions and does not trigger on formula-value changes.
- **影响**: Duplicate cases/work, notification loops, silent event loss,
  redelivery storms, or acknowledgements for work that was never made durable.
- **建议改法和验证点**: Add a minimal event inbox to the existing operation
  state boundary with `event_id` uniqueness, resource identity, revision,
  frozen action list, receipt/process status, attempts, and timestamps. The
  handler must filter the exact app/table, atomically insert-or-recognize the
  event, and return immediately; a worker then fresh-reads each added/edited
  record and calls the existing reconciliation service. It must not trust event
  field values as completion authority. A new edited event whose fresh
  validation digest is already resolved is a no-op. Keep `record_deleted`
  outside this work unit. Tests must cover duplicate ids, new ids with identical
  digests, multi-record action lists, crash/restart boundaries, out-of-order
  revisions, self-write events, missing records, provider/read failure, exact
  resource filtering, and NAV-preflight fallback. Do not add a polling timer.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

## Open Questions

1. **Blocking product decision**: Should an added/edited event automatically
   apply only `missing_completable` fields after all existing safeguards, or
   should it only validate/materialize cases/send receipts and require the
   existing explicit `--apply --confirm` command for every write?

No other blocking question is introduced by this review. Long connection,
exact-resource filtering, and NAV-preflight fallback are the minimal recommended
implementation path if the event entry is accepted into the plan.

## Residual risks and suggested tracking

- **Formula-field changes** — classified: covered by the existing approved NAV
  preflight. The event is a prompt trigger, not the only correctness gate.
- **Feishu app permission/subscription drift** — classified: required readiness
  check in the event-ingress slice and later release runbook; no production
  change is authorized by this plan review.
- **Long-connection client topology** — classified: one singleton receiver in
  the current same-host topology; multi-host/broadcast design remains the
  existing later-work-unit risk.
- **Record deletion behavior** — classified: explicitly outside this work unit;
  this event entry handles only added/edited actions to avoid expanding the
  holdings completion boundary.
- Existing external-write race, unsupported currency evidence, local operator
  authentication, old-binary rollback enforcement, and cross-host locking risks
  remain as classified in the reviewed plan.

## Conclusion

`fail`

The current plan remains strong for manual/NAV-triggered validation and recovery
but is not code-generation-ready for the newly confirmed Feishu message entry.
It explicitly lacks that trigger, leaves background write authority ambiguous,
and has no durable event-delivery handoff. Fixing the three findings requires a
bounded plan revision only; it does not require implementation, a polling timer,
other tables, a generic event framework, production mutation, release, or
deployment.
