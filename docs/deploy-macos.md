# macOS launchd deployment design

Status: design only. No Mac installer, LaunchAgent, Keychain item, or scheduled job has been activated by this document.

## Goal and boundaries

Design a per-user macOS deployment that covers the current Linux API, combined holdings/cash-flow event listener, morning and evening Futu jobs, cash-flow scanner, receipt dispatcher, and quality refresh. Deliver Agent and Listener App Secrets and the quality API read token from the user's macOS Keychain. The exact Python interpreter used by launchd must import the Futu SDK before any Futu/NAV timer can be enabled.

Success means an implementation can render valid plists, pass a noninteractive launchd-context credential/config preflight, enable each consumer independently, show its status, and disable it without deleting business state. Scheduled financial writes and Feishu subscription remain separate operator actions.

Non-goals: changing Linux systemd deployment, Feishu roles or table schema, NAV eligibility, the contents of scheduled business commands, automatic historical NAV replay, background operation before user login or after logout, and implementing or activating the design in this workflow. Commit, PR, release, remote upgrade, and production mutation are outside this design.

The chosen host is a Mac user login session. A LaunchAgent runs in that user's context, not before login. This cannot replace a continuously available Linux production host. Apple documents LaunchAgent login scope and `StartCalendarInterval` wake/off behavior in [Creating Launch Daemons and Agents](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html) and [Scheduling Timed Jobs](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/ScheduledJobs.html).

## Chosen design

### Stable runtime and rendered jobs

The operator prepares the stable checkout, Python 3.12 virtual environment, non-secret canonical config, and local state/log directories before installation. The Mac installer never clones, fetches, upgrades Python packages, imports secrets, or changes a running job. It has a read-only `--plan` mode and an explicit `--apply` mode that writes only the generated plists to `~/Library/LaunchAgents`; it rejects an unstable/missing checkout, wrong OS, missing target interpreter, absent config, or invalid target ownership. Generate plists with stdlib `plistlib`, validate with `plutil -lint`, and use absolute `ProgramArguments` elements rather than shell-interpolated command strings. Render a complete set but load none by default.

Every plist uses the stable checkout as `WorkingDirectory`, absolute interpreter/launcher paths, `PORTFOLIO_CONFIG_FILE`, `PM_DATA_DIR`, `PM_REPORTS_DIR`, `TZ=Asia/Shanghai`, `PM_REQUIRE_SECURE_FEISHU_CREDENTIALS=1`, `PM_CREDENTIAL_BACKEND=keychain`, `PM_KEYCHAIN_FILE=<validated absolute login-Keychain path>`, and `PM_REQUIRE_VENV=1`. The morning/evening plists set `PORTFOLIO_PM_BIN` to the stable checkout's existing `pm` launcher. Add strict-venv handling to that launcher so it exits if `.venv/bin/python` is missing, instead of falling back to global Python; the installer validates this path and all other target executables. The generated environment must not set `CREDENTIALS_DIRECTORY`, `PM_QUALITY_READ_TOKEN`, or any `*_APP_SECRET`. Set `Umask` to `077` (plist integer 63), direct stdout/stderr into a user-owned `~/Library/Logs/portfolio-management` directory with mode `0700`, and keep config and generated plists free of secret bytes. Optional `finnhub_api_key` stays unset in this Mac design. The local Mac timezone must be `Asia/Shanghai` when calendar jobs are enabled; `TZ` in a child process does not schedule launchd itself. Reject a mismatched timezone at activation.

Use one fixed label prefix, `com.liuxie.portfolio-management`, and lock files under the configured state directory. Scheduled jobs do not use `RunAtLoad`; loading them must not itself perform financial writes. API and listener run in the foreground under launchd; `scripts/service.py start` is not their supervisor. KeepAlive restarts only those two long-running jobs. A running instance of a timed job must not be launched again by the installer; `lockf` prevents morning/evening overlap and same-job manual overlap, while existing business locks remain authoritative for records. A lock conflict is an observable skipped attempt, never a success receipt. The Cash Flow scanner uses calendar quarter-hours to retain the Linux trigger times; receipt and quality jobs retain Linux's relative intervals.

The system clock and `/etc/localtime` are checked at activation; do not simulate Asia/Shanghai scheduling with child `TZ`. When the Mac sleeps, calendar wake events may coalesce; when powered off, missed jobs are not replayed. Interval events can be missed while their job is still running. No automatic backfill is added: after a missed morning run, inspect durable receipts/NAV duplicates and use the existing explicit write commands only with separate operator authorization.

### Keychain delivery

Three generic-password items use Keychain service `com.liuxie.portfolio-management` and accounts `pm-feishu-agent-app-secret`, `pm-feishu-listener-app-secret`, and `pm-quality-read-token`. The operator selects one login Keychain file and the installer pins its absolute path in `PM_KEYCHAIN_FILE`; it rejects a missing or wrong-owner path rather than searching the user's default Keychain list. The launchd-context preflight must prove that this file is available after login without a UI prompt. Provision or rotate in that exact file interactively with `/usr/bin/security add-generic-password ... <keychain-file> -w` (the trailing `-w` prompts for the value; validate argument order with a nonproduction item); never pass a password as a command argument, environment value, plist value, YAML field, log line, or chat text. Do not use `-A`. The operator must establish the item's application access decision interactively, then prove retrieval under the same user and launchd job context without displaying the value. Keychain access is scoped to the logged-in user; this design does not claim per-service secret isolation equivalent to Linux systemd credentials. The Keychain CLI's trusted executable access is a material same-user boundary and must be documented in the runbook.

The new explicit backend value `keychain` is accepted only on Darwin. In that mode the existing Feishu credential resolver calls `/usr/bin/security find-generic-password -s <service> -a <credential-name> -w <keychain-file>` with an argument array and a short timeout, captures stdout privately, never logs stdout/stderr, and validates the returned UTF-8 secret with the existing nonempty/size/no-NUL/no-embedded-newline rules. It must use only the pinned file, never the default search list. `src/config.py` applies the same lookup to `quality.read_token` without env/YAML fallback in Keychain mode. Strip only the command's terminal newline. Missing item, locked Keychain, denied prompt, timeout, invalid bytes, conflicting `CREDENTIALS_DIRECTORY`, existing plaintext secret sources, or unsupported platform produce a redacted config issue and **no** plaintext fallback. The Linux `CREDENTIALS_DIRECTORY` path and precedence remain unchanged when the Keychain backend is not selected. The API currently reads `quality.read_token` on each `/quality/status` request; a later Keychain retrieval failure must fail closed with a redacted service-unavailable response, never become a successful auth check or expose the token.

The launcher must force secure mode and backend after any shared non-secret environment source, as the Linux unit currently forces its credential boundary. Agent-only jobs request only the Agent secret; the listener and Feishu preflight request both. Each preflight is a single, noninteractive launchd process. `macos_preflight.sh` runs the two existing commands sequentially and propagates either failure. The quality preflight requests only the quality token and scope. Record the prior run count, use `launchctl kickstart -p` to capture this invocation's PID, wait for that process to finish, then inspect the incremented run count, new exit status, and timestamped redacted log. Treat `launchctl print` as operator diagnostics rather than a stable machine-parsed API; an old `last exit status` or a successful kickstart request is not evidence for this run. An interactive first grant may be done before activation, but a prompt or timeout in background is a failure, not an invitation to weaken access. Secret rotation updates the exact Keychain item, reruns the affected preflight, and restarts affected consumers only after a separate service-change authorization. No automated rollback copies an old plaintext value; restoring it requires an operator-held previous credential or a new rotation.

### Activation, failure, and recovery

1. Prepare a local, stable checkout and Python 3.12 `.venv`; install `requirements.txt` plus the Futu SDK into **that** venv. Before enabling Futu jobs, run exactly the interpreter selected by the strict Mac launcher with `import futu` (or the supported `moomoo` fallback), record package version and exit code, then run `pm config doctor --require-futu --json`. The import's nonzero exit **blocks activation**. The current doctor emits `futu.sdk` only as a warning, so a successful doctor exit never overrides a failed import; treat that warning as an activation failure too. Global Python success is insufficient. Validate the explicit `futu.profiles.lx` and `.sy` mappings used by the scheduled script. Check OpenD login/readiness separately; import alone proves no broker connection.
2. Prepare canonical non-secret Agent/Listener mapping and explicit `futu.profiles` in the selected config. Add the three Keychain items interactively. Run `config doctor --require-secure-feishu`, `events status`, and `config doctor --require-futu --require-quality` locally without displaying identities or secrets. These checks do not enable services or perform business writes.
3. Render plan, inspect paths/labels/arguments/roles, and apply plists. Bootstrap only the Feishu preflight label into `gui/$UID`, run it with `launchctl kickstart`, and verify that this invocation exited successfully. Run the independent quality preflight in the same manner before accepting the API quality endpoint. A successful `bootstrap` or `kickstart` request alone is not preflight success. On failure, leave the affected consumers unloaded.
4. Activate API, quality, write timers, and listener as separate decisions. Before write timers, verify timezone, same-venv Futu import, account mapping, OpenD readiness, and a read-only dry-run. If Linux or another host targets the same accounts/Base, first choose a single active writer: disable its overlapping timers/listener, verify they stopped and no invocation remains, then enable the Mac equivalents; rollback reverses that sequence. Isolated test accounts/Base do not need a production cutover. Before listener, complete the existing Feishu subscription and activation preflight. `launchctl bootstrap gui/$UID <plist>` is the load operation; `launchctl bootout gui/$UID <plist>` disables without deleting data. Observe each job with `launchctl print`, logs, API `/health`, and role-specific business evidence. `/health` proves process availability only and does not prove Keychain quality-token access.
5. For a failed unit, inspect the redacted log and `launchctl print`; fix config/Keychain/SDK/OpenD as appropriate, rerun preflight, and explicitly reload only the affected unit. Do not switch to plaintext fallback. To roll back launchd assets, `bootout` affected labels and restore the previous plist; leave Keychain items, inbox, outbox, SQLite, and NAV rows untouched. Asset replacement, enablement, service restart, Feishu subscription, business canary, and secret cleanup remain distinct authorized actions.

## Alternatives rejected

- Running `scripts/install.sh` on Mac: it delegates to systemd and may prepare a venv before reaching that failure.
- LaunchDaemon at boot: user login Keychain access and GUI-session context would require a different credential architecture; this design explicitly targets a logged-in user's Mac.
- Secret in plist, shell profile, environment file, or temporary credential file: creates plaintext at-rest or process-environment exposure and bypasses the requested Keychain boundary.
- Cron or a custom scheduler: launchd already owns per-user timed jobs; custom replay of missed financial writes would change business behavior.
- A new Python lock framework: macOS provides `/usr/bin/lockf`, while repository business-level locks already use `fcntl`.

## Risks and open questions

| Item | Classification | Owner and destination |
| --- | --- | --- |
| A Keychain item trusted for `/usr/bin/security` may be retrievable by another process under the same logged-in user; it does not provide Linux per-unit credential isolation. | Accepted design limit | Operator/security owner: document same-user trust boundary before activation; choose a signed dedicated helper only if stronger isolation is required. |
| Keychain prompt, locked login Keychain, logout, sleep, power-off, or removed checkout can make the Mac miss work. | Accepted design limit | Operator: use launchd-context preflight and explicit recovery; keep Linux as the continuous production scheduler. |
| Exact `security -w` terminal-newline behavior and unattended access need empirical validation on the target macOS release. | Validation gate | S1 implementer: use nonproduction Keychain items; block activation until confirmed. |
| `requirements.txt` omits Futu SDK; a new venv is not ready merely because global Python imports it. | Validation gate | S3 implementer: document/install the known compatible Mac SDK in the target venv and record its version before enabling Futu timers. |
| Separate hosts can write the same accounts/Base even when each host holds its own local lock. | Activation gate | Operator: use isolated test targets or an explicit single-writer cutover and reversal record before enabling Mac writes/listener. |
